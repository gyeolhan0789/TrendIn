# k6 측정

엔드포인트를 하나씩 격리해 한계를 찾는다. 사용자 여정 시나리오는 이 다음 단계다.

```bash
cd ~/S15P21A102/docs/load-test/k6
./run.sh                             # 전부 (엔드포인트당 3분, 총 25분쯤)
./run.sh endpoint/notifications.js   # 하나만
PEAK_RPS=300 ./run.sh endpoint/notifications.js
```

결과는 `results/<이름>-<시각>.txt` 에 남는다.

## 왜 EC2 에서 돌리나

대상이 `127.0.0.1:18080` 에만 열려 있다. 밖에서 닿지 않는다. SSH 터널로 로컬에서
돌리면 p95 가 서버 성능이 아니라 인터넷 왕복 시간을 재게 된다.

대가로 k6 가 같은 CPU 를 쓴다. Grafana 의 CPU 패널에서 **프로세스(백엔드)는 여유가
있는데 시스템만 1 에 붙으면 k6 가 병목**이라는 뜻이다. 그때 나온 숫자는 서버의
한계가 아니므로 `PEAK_RPS` 를 낮춰 다시 잰다.

## 한계를 찾는 법 — sweep

한 번 돌려 나온 p95 하나는 한계가 아니다. 도착률을 올려 가며 **달성 RPS 가 목표를
못 따라가기 시작하고 `dropped_iterations` 가 붙는 첫 지점**을 찾아야 한다.

```bash
./sweep.sh endpoint/notifications.js            # 5 10 20 40
./sweep.sh endpoint/notifications.js 2 5 10 20  # 직접 지정
```

회차마다 짧게(1분 30초) 돌고 끝에 표를 찍는다.

```
목표RPS    달성RPS      p95          실패율     드롭
5          9.9/s        142ms        0.00%      0
10         19.8/s       310ms        0.00%      0
20         24.1/s       4.2s         0.00%      1832     ← 여기가 무릎
40         19.6/s       56.6s        3.12%      9497
```

무릎을 찾으면 그 값으로 `run.sh` 를 한 번 길게 돌려 정식 수치를 남긴다.

**위에서부터 시작하지 않는다.** 처음부터 높게 잡으면 포화 이후만 보게 된다.
그때 나온 p95 는 서버 성능이 아니라 큐에서 기다린 시간이다.

## k6 가 병목이 아닌지 확인한다

k6 는 대상과 같은 EC2 에서 돈다. 서버가 느려질수록 VU 가 쌓이고, VU 수백 개가
뜨면 k6 자신이 CPU 를 먹는다. 그래서 `maxVUs` 기본값을 200 으로 묶어 두었다
(`MAX_VUS` 로 조절).

측정 중 Grafana 의 CPU 패널을 본다.

- **프로세스가 1 에 붙음** → 백엔드가 한계다. 정상 결과
- **시스템만 붙고 프로세스는 여유** → k6 가 CPU 를 뺏었다. 이 숫자는 못 쓴다

요청 하나가 15초를 넘기면 끊는다(`REQUEST_TIMEOUT`). 그 시점의 서버는 이미 쓸
수 없는 상태라 더 기다려 봐야 큐 대기 시간만 재게 되고, k6 기본값 60초로 두면
붕괴한 측정이 몇 분을 더 끈다.

## 개선 전후를 비교한다 — bench

`sweep.sh` 는 한계를 찾고, `bench.sh` 는 **같은 조건에서 반복 측정**한다. 개선
전후를 나란히 놓으려면 후자가 필요하다.

```bash
./bench.sh baseline           # 지금 상태
# ... 고친다 ...
./bench.sh indexed            # 고친 뒤
./compare.sh baseline indexed
```

```
엔드포인트                                p95 (baseline) p95 (indexed)     변화
-------------------------------------------------------------------------------
GET /members/me/notifications                     1820.0         42.0      97.7%
GET /trends                                        250.0        270.0      -8.0%
```

### 무엇을 고정하나

| | |
| --- | --- |
| 도착률 | 내내 **10 RPS**. 램프를 쓰지 않는다 |
| 길이 | 본 측정 1분 |
| 워밍업 | 측정 전 20초, 결과는 버린다 |
| 데이터 | 재시딩 금지 |

**램프를 쓰지 않는 이유.** 램프에는 낮은 부하 구간이 섞여 있다. 그 구간의 비율이
조금만 달라져도 p95 가 흔들려, 개선 때문인지 측정 때문인지 가릴 수 없다.

**10 RPS 인 이유.** 무릎 한참 아래다. 큐 대기가 섞이지 않아 **서버가 실제로 일한
시간**만 남는다. 포화 상태에서 잰 p95 는 대기 시간이라 개선해도 잘 줄지 않는다.

**워밍업이 필요한 이유.** 두 번째로 잰 쪽은 버퍼 풀과 JIT 가 이미 데워져 있어
그냥 빠르다. 워밍업이 없으면 그 차이를 개선으로 착각한다.

### 두 숫자를 같이 남긴다

개선은 두 방향으로 나타난다.

- **p95** (`bench.sh`) — 같은 부하에서 얼마나 빨라졌나
- **한계 RPS** (`sweep.sh`) — 얼마나 더 받을 수 있게 됐나

하나만 재면 절반을 놓친다. 인덱스를 넣으면 보통 둘 다 좋아지지만, 캐시나 커넥션
풀을 손댄 경우 한쪽만 움직이기도 한다.

## 토큰을 미리 받는 이유

`setup()` 에서 토큰 50개를 발급해 VU 들이 나눠 쓴다. VU 마다 로그인시키면 bcrypt
해싱이 CPU 를 차지해 **로그인이 가짜 병목**으로 잡힌다. 실제 사용자도 15분짜리
토큰으로 여러 번 조회한다. 로그인 비용은 `endpoint/auth-login.js` 에서만 잰다.

## 스크립트

| 스크립트 | 무엇을 보나 | 기본 RPS |
| --- | --- | ---: |
| `trends-list.js` | 인증 없는 목록. 다른 측정의 기준선 | 50 |
| `trend-contents.js` | `keyword_contents` 가 `keyword_id` 단독 조회를 받는다 | 30 |
| `notifications.js` | **`notifications` 에 `member_id` 인덱스가 없다** | 20 |
| `saved-trends.js` | 인덱스가 있는 개인화 조회. 비교군 | 20 |
| `trend-history.js` | 450만 행 위의 기간별 조회 | 30 |
| `trend-regions.js` | 242만 행 + `journey` 의 나라별 집계 | 20 |
| `auth-login.js` | bcrypt. 데이터 양과 무관한 비용 | 20 |

**헤비 회원으로 잰다.** 시드가 회원을 `id % 100` 으로 갈라, 95~99 인 회원에게
알림 300~1,500건과 저장 100~500건을 몰아줬다. 평균 회원만 재면 문제가 드러나지
않는다. `lib/config.js` 의 `heavyMemberId()` 가 그 규칙에서 id 를 계산한다 —
특정 id 를 박아 두면 시드 규모를 바꿀 때 조용히 어긋나기 때문이다.

**상위 트렌드를 고른다.** 콘텐츠의 70% 와 국가 데이터 전부가 상위 2,000 개
키워드에 몰려 있다. 그 밖을 고르면 빈 결과가 와서 아무것도 재지 못한다.

## Grafana 와 함께 보기

k6 의 터미널 요약은 클라이언트가 본 것이고, 서버 안에서 무슨 일이 있었는지는
Grafana **TrendIn 부하테스트** 대시보드가 보여준다. 상단 `대상` 을
`backend-loadtest` 로 두고 본다.

특히 **HikariCP 대기(pending)** 를 본다. 0 을 넘으면 커넥션 풀이 마른 것이고,
그때는 API 코드를 아무리 고쳐도 소용없다.

k6 결과까지 같은 그래프에 얹으려면 remote write 로 밀어넣는다. Phase 0 에서
Prometheus 에 수신을 켜 뒀다.

```bash
export K6_PROMETHEUS_RW_SERVER_URL=http://localhost:9090/api/v1/write
export K6_OUT=experimental-prometheus-rw   # k6 버전에 따라 이름이 다르다
./run.sh
```

출력 이름이 맞지 않으면 k6 가 시작하며 거절한다. 그때는 이 줄만 빼면 터미널
요약과 `results/*.txt` 로 충분하다.
