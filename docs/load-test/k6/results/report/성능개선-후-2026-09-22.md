# 부하테스트 결과 — 성능 개선 후 (2026-09-22)

`notifications` 에 `member_id` 인덱스를 넣고 다시 쟀다. [성능개선-전](성능개선-전-2026-09-21.md)
과 짝이 되는 문서다.

**이 문서의 비교 대상은 `bench.sh` 의 10 RPS 고정 측정이다.** 개선 전 리포트의 "p95 56.6초"
와 여기의 "7.33ms" 를 나란히 놓으면 안 된다 — 앞의 것은 3분 램프로 포화시킨 값이고 뒤의 것은
무릎 아래에서 잰 값이다. **900.55ms → 7.33ms** 가 같은 조건의 비교다.

---

## 세 줄 요약

1. **알림이 123배 빨라졌다.** 목록 p95 900.55ms → **7.33ms**, 안 읽은 개수 608.11ms →
   **4.39ms**. 인덱스 두 개가 전부다.
2. **이제 비교군보다 빠르다.** `saved-trends`(15.39ms)가 인덱스 있는 개인화 조회의 기준이었는데,
   알림이 그 절반이다. 목표(30ms 아래)를 크게 넘겼다.
3. **다른 엔드포인트 몇 개가 나빠진 것처럼 보이지만 잡음이다.** 중앙값은 ±11% 안에 있고,
   p95 만 흔들렸다. 아래에 근거를 적었다.

**드롭이 0 이라는 것이 핵심이다.** 목표 도착률을 양쪽 다 온전히 채웠으므로 큐 대기가 섞이지
않았고, p95 는 서버가 실제로 일한 시간이다.

**바뀐 것은 인덱스 두 개뿐이다.**

## 🟢 알림 — 목표 초과 달성

| | before | after | 배수 |
| --- | ---: | ---: | ---: |
| 목록 avg | 424.46ms | **4.90ms** | 87× |
| 목록 med | 359.29ms | **4.53ms** | 79× |
| 목록 **p95** | 900.55ms | **7.33ms** | **123×** |
| 안 읽은 개수 avg | 229.60ms | **2.80ms** | 82× |
| 안 읽은 개수 med | 174.07ms | **2.60ms** | 67× |
| 안 읽은 개수 **p95** | 608.11ms | **4.39ms** | **139×** |

**알림 패널 한 번 여는 DB 비용이 654ms → 7.7ms 다.** 85배 줄었다.

avg·med·p95 가 **전부 같은 배수로** 움직인 것이 중요하다. 한쪽만 줄었다면 잡음을 의심해야
하지만, 분포가 통째로 내려앉았다. 풀스캔이 인덱스 스캔으로 바뀐 것 말고는 설명할 방법이 없다.

### 비교군을 추월했다

| 엔드포인트 | p95 | 인덱스 |
| --- | ---: | --- |
| `GET /members/me/notifications` | **7.33ms** | (신규) `(member_id, created_at DESC, id DESC)` |
| `.../unread-count` | **4.39ms** | (신규) `(member_id) WHERE is_read = false` |
| `GET /members/me/saved-trends` | 15.39ms | 기존 |

개선 전 리포트에서 `saved-trends` 12.5ms 를 "정상 수준" 의 근거로 삼고 목표를 30ms 로 잡았는데,
결과가 그 절반이다. 정렬 순서까지 인덱스에 맞춘 것이 이유로 보인다 — 플래너가 `LIMIT 20` 에서
인덱스를 20행만 걷고 멈출 수 있다.

**다만 `EXPLAIN` 으로 확인한 것은 아니다.** 아래 "확인하지 못한 것" 을 본다.

## 🟡 나빠진 것처럼 보이는 것들 — 잡음이다

`GET /trends` +37%, 콘텐츠 +49% 는 그냥 두면 "인덱스가 다른 곳을 느리게 했다" 로 읽힌다.
그렇게 보지 않는 근거가 셋이다.

### 1. 중앙값은 거의 안 움직였다

p95 는 600개 표본의 꼬리라 흔들린다. 중앙값을 보면 다른 그림이 나온다.

| 엔드포인트 | med 변화 | p95 변화 |
| --- | ---: | ---: |
| `GET /trends/{id}/contents` | **+1.5%** | +49.2% |
| `GET /trends/{id}` | +2.2% | +5.6% |
| `GET /members/me/interest-keywords` | +6.5% | +15.9% |
| `GET /members/me/saved-trends` | +7.0% | +23.1% |
| `GET /trends` | +15.3% | +37.0% |
| `POST /auth/login` | **−10.6%** | −15.1% |

콘텐츠는 **중앙값이 1.5% 움직였다.** 일하는 시간은 그대로이고 꼬리만 길어졌다. 부하가 아니라
간섭의 모양이다.

### 2. DB 를 안 쓰는 엔드포인트가 15% 빨라졌다

`POST /auth/login` 은 bcrypt CPU 비용이 전부다. 인덱스와 아무 관계가 없는데 p95 가
114.22 → 96.98ms 로 **좋아졌다.** 두 회차 사이에 **머신 상태가 달랐다**는 뜻이다.

에러를 즉시 돌려주는 `regions` 세 개도 11~18% 빨라졌다. 같은 이유다.

### 3. DB 를 운영과 공유한다

EC2 가 한 대라 `trendin_test` 는 운영과 **같은 PostgreSQL 인스턴스** 안에 있다. 버퍼 풀·WAL·
디스크가 공유된다. 두 회차는 **2시간 30분 떨어져 있다**(11:06 ↔ 13:36). 그 사이 운영 트래픽과
파이프라인 배치가 같았다고 볼 근거가 없다.

### 그래도 하나는 남는다

`GET /trends` 는 중앙값도 **+15.3%** 다. 다른 것들보다 크다. 이건 잡음으로 넘기지 말고
다음 작업에서 확인할 목록에 올린다. 개선 전 리포트가 이미 이 엔드포인트를 커넥션 풀
용의자로 지목했다.

## 확인하지 못한 것

정직하게 남긴다.

**`EXPLAIN` 증거가 없다.** 벽시계 시간이 123배 줄었다는 것은 측정됐지만, 계획이
`Seq Scan` → `Index Scan` 으로 바뀐 기록을 남기지 않았다. 특히 부분 인덱스
`idx_notifications_member_unread` 가 실제로 쓰였는지 모른다 — Hibernate 가 `is_read = ?` 로
바인드 파라미터를 내보내면 플래너가 그 인덱스를 못 쓴다. 안 쓰였어도 다른 인덱스가
`member_id` 를 받으므로 수치는 이만큼 나올 수 있다. 확인은 [V12 주석](../../../../../backend/src/main/resources/db/migration/V12__notification_member_indexes.sql)
의 질의로 한다.

**한계 RPS 를 재지 않았다.** `bench.sh` 는 "같은 부하에서 얼마나 빨라졌나" 만 답한다.
"얼마나 더 받을 수 있게 됐나" 는 `sweep.sh` 로 따로 재야 한다. 개선 전 리포트에서 무릎을
못 찾은 항목이 그대로 남아 있다.

**`{id}` 계열은 `compare.sh` 가 자동 비교하지 못한다.** baseline 회차는 엔드포인트 이름이
`GET /trends/{id` 로 잘리던 옛 `bench.sh` 로 돌았고, indexed 회차는 고친 뒤에 돌았다. 위 표의
그 행들은 raw 파일에서 손으로 짝지은 값이다. 다음 회차부터는 자동으로 맞는다.

**운영은 아직 개선되지 않았다.** 아래를 본다.

## ⚠️ 이 개선은 아직 사용자에게 가지 않았다

| | 인덱스 |
| --- | --- |
| `trendin_test` (부하테스트) | ✅ **psql 로 손으로 넣었다** |
| `forever102` (운영) | ❌ **없다** |

V12 마이그레이션은 `dev` 에 있지만, **파일이 저장소에 있는 것과 운영 DB 에 적용된 것은 다르다.**
운영 백엔드가 새 이미지로 배포되어 Flyway 가 V12 를 돌려야 실제 사용자의 알림이 빨라진다.

배포 후 로그에 `Migrating schema "public" to version "12"` 가 보이면 끝이다.

### 뒷정리가 남아 있다

측정이 끝났으므로 `trendin_test` 에 손으로 넣은 인덱스를 **지워야 한다.**

```sql
DROP INDEX idx_notifications_member_created;
DROP INDEX idx_notifications_member_unread;
```

안 지우면 새 이미지로 `./up.sh --recreate` 할 때 Flyway 가 V12 를 돌리다
`relation "idx_notifications_member_created" already exists` 로 죽고 `backend-loadtest` 가
기동하지 않는다.

## 다음에 할 일

우선순위 순. 개선 전 리포트의 목록에서 알림 항목이 빠지고 순서가 바뀌었다.

1. **운영에 V12 를 배포한다.** 이걸 해야 이번 작업이 사용자에게 닿는다.
2. **`trendin_test` 의 손으로 넣은 인덱스를 지운다.** 안 지우면 다음 `up.sh --recreate` 가 깨진다.
3. **`GET /trends/{id}/regions` 의 실제 응답을 확인한다.** 200 응답률이 여전히 0% 다. 다만
   운영 재배포 후에 봐야 한다 — 팀원 수정이 아직 이 컨테이너에 없다.
4. **`GET /trends/{id}/contents` 로 넘어간다.** 부하 시 p95 55.8초로 남은 최악이다. 성질이
   알림과 다르다 — 10 RPS 에서 95ms 라 **쿼리는 준수하고 처리량에서 막힌다.**
   `keyword_contents` 의 PK 가 `(content_id, keyword_id)` 라 `keyword_id` 단독 조회가 선두
   컬럼을 못 쓴다.
5. **`GET /trends` 의 Hikari `pending` 을 본다.** 10 RPS 에서 25~34ms 인 질의가 부하에서 10초가
   됐고, 이번 회차에서 중앙값이 15% 움직인 유일한 엔드포인트이기도 하다. `maximum-pool-size` 가
   설정돼 있지 않아 커넥션이 기본 10개다.
6. **`sweep.sh` 로 알림의 새 한계 RPS 를 잰다.** 스크립트 버그는 고쳤다. p95 와 처리량은 다른
   축이라, 하나만 재면 절반을 놓친다.
