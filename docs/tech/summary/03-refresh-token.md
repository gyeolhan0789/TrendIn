# 리프레시 토큰 — 동시 요청에서도 세션이 어긋나지 않게

> 검증과 쓰기 사이에 끼어드는 요청 때문에 **로그아웃한 세션이 되살아나는** 문제를 Redis Lua 스크립트로 막았다.

---

## 문제 상황

JWT 기반 인증에서 리프레시 토큰을 Redis 에 보관하는 구조를 만들었다. 재발급과 로그아웃은 둘 다 같은 모양이었다.

```
① 저장된 토큰을 읽는다
② 제시된 토큰과 같은지 확인한다
③ 같으면 교체(재발급)하거나 삭제(로그아웃)한다
```

**①과 ③ 사이에 다른 요청이 끼어들 수 있다는 것**을 뒤늦게 알았다.

```
로그아웃:  GET → (일치) ─────────────→ DEL
재발급:              GET → (일치) → SET   ← 로그아웃이 지운 키를 되살린다
```

사용자는 로그아웃했는데 **세션이 살아 있는 상태**가 된다. 토큰을 탈취당한 상황에서 로그아웃으로 끊으려 해도 끊기지 않는다는 뜻이라, 보안 문제로 봤다.

프런트에서 토큰 만료 직전에 재발급이 자동으로 나가는 구조라 **실제로 겹칠 가능성이 있었다.** 탭을 여러 개 열어 두면 동시에 재발급이 두 번 나가기도 한다.

## 내가 접근한 방법

"락을 어떻게 걸까"로 가기 전에 **문제의 범위를 좁혔다.**

- 경쟁이 일어나는 자원은 **회원 한 명의 키 하나**다. 여러 키에 걸친 트랜잭션이 아니다.
- 필요한 보장은 **"읽고 비교하고 쓰는 것이 쪼개지지 않을 것"** 하나다.
- 처리량이 큰 경로가 아니다. 재발급은 토큰 만료 주기(15분)마다 한 번, 로그아웃은 더 드물다.

범위가 **단일 키의 compare-and-set** 으로 좁혀지자 선택지가 분명해졌다. 분산 락처럼 무거운 장치는 필요 없었다.

## 여러 가지 대안

| 대안 | 왜 택하지 않았나 |
| --- | --- |
| **애플리케이션 레벨 `synchronized`** | 서버가 여러 대로 늘면 깨진다. 지금은 한 대지만 확장을 막는 선택이다 |
| **`WATCH` / `MULTI` / `EXEC`** (낙관적 잠금) | 동작은 하지만 **왕복이 늘고**(WATCH → GET → MULTI → EXEC) 충돌 시 재시도 루프를 직접 짜야 한다. 단일 키에는 과하다 |
| **Redisson 분산 락** | 라이브러리 의존성이 늘고, 락 획득·해제·만료라는 **또 다른 실패 모드**가 생긴다. 단일 키 CAS 에 쓸 도구가 아니다 |
| **PostgreSQL 에 저장 + `UPDATE ... WHERE token = ?`** | DB 가 원자성을 보장하므로 정합성은 해결된다. 하지만 **만료 토큰 청소를 배치로 따로 돌려야** 하고, 인증 경로마다 DB 를 치게 된다 |
| **세션 기반 인증으로 회귀** | 서버 상태를 늘리는 방향이라 확장에 불리하다. JWT 를 고른 전제와 어긋난다 |
| **Lua 스크립트** | ← **선택** |

## 왜 이 기술을 사용했는지

**Redis 는 Lua 스크립트를 직렬로 실행한다.** 검증과 쓰기를 한 스크립트에 넣으면 그 전체가 원자 단위가 되고, 중간에 다른 명령이 끼어들 수 없다.

```lua
-- 회전: 저장된 해시가 제시된 토큰의 것과 같을 때만 새 토큰으로 교체
if redis.call('GET', KEYS[1]) == ARGV[1] then
    redis.call('SET', KEYS[1], ARGV[2], 'PX', ARGV[3])
    return 1
end
return 0
```

이 선택이 좋았던 이유는 세 가지다.

**왕복이 한 번이다.** `WATCH`/`MULTI` 는 네 번 오가지만 스크립트는 한 번이다. 재시도 루프도 필요 없다.

**추가 의존성이 없다.** 이미 쓰고 있는 Redis 의 기능이다. 락 매니저 같은 새 실패 모드가 생기지 않는다.

**실패가 예외가 아니라 반환값이다.** `0` 이 돌아오면 "이 토큰은 이미 회전됐거나 로그아웃됐다"는 뜻이고, 호출부는 그걸 정상 흐름으로 다룬다. 예외로 던지면 레이스라는 **정상적으로 일어날 수 있는 일**을 장애처럼 취급하게 된다.

**같은 토큰으로 동시에 들어온 요청은 하나만 성공한다.** 두 번째는 저장된 해시가 이미 바뀌어 있어 `0` 을 받는다. 이 성질은 나중에 **토큰 재사용 탐지**(탈취된 토큰이 쓰이면 세션 전체를 끊는 기능)의 토대가 된다.

## 어떤 과정으로 해결했는지

**1. 키 구조를 회원당 하나로 정했다.**

```
refresh:member:{memberId}
```

토큰마다 키를 만들면 "이 회원의 모든 세션 끊기"가 `KEYS` 스캔이 된다. 회원당 하나면 새로 로그인할 때 자연스럽게 덮어써지고 **마지막 토큰만 유효**하다. 탈퇴할 때도 키 하나만 지우면 전 기기가 끊긴다.

**2. 원문 대신 SHA-256 해시를 저장했다.**

Redis 덤프가 유출돼도 토큰을 그대로 쓸 수 없다. 비교는 해시끼리 하므로 기능에는 영향이 없다.

**3. TTL 을 값에 붙였다.**

`SET ... PX` 로 만료를 Redis 에 맡겼다. 별도 청소 배치가 필요 없다는 점이 PostgreSQL 대안 대비 가장 큰 이점이었다.

**4. 연산별로 의미를 나눴다.**

| 연산 | 동작 | 이유 |
| --- | --- | --- |
| `save` | 무조건 덮어쓰기 | 새 로그인은 기존 세션을 대체한다 |
| `rotate` | **일치할 때만** 교체 | 이미 회전된 토큰으로는 재발급 불가 |
| `deleteIfMatches` | **일치할 때만** 삭제 | 남의 토큰으로 내 세션을 끊을 수 없다 |
| `deleteAll` | 무조건 삭제 | 탈퇴는 어느 기기에서 했든 전부 끊는다 |

**5. 탈퇴 시 삭제를 트랜잭션 안에 뒀다.**

Redis 는 롤백되지 않으므로 어느 쪽에 둘지 고민이 있었다. 두 방향의 실패를 비교했다.

- **트랜잭션 안 → DB 실패**: 세션만 지워진다. 다시 로그인하면 그만이다
- **트랜잭션 밖 → Redis 실패**: **회원이 사라졌는데 토큰이 살아 있다**

피해가 작은 쪽을 골랐다.

**6. 남는 위험을 문서화했다.**

액세스 토큰은 서명과 만료만 보는 JWT 라 **로그아웃·탈퇴 후에도 남은 유효 기간(최대 15분) 동안 통과한다.** 블랙리스트를 두면 막을 수 있지만 **조회마다 Redis 를 치게 되어** JWT 를 고른 이유가 사라진다. 만료를 15분으로 짧게 가져가는 선에서 타협하고, 그 사실을 코드 주석과 기술 문서에 남겼다.

## 결과

- **로그아웃한 세션이 되살아나는 경로가 사라졌다.** 동시 요청 중 하나만 성공하도록 Redis 가 보장한다.
- **왕복 한 번, 추가 의존성 0.** 분산 락이나 재시도 루프 없이 해결했다.
- **서버를 여러 대로 늘려도 유효하다.** 애플리케이션이 아니라 Redis 가 직렬성을 보장하므로 인스턴스 수와 무관하다.
- **확장 지점이 생겼다.** `rotate` 가 `false` 를 돌려주는 순간이 곧 "이미 쓴 토큰이 다시 왔다"는 신호다. 토큰 재사용 탐지를 붙일 자리가 이미 마련돼 있다.

**가장 크게 배운 것은 범위를 좁히는 일이 도구 선택을 결정한다는 점이다.** "동시성 문제"로 두면 분산 락을 찾게 되지만, "단일 키 compare-and-set"으로 좁히면 Lua 스크립트 7줄로 끝난다. 문제를 정확히 규정하는 데 쓴 시간이 구현 시간보다 길었고, 그게 맞는 비율이었다고 생각한다.
