# 알림 조회 p95 900ms → 7ms

> 인덱스 두 개로 응답 시간을 **123배** 줄였다. 코드 변경은 없었다.

---

## 문제 상황

부하테스트를 돌려 보니 알림 두 엔드포인트만 유독 느렸다.

| 엔드포인트 | p95 |
| --- | ---: |
| `GET /members/me/notifications` | **900.55ms** |
| `GET /members/me/notifications/unread-count` | **608.11ms** |
| `GET /members/me/saved-trends` ← 비교군 | 12.50ms |

성격이 같은 개인화 조회인데 **72배** 차이였다. 특히 안 읽은 개수는 헤더에 늘 붙어 있어 **화면을 넘길 때마다 호출**되는 API 였다.

큐 대기가 없는 도착률에서 잰 값이었으므로(`dropped_iterations` 0), 저 900ms 는 네트워크나 대기가 아니라 **서버가 실제로 일한 시간**이었다.

## 내가 접근한 방법

"느리다"를 "무엇이 느린가"로 좁히는 것부터 했다.

세 가지를 순서대로 확인했다.

1. **비교군을 세웠다.** `saved-trends` 는 같은 구조의 개인화 조회인데 12.5ms 였다. 이 차이가 "원래 그런 것"이 아니라 **이 엔드포인트만의 문제**임을 먼저 확정했다.
2. **스키마를 읽었다.** `notifications` 의 인덱스는 PK 와 `dedup_key` 유니크 둘뿐이었다. 외래키 `fk_notifications_member` 가 있었지만 **PostgreSQL 은 외래키에 인덱스를 만들어 주지 않는다.**
3. **질의 패턴을 모았다.** `NotificationRepository` 의 조회는 전부 `where member_id = ?` 로 시작하고 있었다.

인덱스 없이 68만 행을 스캔하고 있었다는 결론이 나왔다.

## 여러 가지 대안

| 대안 | 왜 택하지 않았나 |
| --- | --- |
| **`(member_id)` 단일 인덱스** | 풀스캔은 면하지만 그 회원의 행을 **전부 꺼내 정렬한 뒤** 20개만 남긴다. 헤비 회원은 알림이 1,500건이다 |
| **`(member_id, is_read)` 복합 인덱스** | 읽은 알림(70%)까지 색인해 인덱스가 3배 커진다. 안 읽은 개수만 세는 질의에는 과하다 |
| **Redis 에 안 읽은 개수 캐싱** | 알림 생성·읽음 처리마다 무효화가 필요해 **정합성 문제를 새로 만든다.** DB 가 7ms 면 캐시를 둘 이유가 없다 |
| **`members.unread_count` 비정규화** | 같은 이유. 쓰기 경로마다 카운터를 맞춰야 하고 틀어지면 되돌리기 어렵다 |
| **커서 페이지네이션으로 `count(*)` 제거** | 유효한 개선이지만 **API 스펙과 프런트를 같이 바꿔야 한다.** 인덱스만으로 목표를 넘겨 보류했다 |

**인덱스를 먼저 시도한 이유는 되돌리기 쉬워서다.** 캐시나 비정규화는 한번 넣으면 걷어내기 어렵지만, 인덱스는 `DROP` 한 줄이고 애플리케이션 코드를 건드리지 않는다. 가장 싼 수단으로 목표를 넘길 수 있는지부터 확인했다.

## 왜 이 기술을 사용했는지

최종적으로 **복합 인덱스 + 부분 인덱스** 조합을 썼다.

```sql
CREATE INDEX idx_notifications_member_created
    ON notifications (member_id, created_at DESC, id DESC);

CREATE INDEX idx_notifications_member_unread
    ON notifications (member_id) WHERE is_read = false;
```

**복합 인덱스에 정렬 순서까지 담은 이유.** 질의가 `order by created_at desc limit 20` 이다. 인덱스가 그 순서와 같으면 플래너는 **인덱스를 20행만 걷고 멈춘다.** 실행 계획에서 `Sort` 노드가 통째로 사라진다. `member_id` 만 색인하면 1,500행을 꺼내 정렬하는 비용이 그대로 남는다.

**`id DESC` 를 tie-breaker 로 둔 이유.** `created_at` 이 같은 행의 순서를 고정하기 위해서다. 없으면 같은 시각의 알림이 **페이지를 넘길 때마다 순서가 달라져 행이 중복되거나 누락된다.** 성능이 아니라 정확성 문제다.

**부분 인덱스를 고른 이유.** 알림의 70%가 읽은 상태라 `WHERE is_read = false` 로 걸러 색인하면 `(member_id, is_read)` 보다 **3배 작다.** 엔트리가 전부 "안 읽음"이라 `count` 가 인덱스만 읽고 끝나고, 읽음 처리로 `is_read` 가 `true` 가 되면 그 엔트리는 **인덱스에서 빠져** 표가 더 줄어든다.

덤으로 복합 인덱스가 `Page` 가 쏘는 `count(*)` 까지 받는다. 선두 컬럼만 쓰므로 Index Only Scan 이 된다. **인덱스 하나가 목록과 카운트를 동시에 처리한다.**

**인덱스를 두 개나 둘 수 있었던 이유는 이 서비스가 읽기 중심이기 때문이다.** 인덱스는 조회를 빠르게 하는 대신 **INSERT·UPDATE·DELETE 마다 인덱스도 갱신**해야 해서 쓰기가 느려진다. 쓰기가 잦은 표라면 "인덱스 두 개"는 쉽게 꺼낼 카드가 아니다.

`notifications` 의 쓰기·읽기 비율을 따져 보니 비대칭이 뚜렷했다.

| | 빈도 |
| --- | --- |
| **INSERT** | **하루 한 번** — 알림 생성 배치(`0 0 0 * * *`)가 유일한 경로다 |
| **UPDATE** | 알림을 읽을 때. 사용자당 하루 몇 번 |
| **SELECT (목록)** | 알림 벨을 열 때마다 |
| **SELECT (안 읽은 개수)** | **헤더에 늘 붙어 있어 화면을 넘길 때마다** |

서비스 전체도 같은 구조다. 트렌드·키워드·지표·AI 해설은 **Spark 파이프라인이 배치로 적재**하고 백엔드는 읽기만 한다. 백엔드가 직접 쓰는 것은 회원·관심 키워드·저장 목록처럼 사용자 행동에 따른 소량뿐이다.

**쓰기 비용은 하루 한 번 배치에서만 발생하고, 그 대가로 하루 종일 일어나는 조회가 빨라진다.** 트레이드오프가 한쪽으로 크게 기울어 있어 인덱스를 적극적으로 쓰는 것이 맞는 선택이었다.

## 어떤 과정으로 해결했는지

1. **기준선을 고정했다.** 램프 없이 10 RPS 1분(`bench.sh`)으로 재는 측정을 따로 만들었다. 포화시킨 측정은 큐 대기가 섞여 개선 전후를 비교할 수 없다.
2. **마이그레이션을 추가했다.** `V12__notification_member_indexes.sql`. Flyway 가 스키마를 소유하므로 운영 반영도 배포 한 번이다.
3. **같은 조건에서 다시 쟀다.** 2시간 30분 뒤, 같은 시나리오·같은 이미지·재시딩 없이. 바뀐 것은 인덱스 둘뿐이었다.
4. **비교 가능성부터 검증했다.** 완료 반복 600–601, `dropped_iterations` 0 — 양쪽 다 목표 도착률을 온전히 채웠음을 확인하고 나서 숫자를 읽었다.
5. **의도와 근거를 마이그레이션 주석에 남겼다.** 왜 정렬 순서까지 넣었는지, 부분 인덱스의 전제가 무엇인지, 전제가 깨지면 어떻게 바꿔야 하는지까지 적었다. 인덱스는 지우기 쉬워서 **이유를 모르면 지워진다.**

## 결과

| 지표 | before | after | 배수 |
| --- | ---: | ---: | ---: |
| 목록 avg | 424.46ms | **4.90ms** | 87× |
| 목록 med | 359.29ms | **4.53ms** | 79× |
| **목록 p95** | **900.55ms** | **7.33ms** | **123×** |
| 안 읽은 개수 avg | 229.60ms | **2.80ms** | 82× |
| **안 읽은 개수 p95** | **608.11ms** | **4.39ms** | **139×** |

**알림 패널을 한 번 여는 DB 비용이 654ms → 7.7ms 가 됐다.** 85배다.

목표는 비교군(`saved-trends` 12.5ms)을 근거로 "30ms 아래"로 잡았는데, 결과는 **비교군의 절반**이었다.

avg·med·p95 가 **전부 비슷한 배수로** 움직인 점을 확인했다. 한쪽만 줄었다면 잡음을 의심해야 한다.

**남은 과제.** `EXPLAIN (ANALYZE, BUFFERS)` 로 플래너가 실제로 그 인덱스를 골랐는지는 확인하지 못했다. 벽시계 시간이 123배 줄었다는 것은 측정됐지만 계획 자체를 본 것은 아니다. 특히 부분 인덱스는 **조건이 SQL 에 리터럴로 박혀야** 쓰이는데, Hibernate 가 `is_read = ?` 로 파라미터를 내보내면 적용되지 않는다. 확인 후 안 쓰이면 `(member_id, is_read)` 로 바꿀 계획이다.
