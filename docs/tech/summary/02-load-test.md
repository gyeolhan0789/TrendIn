# 믿을 수 있는 부하테스트 환경 만들기

> 숫자를 내는 것보다 **그 숫자를 믿을 수 있게 만드는 것**이 어려웠다. 운영을 건드리지 않고 운영과 같게 재는 환경을 설계했다.

---

## 문제 상황

성능을 개선하려면 먼저 재야 했는데, 처음 돌린 측정은 쓸 수가 없었다.

- **p95 가 56초**로 나왔다. 이게 서버가 느린 건지, 부하 생성기가 밀린 건지, 큐에서 기다린 건지 구분되지 않았다.
- 개선 전후를 비교해야 하는데 **두 측정이 비교 가능한지 판단할 근거**가 없었다.
- 운영 서버 한 대뿐이라 **측정이 운영을 망가뜨릴 위험**이 있었다.

"어디가 병목인가"를 묻기 전에 **"이 숫자를 믿어도 되는가"** 부터 해결해야 했다.

## 내가 접근한 방법

측정을 하나의 실험으로 보고, 실험이 갖춰야 할 조건을 먼저 정의했다.

1. **독립변수가 하나여야 한다** — 인덱스 말고는 아무것도 달라지지 않아야 한다
2. **측정값이 서버의 일한 시간이어야 한다** — 대기 시간이 섞이면 안 된다
3. **대조군이 있어야 한다** — 900ms 가 비정상인지 판단할 기준
4. **반복 가능해야 한다** — 같은 데이터, 같은 시나리오로 다시 잴 수 있어야 한다
5. **운영에 피해가 없어야 한다**

이 다섯을 각각 어떻게 만족시킬지를 설계 과제로 삼았다.

## 여러 가지 대안

**부하 모델**

| 대안 | 왜 택하지 않았나 |
| --- | --- |
| **고정 VU** (`constant-vus`) | 서버가 느려지면 **요청 발생도 같이 느려진다.** 부하가 저절로 줄어 포화점이 보이지 않는다. 실제 사용자는 서버가 느리다고 클릭을 멈추지 않는다 |
| 도착률 고정 (`arrival-rate`) | ← **선택.** 초당 도착 건수를 고정하고 동시 요청 수는 서버 상태에 따라 늘어나게 둔다 |

**측정 환경**

| 대안 | 왜 택하지 않았나 |
| --- | --- |
| **운영 DB 에 직접** | 가장 정확하지만 측정이 곧 장애가 된다 |
| **별도 EC2 를 띄워 복제** | 가장 안전하지만 **비용과 시간**이 든다. 인스턴스가 다르면 성능도 달라져 비교 의미가 줄어든다 |
| 같은 인스턴스·다른 DB | ← **선택.** 같은 하드웨어·같은 이미지라 운영에 가장 가깝고, 데이터만 격리된다 |

**시드 데이터**

| 대안 | 왜 택하지 않았나 |
| --- | --- |
| **전원에게 같은 양** | PostgreSQL 통계가 "회원당 N행"으로 잡혀 **플래너가 늘 같은 계획을 고른다.** 실제로 무너지는 자리가 드러나지 않는다 |
| **운영 데이터 복제** | 개인정보가 측정 환경으로 넘어간다 |
| 계층을 나눈 합성 데이터 | ← **선택.** 분포를 의도적으로 치우치게 만든다 |

**도구**

JMeter·Gatling 대신 **k6** 를 썼다. 시나리오를 JavaScript 로 쓰므로 토큰 재사용·회원 계층별 분기 같은 로직을 그대로 코드로 짤 수 있고, `arrival-rate` 와 `dropped_iterations` 를 1급 개념으로 제공한다.

## 왜 이 기술을 사용했는지

**`ramping-arrival-rate`** — 초당 도착 건수를 고정하면 동시 요청 수는 Little's Law 로 따라온다.

```
필요 VU = 도착률 × 응답시간
```

10 RPS 에서 응답이 900ms 면 VU 9개, 10초로 늘어지면 VU 100개가 필요하다. 그래서 **VU 증가 자체가 성능 저하의 신호**가 된다. 고정 VU 모델에서는 이 신호가 아예 생기지 않는다.

**`dropped_iterations`** — k6 가 목표 도착률을 채우지 못하고 버린 반복 수다. 이게 0 이 아니면 **그 측정의 응답시간은 큐 대기를 포함**한다. 조건 2(서버가 일한 시간)를 기계적으로 검증할 수 있는 지표라 이걸 합격 기준으로 삼았다.

**회원 계층 분리** — `id % 100` 으로 네 계층을 만들었다.

| 계층 | 비율 | 인원 | 알림 |
| --- | ---: | ---: | ---: |
| 가입만 함 | 50% | 5,000 | 0~2 |
| 가볍게 씀 | 30% | 3,000 | 5~20 |
| 꾸준히 씀 | 15% | 1,500 | 50~200 |
| **헤비** | 5% | 500 | **300~1,500** |

**개인화 조회는 헤비 회원으로 잰다.** 평균 회원으로 재면 알림 문제가 드러나지 않는다. 실제 서비스가 무너지는 자리는 평균이 아니라 꼬리다.

**`setseed(0.42)`** — 시드 SQL 이 매번 같은 데이터를 만든다. 조건 4(반복 가능성)가 여기서 나온다.

## 어떤 과정으로 해결했는지

1. **격리 환경을 구성했다.** 운영과 **같은 이미지**로 `backend-loadtest` 를 `:18080` 에 띄우고, 같은 PostgreSQL 인스턴스 안의 별도 DB(`trendin_test`)와 분리된 Redis 를 붙였다.
2. **사고를 코드로 막았다.** `seed/00_guard.sql` 이 대상 DB 이름이 `trendin_test` 가 아니면 즉시 중단한다. 운영에 시드를 쏟는 사고는 한 번이면 복구가 안 된다.
3. **노이즈를 껐다.** 측정 중 알림 배치 스케줄러가 깨면 수치가 흔들리므로 `TREND_NOTIFICATION_CRON: "-"` 로 비활성화했다.
4. **가짜 병목을 제거했다.** 인증 토큰을 `setup()` 에서 50개 발급해 나눠 쓴다. VU 마다 로그인하면 **bcrypt 가 가짜 병목**이 되어 정작 재려던 것이 묻힌다.
5. **데이터 분포를 실제에 맞췄다.** 콘텐츠와 국가 데이터를 상위 2,000개 키워드에 몰아 뒀다. 고르게 뿌리면 어느 트렌드를 눌러도 결과가 작아 아무것도 재지 못한다.
6. **기준선 측정을 따로 만들었다.** 포화시키는 램프 측정(`run.sh`)과 별개로, 램프 없이 **10 RPS 고정 1분**만 도는 `bench.sh` 를 뒀다. 개선 전후 비교는 이쪽으로만 한다.
7. **읽는 순서를 정했다.** 숫자를 보기 전에 **비교 가능성부터** 확인한다.

   | | baseline | indexed |
   | --- | --- | --- |
   | 시나리오 | `10.00 iterations/s for 1m0s` | 동일 |
   | 완료 반복 | 600–601 | 600–601 |
   | `dropped_iterations` | 없음 | 없음 |
   | 백엔드 이미지 | 운영이 돌리는 것 | 동일 |

   조건이 하나라도 다르면 나머지 숫자는 읽을 필요가 없다.

## 결과

**이 환경 덕에 알림 병목을 찾아냈고, 인덱스 개선을 123배로 정량화할 수 있었다.** 같은 조건에서 두 번 잰 값이라 "인덱스 때문"이라고 말할 수 있다.

부수적으로 얻은 것도 있다.

- **비교군을 둔 덕에 목표가 생겼다.** `saved-trends` 12.5ms 가 "인덱스 있는 개인화 조회의 정상 수준"이었고, 거기서 "30ms 아래"라는 목표가 나왔다.
- **잡음을 잡음으로 읽을 수 있게 됐다.** 인덱스와 무관한 `POST /auth/login` p95 가 114.22 → 96.98ms 로 **같이 좋아진 것**을 보고, 두 회차 사이 머신 상태가 달랐음을 알았다. 그래서 다른 엔드포인트의 ±15% 변화를 개선·악화로 해석하지 않았다. 이 판단이 없었으면 "`GET /trends` 가 37% 나빠졌다"는 잘못된 결론을 냈을 것이다.
- **스크립트 버그를 잡았다.** `bench.sh` 가 결과 표를 비워 내보내고 있었는데, `grep -m1` 이 `█ TOTAL RESULTS` 보다 먼저 나오는 `█ THRESHOLDS` 블록을 집고 있었다. 측정 도구 자체도 검증 대상이라는 걸 배웠다.

**한계도 기록해 뒀다.** k6 가 같은 EC2 에 있어 자원을 다투고, DB 가 운영과 같은 인스턴스라 측정이 운영에 영향을 준다. 다음에 장비를 늘릴 수 있다면 부하 생성기부터 분리할 것이다.
