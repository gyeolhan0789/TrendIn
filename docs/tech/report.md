## 1. 알림 조회 인덱스 — p95 900.55ms → 7.33ms

### 증상

부하테스트에서 알림 두 엔드포인트만 유독 느렸다. 같은 개인화 조회인데 비교군의 **72배**였다.

| 엔드포인트 | p95 |
| --- | ---: |
| `GET /members/me/notifications` | **900.55ms** |
| `GET /members/me/notifications/unread-count` | **608.11ms** |
| `GET /members/me/saved-trends` ← 비교군 | 12.50ms |

큐 대기가 없는 도착률(10 RPS 고정, `dropped_iterations` 0)에서 잰 값이므로 **저 900ms 는 전부 서버가 실제로 일한 시간**이다.

### 원인 — PostgreSQL 은 외래키에 인덱스를 만들지 않는다

`V1` 이 `notifications` 에 만든 인덱스는 PK(`id`)와 `dedup_key` 유니크 둘뿐이었다. 외래키 제약 `fk_notifications_member` 는 **조회에 쓰이지 않는다.** 그런데 `NotificationRepository` 의 질의는 전부 `member_id` 로 시작한다.

MySQL 은 외래키에 인덱스를 자동 생성하지만 PostgreSQL 은 하지 않는다. 이 차이를 모르면 "FK 가 있으니 인덱스도 있겠지"라고 넘어가게 된다.

### 해결 — 인덱스 두 개

```sql
-- 목록 조회: where member_id = ? order by created_at desc, id desc limit 20
CREATE INDEX idx_notifications_member_created
    ON notifications (member_id, created_at DESC, id DESC);

-- 안 읽은 개수: where member_id = ? and is_read = false
CREATE INDEX idx_notifications_member_unread
    ON notifications (member_id) WHERE is_read = false;
```

### 왜 `(member_id)` 단독으로는 부족한가

단독 인덱스로도 풀스캔은 면한다. 하지만 **그 회원의 행을 전부 꺼내 정렬한 뒤 20개만 남긴다.** 헤비 회원은 알림이 최대 1,500건이다.

정렬 순서까지 인덱스에 담으면 플래너가 **인덱스를 20행만 걷고 멈춘다.** 실행 계획에서 `Sort` 노드가 사라진다.

### `id DESC` 를 뒤에 둔 이유

`created_at` 이 같은 행의 순서를 고정하기 위해서다. tie-breaker 가 없으면 같은 시각의 알림이 **페이지를 넘길 때마다 순서가 달라져 행이 중복되거나 누락된다.** 정렬 키가 유일하지 않은 오프셋 페이지네이션의 고전적인 함정이다.

### 덤으로 `count(*)` 까지 받는다

`Page` 반환 타입은 `select count(*) ... where member_id = ?` 를 한 번 더 쏜다. 이 질의는 인덱스의 **선두 컬럼만** 쓰므로 같은 인덱스로 Index Only Scan 이 된다. 인덱스 하나가 목록과 카운트를 동시에 받는다.

### 인덱스 두 개를 둘 수 있었던 이유 — 읽기 중심 서비스

인덱스는 조회를 빠르게 하는 대신 **INSERT·UPDATE·DELETE 마다 인덱스도 갱신**해야 한다. 쓰기가 잦은 표라면 인덱스를 늘리는 것이 곧 쓰기 지연이 된다.

`notifications` 는 그 반대였다.

| 연산 | 빈도 |
| --- | --- |
| **INSERT** | **하루 한 번** — 알림 생성 배치(`0 0 0 * * *`)가 유일한 경로다 |
| **UPDATE** | 알림을 읽을 때. 사용자당 하루 몇 번 |
| **SELECT (목록)** | 알림 벨을 열 때마다 |
| **SELECT (안 읽은 개수)** | **헤더에 늘 붙어 있어 화면을 넘길 때마다** |

서비스 전체도 같다. 트렌드·키워드·지표·AI 해설은 **Spark 파이프라인이 배치로 적재**하고 백엔드는 읽기만 한다 — `KeywordMetricRepository`·`TrendAnalysisRepository`·`ContentRepository` 에는 `save` 호출이 아예 없다. 백엔드가 직접 쓰는 것은 회원·관심 키워드·저장 목록처럼 사용자 행동에 따른 소량뿐이다.

**쓰기 비용은 하루 한 번 배치에서만 발생하고, 그 대가로 하루 종일 일어나는 조회가 빨라진다.** 트레이드오프가 한쪽으로 크게 기울어 있어 인덱스를 적극적으로 쓰는 쪽이 맞았다. 쓰기가 잦은 표였다면 커서 페이지네이션이나 카운트 비정규화를 먼저 검토했을 것이다.

### 부분 인덱스의 함정 — 조건이 리터럴이어야 한다

안 읽은 개수는 헤더에 늘 붙어 있어 화면마다 호출된다. 알림의 70%가 읽은 상태이므로 **부분 인덱스**가 유리하다.

- `(member_id, is_read)` 보다 **3배 작다**
- 엔트리가 전부 "안 읽음"이라 `count` 가 인덱스만 읽고 끝난다
- 읽음 처리로 `is_read` 가 `true` 가 되면 그 엔트리는 **인덱스에서 빠져** 표가 더 줄어든다

> ⚠️ **부분 인덱스는 조건이 SQL 에 리터럴로 박혀야 쓰인다.**
>
> 플래너가 "질의의 조건이 인덱스의 조건을 함의함"을 **계획 시점에** 증명해야 한다. Hibernate 가 `is_read = ?` 로 바인드 파라미터를 내보내면 이 인덱스를 **못 쓴다.** Spring Data 의 `...ReadFalse` 파생 질의는 JPQL 에 불리언 리터럴을 넣으므로 `is_read = false` 로 나올 것이 기대되지만, 확인하지 않았다.

못 쓰더라도 성능이 되돌아가지는 않는다. 위의 `idx_notifications_member_created` 가 `member_id = ?` 를 받고 `is_read` 는 필터로 처리하므로, 68만 행 풀스캔이 그 회원의 1,500행 인덱스 스캔으로 줄어든다.

### 결과

같은 조건(10 RPS 고정, 2시간 30분 간격, 바뀐 것은 인덱스 둘뿐)에서 다시 쟀다.

| 지표 | before | after | 배수 |
| --- | ---: | ---: | ---: |
| 목록 avg | 424.46ms | **4.90ms** | 87× |
| 목록 med | 359.29ms | **4.53ms** | 79× |
| **목록 p95** | **900.55ms** | **7.33ms** | **123×** |
| 안 읽은 개수 avg | 229.60ms | **2.80ms** | 82× |
| 안 읽은 개수 med | 174.07ms | **2.60ms** | 67× |
| **안 읽은 개수 p95** | **608.11ms** | **4.39ms** | **139×** |

**알림 패널 한 번 여는 DB 비용이 654ms → 7.7ms 다.** 85배 줄었다.

avg·med·p95 가 **전부 같은 배수로** 움직인 것이 중요하다. 한쪽만 줄었다면 잡음을 의심해야 한다.

### ⚠️ 아직 확인하지 못한 것

**`EXPLAIN` 증거가 없다.** 벽시계 시간이 123배 줄었다는 것은 측정됐지만, 플래너가 실제로 그 인덱스를 골랐는지는 확인하지 못했다. 다음 명령 한 번이면 된다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM notifications WHERE member_id = <헤비회원> AND is_read = false;
-- "Index Only Scan using idx_notifications_member_unread" 가 보이면 의도대로다.
```

파라미터 바인딩으로 나오는 것이 확인되면 부분 인덱스를 `(member_id, is_read)` 로 바꾼다.

## 2. 부하테스트 방법론

숫자는 환경이 바뀌면 의미를 잃지만 **재는 방법**은 남는다.

### 동시 사용자 N명 모델을 쓰지 않았다

`ramping-arrival-rate` 로 **초당 도착 건수**를 고정하고, 동시 요청 수(k6 의 VU)는 서버가 느려지는 만큼 **저절로 늘어나게** 했다.

고정 VU 로 재면 서버가 느려질 때 **요청 발생도 같이 느려진다.** 부하가 저절로 줄어드니 포화점이 안 보인다. 실제 사용자는 서버가 느리다고 클릭을 멈추지 않는다.

필요한 VU 수는 Little's Law 로 따라온다.

```
필요 VU = 도착률 × 응답시간
```

10 RPS 에서 응답이 900ms 면 VU 9개, 10초로 늘어지면 VU 100개가 필요하다. 그래서 **VU 증가 자체가 성능 저하의 신호**다.

### 포화 신호는 `dropped_iterations`

k6 가 목표 도착률을 채우지 못하고 반복을 버린 수다. 이게 0 이 아니면 **그 측정의 응답시간은 큐 대기를 포함**한다.

### 무릎 아래에서 재야 서버의 일한 시간이다

개선 전 리포트에는 "p95 56.6초"라는 숫자도 있다. 3분 램프로 포화시킨 값이다. 이것과 개선 후의 "7.33ms"를 나란히 놓으면 **안 된다.**

비교는 **같은 조건**이어야 한다. 그래서 램프 없이 **10 RPS 고정 1분**(`bench.sh`)을 기준선으로 따로 뒀고, `900.55ms → 7.33ms` 가 그 비교다.

### 비교 가능성부터 확인한다

숫자를 읽기 전에 두 회차가 비교 가능한지부터 봤다. 조건이 하나라도 다르면 나머지를 읽을 필요가 없다.

| | baseline | indexed |
| --- | --- | --- |
| 시나리오 | `10.00 iterations/s for 1m0s` | **동일** |
| 완료 반복 | 600–601 | **600–601** |
| `dropped_iterations` | **없음** | **없음** |
| 백엔드 이미지 | 운영이 돌리는 것 | **동일** |
| 데이터 | 재시딩 안 함 | **동일** |

### 비교군을 둔다

알림이 900ms 라는 것만으로는 "원래 그런 건지" 알 수 없다. 인덱스가 있는 같은 성격의 개인화 조회(`saved-trends` 12.50ms)를 나란히 두니 **72배**라는 서술이 가능해졌다.

목표도 그 비교군에서 나왔다 — "30ms 아래".

### 시드 데이터는 균일하면 안 된다

**이게 이 측정에서 가장 중요한 설계다.** 전원에게 같은 양을 주면 PostgreSQL 통계가 "회원당 N행"으로 잡혀 **플래너가 늘 같은 계획을 고른다.** 실제 서비스에서 무너지는 자리가 드러나지 않는다.

`id % 100` 으로 네 계층으로 갈랐다.

| 계층 | 비율 | 인원 | 저장한 트렌드 | 관심 키워드 | 알림 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 가입만 함 | 50% | 5,000 | 0 | 0~1 | 0~2 |
| 가볍게 씀 | 30% | 3,000 | 1~5 | 2~5 | 5~20 |
| 꾸준히 씀 | 15% | 1,500 | 6~30 | 5~15 | 50~200 |
| **헤비** | 5% | 500 | **100~500** | 20~50 | **300~1,500** |

**개인화 조회는 헤비 회원으로 잰다.** 평균 회원으로 재면 알림·저장목록의 문제가 드러나지 않는다. 상세·이력·지역은 비교군이라 평균 회원을 쓴다.

전체 규모는 회원 1만 명, `keyword_metric_history` 450만 행, `keyword_country_daily_metrics` 240만 행이다. `setseed(0.42)` 로 **매번 같은 데이터**가 만들어져 회차 간 비교가 성립한다.

**콘텐츠와 국가 데이터는 상위 2,000개 키워드에 몰아 뒀다.** 고르게 뿌리면 어느 트렌드를 눌러도 결과가 작아 아무것도 재지 못한다.

### 운영을 건드리지 않고 운영과 같게 잰다

| | |
| --- | --- |
| 대상 | `backend-loadtest` — 운영과 **같은 이미지**, DB 만 다르다 |
| DB | `trendin_test` — 같은 PostgreSQL 인스턴스 안의 **별도 데이터베이스** |
| Redis | 운영과 분리된 `redis-loadtest` |
| 알림 배치 | **껐다**(`TREND_NOTIFICATION_CRON: "-"`) — 측정 중 스케줄러가 깨면 수치가 흔들린다 |

`seed/00_guard.sql` 이 대상 DB 이름이 `trendin_test` 가 아니면 즉시 중단한다. 운영에 시드를 쏟을 사고를 코드로 막았다.

### 가짜 병목을 만들지 않는다

인증 토큰은 `setup()` 에서 50개 발급해 나눠 쓴다. VU 마다 로그인하면 **bcrypt 가 가짜 병목**이 되어 정작 재려던 것이 묻힌다.

### ⚠️ 이 측정의 한계

- **k6 가 같은 EC2 에 있다.** 대상이 localhost 에만 열려 있어 어쩔 수 없었지만 자원을 다툰다.
- **두 회차 사이 머신 상태가 달랐다.** 인덱스와 무관한 `POST /auth/login` p95 가 114.22 → 96.98ms 로 **같이 좋아진 것**이 그 증거다. 그래서 다른 엔드포인트의 ±15% 변화는 잡음으로 읽어야 한다.
- **DB 가 운영과 같은 인스턴스**다. 측정이 운영 성능에 영향을 준다.

## 3. 리프레시 토큰 — Redis + Lua

### 설계

| 항목 | 선택 | 이유 |
| --- | --- | --- |
| 저장소 | Redis | TTL 이 자료구조에 내장돼 만료 청소가 따로 필요 없다 |
| 키 | **회원당 하나** `refresh:member:{id}` | 새로 로그인하면 덮어써서 마지막 토큰만 유효 |
| 값 | 원문이 아닌 **SHA-256 해시** | Redis 덤프가 유출돼도 토큰을 그대로 쓸 수 없다 |
| 액세스 토큰 | JWT, 서버에 저장하지 않음 | 조회마다 Redis 를 치지 않는다 |

### 문제 — read-then-write 레이스

재발급과 로그아웃은 모두 "저장된 토큰이 제시된 것과 같은지 확인한 뒤 쓴다"는 구조다. 이걸 두 번의 왕복으로 하면 사이에 다른 요청이 끼어든다.

```
로그아웃:  GET → (일치) ─────────────→ DEL
재발급:              GET → (일치) → SET   ← 로그아웃이 지운 키를 되살린다
```

로그아웃했는데 세션이 살아 있는 상태가 된다.

### 해결 — Lua 스크립트로 원자화

Redis 는 스크립트를 **직렬로** 실행한다. 검증과 쓰기를 한 스크립트에 넣으면 그 전체가 원자 단위가 된다.

```lua
-- 회전: 저장된 해시가 제시된 토큰의 것과 같을 때만 새 토큰으로 교체
if redis.call('GET', KEYS[1]) == ARGV[1] then
    redis.call('SET', KEYS[1], ARGV[2], 'PX', ARGV[3])
    return 1
end
return 0
```

```lua
-- 로그아웃: 저장된 해시가 제시된 토큰의 것과 같을 때만 삭제
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

```java
public boolean rotate(Long memberId, String oldRefreshToken, String newRefreshToken, Duration ttl) {
    return SUCCESS.equals(redisTemplate.execute(
            ROTATE, List.of(key(memberId)),
            hash(oldRefreshToken), hash(newRefreshToken), String.valueOf(ttl.toMillis())));
}
```

**같은 토큰으로 동시에 들어온 요청은 하나만 성공한다.** 두 번째 요청은 저장된 해시가 이미 바뀌어 있어 `0` 을 받는다. 토큰 재사용 탐지의 토대가 된다.

반환값이 `boolean` 이라 호출부가 "실패했다"를 바로 알 수 있다 — 예외를 던지지 않으므로 정상 흐름으로 다룬다.

### 탈퇴는 다르게 지운다

재발급·로그아웃은 `deleteIfMatches`(제시한 토큰이 현재 것일 때만)지만, **탈퇴는 무조건 삭제**한다. 어느 기기에서 탈퇴했든 모든 기기의 세션을 끊어야 하기 때문이다.

그리고 그 삭제를 **트랜잭션 안**에 둔다. Redis 는 롤백되지 않지만, 그 방향의 실패는 "세션만 지워졌다"라 다시 로그인하면 그만이다. 반대로 두면 **회원이 사라졌는데 토큰이 살아 있는 창**이 생긴다.

### ⚠️ 액세스 토큰은 즉시 폐기되지 않는다

서명과 만료만 보는 JWT 라, 로그아웃·탈퇴 후에도 **남은 유효 기간(최대 15분) 동안 필터를 통과한다.** 탈퇴한 회원의 요청은 회원을 찾지 못해 `404` 로 끝난다.

프런트가 세션을 지우므로 그 기기는 괜찮지만, **다른 탭이 열려 있었다면 그 탭은 404 를 받는다.** 완전히 막으려면 블랙리스트가 필요하고, 그러면 조회마다 Redis 를 치게 된다. 트레이드오프를 알고 선택했다.
