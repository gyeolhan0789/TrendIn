# 07 — 지표와 순위

`aggregate` Job 의 본체. 언급량을 세고, 기간별로 묶고, 순위와 성장률을 내고, 트렌드 유형을 판정한다. 목록 화면(`CURRENT`/`NEW`/`RISING` × `24H`/`7D`/`30D`)과 상세 화면의 언급량 그래프가 전부 이 문서의 산출물이다.

정의가 애매하면 나중에 "이 숫자가 왜 이래?"에 답할 수 없으므로 각 값을 한 문장으로 못박는다.

## 1. 언급량

> **언급량 = 그 키워드가 등장한 문서 수.** 출현 횟수가 아니다.

같은 문서에서 `Kubernetes` 가 20번 나와도 1이다.

**출현 횟수를 쓰지 않는 이유** — 긴 글이 통계를 지배한다. 튜토리얼 한 편이 짧은 게시글 50개보다 큰 영향을 갖게 되는데, "얼마나 많은 사람이 이야기하는가"를 재려는 목적에 어긋난다.

출현 횟수는 내부 통계 테이블에 **함께 저장한다.** 서비스에는 안 나가지만 이상 탐지(한 문서에서 500번 반복 = 스팸)에 쓴다.

## 2. 일별 언급량을 어디에 두나

**현행 스키마에 키워드별 일별 지표 테이블이 없다.** 그래서 두 층으로 나눈다.

| 층 | 어디 | 무엇 |
| --- | --- | --- |
| 원자료 | 내부 `pl_keyword_daily_stat` | 키워드 × 날짜 × 도메인. 문서 수·출현 수·소스 수·저자 수 |
| 서비스 | `trend_metrics` (`period = '24H'`) | 트렌드가 된 키워드의 일별 언급량 |

### `trend_metrics` 가 곧 시계열이다

`trend_metrics` 는 PK 가 `id` 이고 `trend_id` 는 단순 FK 다. **한 트렌드·한 기간에 여러 행이 쌓인다.** 기간별 최신 1행만 두는 구조가 아니다.

그래서 `period = '24H'`, `period_start = period_end = 그날` 행을 매일 남기면 **그 누적이 곧 일별 언급량 시계열**이 된다. 상세 화면의 그래프는 이 행들을 날짜순으로 읽으면 된다.

```
trend_metrics
  (trend_id=42, period='24H', period_start=2026-09-01, mention_count=120)
  (trend_id=42, period='24H', period_start=2026-09-02, mention_count=138)
  (trend_id=42, period='24H', period_start=2026-09-03, mention_count=201)   ← 시계열
  (trend_id=42, period='7D',  period_start=2026-08-28, mention_count=890)   ← 기간 지표
  (trend_id=42, period='30D', period_start=2026-08-05, mention_count=3120)
```

`7D`·`30D` 행도 같은 테이블에 쌓이므로 `period` 로 걸러 읽는다.

### ⚠️ 트렌드가 아닌 키워드는 지표가 없다

`trend_metrics` 는 `trends` 를 거쳐야 한다. **`trends` 행이 없는 키워드는 서비스에서 볼 수 있는 지표가 하나도 없다.**

사용자가 관심 키워드로 등록했는데 그 키워드가 트렌드로 뜬 적이 없으면 언급량 그래프가 빈칸이다. 내부에는 `pl_keyword_daily_stat` 에 값이 있는데 내보낼 자리가 없다.

우회할 수 없다. [00 §7](00-overview.md) 한계 4번이고 기획 확인이 필요하다. 선택지는 두 가지다.

| 선택지 | 대가 |
| --- | --- |
| 관심 키워드로 등록된 키워드는 트렌드가 아니어도 `trends` 행을 만든다 | `trends` 가 "트렌드"가 아니게 된다. 목록 조회에서 걸러내야 한다 |
| 그대로 둔다 | 관심 키워드 상세가 비는 경우가 생긴다 |

### 언급량 0인 날 — 행의 존재로 구분한다

**제안: `24H` 행을 언급량이 0이어도 넣되, 수집이 실패한 날은 행을 만들지 않는다.**

| 그날 상황 | `24H` 행 | 프론트가 보는 것 |
| --- | --- | --- |
| 수집 정상, 언급 있음 | `mention_count = N` | 값 |
| 수집 정상, 언급 없음 | `mention_count = 0` | **0** |
| 수집 실패 | **행 없음** | **그래프의 구멍 = 데이터 없음** |

이러면 [00 §7](00-overview.md) 한계 1번(0 과 null 을 구분할 수 없다)이 **부분적으로 해소된다.** 별도 테이블 없이 행의 유무가 그 구분을 담는다.

수집 상태는 `ingest` 가 `pl_batch_stat` 에 남긴 값을 읽는다 ([02 §4](02-input-contract.md)).

**⚠️ "수집 실패한 날" 을 판정하기가 어려워졌다.** 수집이 시간 주기라 한 소스가 하루 24~48 번 시도하고, 상태는 `(일자, 소스)` 별로 `COMPLETED`/`PARTIAL`/`MISSING` 이 나온다 ([02 §4](02-input-contract.md)). 여기서 "행을 만들지 않는다" 를 걸 조건이 명확하지 않다.

| 조건 | 결과 |
| --- | --- |
| 모든 소스가 `MISSING` | 행 없음. 이건 확실하다 — 그날 데이터가 없다 |
| 일부 소스만 `MISSING` | **애매하다.** 나머지 소스 데이터는 정상인데 값이 낮게 나온다 |
| 모든 소스가 `PARTIAL` | **애매하다.** 24 회 중 1 회씩 실패한 것과 20 회씩 실패한 것이 같은 상태값이다 |

**제안 — `MISSING` 이 전부일 때만 행을 빼고, 나머지는 값을 넣는다.** 그리고 `pl_batch_stat` 에 실패한 실행 수를 남겨(그것도 [02 §4](02-input-contract.md)) 운영 조회로 "그날 왜 낮았나" 에 답할 수 있게 한다. 서비스로는 나가지 않는다.

이유는 하향 편향이 안전한 방향이기 때문이다. 값을 넣으면 실제보다 적게 보이고, 행을 빼면 데이터가 아예 없는 것처럼 보인다. 소스 7 곳 중 1 곳이 죽은 날을 "데이터 없음" 으로 그리는 것이 더 큰 왜곡이다.

**시간 주기가 이 문제를 완화하기도 한다.** 하루가 통째로 비려면 브로커나 MinIO 가 죽어야 한다. 소스 한 곳의 일시적 장애는 다음 시각 실행이 메운다 — 다만 그 기사는 **발행일 기준**으로 집계되므로([§3](#3-period_start--발행-기준)) 소급 재계산 구간 안이면 값이 나중에 정정된다.

**한계** — `PARTIAL`(소스 일부만 성공)인 날은 여전히 구분되지 않는다. 값을 그대로 넣으므로 실제보다 적게 나온다. 하향 편향이라 방향은 안전하지만, 그날이 하락으로 보인다.

**이건 프론트와 합의가 필요하다.** "행이 없는 날은 구멍으로 그린다"를 프론트가 구현해야 의미가 있다. 0 으로 그리면 아무것도 달라지지 않는다.

행 수는 트렌드 수 × 날짜 수다. 트렌드가 수천 개면 연 수백만 행인데, 이 규모는 감당된다.

## 3. `period_start` — 발행 기준

> **집계 날짜는 `published_at` 을 KST 로 변환한 date 다.** 수집 시각이 아니다.

상위 문서 §5 가 못박은 규약이다: *"키워드가 언제 화제였는지는 문서별 `published_at` 으로 집계하며, `collected_at` 은 파이프라인 운영 정보로만 쓴다."*

`published_at` 이 없는 문서는 [03 §3](03-normalization-spec.md) 의 대체 규칙으로 `collected_at` 기준 날짜를 쓴다.

### 소급 재계산 — 이게 `aggregate` 를 분리한 이유다

오늘 수집한 문서의 발행일이 어제일 수 있다. 그러면 **어제의 언급량이 오늘 바뀐다.** 오늘치만 계산하고 끝내면 어제 숫자가 영원히 틀린 채 남는다.

**매 실행마다 최근 W일을 통째로 다시 계산한다.**

| 항목 | |
| --- | --- |
| W 의 근거 | 소스가 주는 문서의 발행일 분포. 대부분 D~D-1 에 몰리지만 꼬리가 있다 |
| W 를 정하는 법 | `collected_date − published_date` 분포를 실제로 재서 정한다. **추측하지 않는다** |
| W 를 크게 잡는 비용 | 매 실행의 계산량. 규모가 작아 여유가 있다 |
| W 를 작게 잡는 비용 | 오래된 문서의 언급이 영영 반영되지 않는다 |

의심스러우면 **크게 잡는다.** [00 §3](00-overview.md) 의 규모에서 30일 재계산은 부담이 아니다.

**⚠️ 과거분 백필이 이 분포를 한 번 크게 흔든다.** 두산 4곳과 `marieclaire` 는 소스당 **한 번** 피드 30페이지를 훑는데, vogue 기준 약 6주 전까지 간다 (`web-collect.md` #9). 즉 그 실행에서 `collected_date − published_date` 가 최대 42일짜리 문서가 한꺼번에 들어온다.

| | 처리 |
| --- | --- |
| W 를 42일 이상으로 잡는다 | 백필분이 반영되지만, 그 뒤 상시 구간에서 매일 6주를 재계산한다 |
| W 는 상시 분포로 잡고, **백필 직후 한 번 수동으로 범위를 넓혀 돌린다** | 권장 |

**후자로 간다.** 백필은 소스당 한 번뿐이라 상시 W 를 그것에 맞추면 매일 값을 하지 않는 계산을 한다. 임계값을 바꾼 날에 범위를 넓혀 한 번 돌리는 것과 같은 패턴이다(아래 문단).

**W 를 실측할 때 백필 구간을 섞지 않는다.** 섞으면 꼬리가 6주까지 늘어난 분포가 나오고, 그건 상시 분포가 아니다. 백필 실행분(`ingest_run_id` 로 구분)을 빼고 잰다.

**같은 이유로 [04 §10](04-keyword-extraction-spec.md) 의 임계값 변경과 [05 §8](05-keyword-registry-spec.md) 의 병합도 이 구간 재계산으로 반영된다.** W 일보다 오래된 구간에는 계단이 남는데, 이건 감수한다. 전 구간 재계산은 매일 하기엔 무겁고, 임계값을 바꾼 날에 수동으로 범위를 넓혀 한 번 돌리는 편이 낫다.

## 4. `trends` — 어떤 키워드가 트렌드가 되나

`trends` 는 키워드당 최대 하나다 (`keyword_id` 에 UK). **모든 키워드가 트렌드가 되지는 않는다.**

### 생성 조건

> 어느 기간에서든 그 도메인의 랭킹 상위 N 에 들면 `trends` 행을 만든다.

| 컬럼 | 값 |
| --- | --- |
| `keyword_id` | 대상 키워드 |
| `first_detected_at` | **최초로 트렌드가 된 시각.** 한 번 정하면 갱신하지 않는다 |
| `description` · `summary` · `reason` | **`NULL`** — [00 §4](00-overview.md) |
| `updated_at` | 매 갱신 시각 |

`first_detected_at` 은 `keywords.first_seen_at` 과 다르다. 전자는 "트렌드로 올라온 때", 후자는 "처음 관측된 때"다. 둘을 혼동하면 `NEW` 판정이 어긋난다 ([§5](#5-트렌드-유형과-순위)).

### 트렌드에서 내려오면

**`trends` 행을 지우지 않는다.** 지우면 `trend_metrics` 이력이 함께 사라지고([05 §1](05-keyword-registry-spec.md) 과 같은 FK 문제), 상세 화면의 과거 그래프가 통째로 없어진다.

대신 **그 회차의 `trend_metrics` 행을 만들지 않는다.** 최신 측정이 없으면 목록에 안 나온다. 상세는 과거 이력으로 여전히 볼 수 있다.

이 규칙 때문에 `trends` 는 단조 증가한다. 한 번 트렌드였던 키워드가 계속 쌓인다. 규모상 문제되지 않고, 오히려 "예전에 뜨던 트렌드"를 보여줄 여지가 생긴다.

## 5. `trend_metrics` — 기간 지표

### `period` 값 규약

`period` 가 varchar 라 DB 가 값을 막지 않는다. **`24H` / `7D` / `30D` 를 제안하며 확정이 필요하다** ([00 §7](00-overview.md) 10번).

| period | 현재 구간 | 직전 구간 |
| --- | --- | --- |
| `24H` | 기준일 하루 | 그 전날 하루 |
| `7D` | 기준일 포함 7일 | 그 앞 7일 |
| `30D` | 기준일 포함 30일 | 그 앞 30일 |

`period_start`·`period_end` 가 현재 구간의 경계다. **구간은 닫힌 구간이고 겹치지 않는다.**

`24H` 를 "지금부터 24시간 전"이 아니라 **날짜 단위**로 자르는 이유는 원자료가 일 단위 집계이기 때문이다. 시각 단위로 자르려면 원문을 다시 읽어야 하는데 그럴 값어치가 없다.

### `mention_count` 와 `previous_mention_count`

각 구간의 일별 값을 더한다. 데이터가 없으면 0 이다.

`previous_mention_count` 는 **직전 구간을 다시 계산해서** 얻는다. 직전 측정 행에서 읽어오지 않는다 — 그 행의 값이 소급 재계산([§3](#3-period_start--발행-기준))으로 바뀌었을 수 있기 때문이다. 원자료에서 계산하면 항상 최신이다.

### `growth_amount`

```
growth_amount = mention_count − previous_mention_count
```

**⚠️ 이 컬럼이 생성 컬럼(`GENERATED ALWAYS AS ... STORED`)인지 확인해야 한다.** 생성 컬럼이면 INSERT 에 넣는 순간 PostgreSQL 이 오류를 낸다. 확인 전까지는 계산해서 넣는 것을 기본으로 하고, 오류가 나면 빼면 된다. [00 §7](00-overview.md) 12번(`growth_amount` 생성 컬럼 여부).

### `growth_rate`

```
growth_rate = (mention_count − previous_mention_count) / previous_mention_count × 100
```

**직전 언급량이 0이면 `NULL` 이다.** 무한대나 큰 수로 채우지 않는다. 소수 첫째 자리로 반올림한다.

`NULL` 은 "성장률 0" 이 아니라 **"계산 불가(전에 없었음)"** 라는 점을 API 문서에 남겨달라고 백엔드에 전달해야 한다. 프론트가 `NULL` 을 0으로 그리면 새로 뜬 키워드가 전부 "성장 없음"으로 보인다.

### `trend_type`

varchar 라 값 규약이 필요하다. **`CURRENT` / `NEW` / `RISING` 을 제안한다.**

한 트렌드는 한 측정에서 정확히 하나의 유형을 갖는다. 배타적으로 판정한다.

| 순위 | 유형 | 조건 |
| --- | --- | --- |
| 1 | `NEW` | `keywords.first_seen_at` 이 현재 구간 안 **그리고** 아래 최소 조건 전부 |
| 2 | `RISING` | `growth_rate` 가 임계 이상 **그리고** `mention_count` 하한 이상 |
| 3 | `CURRENT` | 나머지 중 `mention_count` 상위 |

같은 키워드가 `7D` 에서는 `RISING`, `30D` 에서는 `CURRENT` 일 수 있다. 그래서 `trend_type` 이 `trends` 가 아니라 `trend_metrics` 에 있는 것이다.

#### `NEW` 의 최소 조건 — 여기가 가장 빡빡해야 한다

자동 발견 방식([04](04-keyword-extraction-spec.md))에서 "새로 뜨는 트렌드" 목록은 **노이즈가 가장 먼저 도착하는 곳**이다. 오타·봇·일회성 문자열이 정의상 전부 "처음 보는 것"이기 때문이다.

방어는 두 겹이다.

1. **[05 §5](05-keyword-registry-spec.md) 의 승격 관문.** 승격되지 않은 후보는 `keywords` 에 없으므로 여기 올 수 없다. 이게 1차 방어선이고 대부분을 거른다.
2. **여기서 한 번 더.** 승격됐다고 전부 `NEW` 로 내보내지 않는다.

| 추가 조건 | 막는 것 |
| --- | --- |
| 서로 다른 소스 ≥ 2 | 한 커뮤니티의 밈 |
| 서로 다른 저자 ≥ 하한 | 자기홍보 |
| `mention_count` ≥ 하한 | 표본 부족 |
| `dup_of` 제외 기준 | 크로스포스트 |

**`previous_rank IS NULL` 을 `NEW` 의 근거로 쓰지 않는다.** 순위권 밖에 있다가 올라온 오래된 키워드도 `previous_rank` 가 없다. `NEW` 의 근거는 `keywords.first_seen_at` 이다.

#### `RISING` 에 언급량 하한이 반드시 필요한 이유

성장률만 보면 1건 → 3건이 200% 다. 하한이 없으면 급상승 목록이 전부 극소 표본으로 채워진다. 성장률 상위 정렬에서 이건 예외가 아니라 기본값이다.

### `rank`

> `(domain, trend_type, period)` 안에서 `mention_count` 내림차순.

**⚠️ `trend_metrics` 에도 `trends` 에도 `domain` 이 없다.** `keywords.domain` 을 조인해서 얻어야 한다. 계산할 때는 문제없지만, 백엔드가 도메인별 목록을 조회할 때 매번 `trend_metrics → trends → keywords` 3단 조인을 타게 된다. 성능이 문제되면 비정규화를 요청한다.

#### 동점 처리 — 제안

`rank` 는 저장 컬럼이므로 배치가 값을 넣기 전에 규칙이 필요하다. **공동 순위를 두지 않고 아래 순서로 유일한 순위를 매긴다.**

```
1. mention_count       DESC
2. growth_rate         DESC NULLS LAST
3. keyword_id          ASC
```

| 결정 | 이유 |
| --- | --- |
| 공동 순위 없음 | `rank` 가 페이징 기준이다. 공동 순위가 있으면 한 페이지에 같은 등수가 여럿 나오고 총 페이지 수 계산이 틀어진다 |
| 2차 키가 `growth_rate` | 언급량이 같으면 더 빠르게 크는 쪽이 위인 게 사용자 기대에 맞다 |
| 3차 키가 `keyword_id` | **결정적**이어야 한다. 같은 데이터로 두 번 계산하면 같은 순위가 나와야 `previous_rank` 비교가 의미를 갖는다 |

3차 키가 없으면 Spark 의 정렬이 실행마다 달라져, 데이터가 하나도 안 변해도 순위가 흔들리고 그게 화면에 "순위 변동"으로 나타난다.

### `previous_rank`

직전 구간을 같은 규칙으로 계산해서 얻는다. 그 키워드가 직전 구간 순위권에 없었으면 `NULL`.

`previous_mention_count` 와 마찬가지로 **직전 측정 행에서 읽어오지 않는다.** 소급 재계산으로 값이 바뀌었을 수 있다.

이 방식의 값어치는 **같은 날 여러 번 돌려도 결과가 같다**는 것이다. 이전 값을 행에서 이월하는 구조였다면 재실행이 곧 오염인데, 원자료에서 매번 계산하면 그 문제가 아예 없다.

### `measured_at`

계산을 수행한 시각. `period_start` 와 다르다 — 9월 3일치를 9월 10일에 재계산하면 `period_start` 는 9월 3일, `measured_at` 은 9월 10일이다.

## 6. 멱등성

`trend_metrics` 는 이력 테이블이라 **그냥 INSERT 하면 재실행마다 중복이 쌓인다.**

### 유니크 제약이 있으면

```sql
INSERT INTO trend_metrics (...) SELECT ... FROM pl_stage_trend_metrics
ON CONFLICT (trend_id, period, period_start) DO UPDATE SET
  period_end = EXCLUDED.period_end,
  trend_type = EXCLUDED.trend_type,
  rank = EXCLUDED.rank,
  ...
  measured_at = EXCLUDED.measured_at;
```

### 없으면 — 범위 삭제 후 삽입

```sql
BEGIN;
DELETE FROM trend_metrics
 WHERE period = :period AND period_start BETWEEN :from AND :to;
INSERT INTO trend_metrics (...) SELECT ... FROM pl_stage_trend_metrics;
COMMIT;
```

**유니크 제약을 받는 쪽을 권한다** ([00 §7](00-overview.md) 9번 — 티어 1). 범위 삭제는 동작하지만, 제약이 없으면 다른 경로(수동 스크립트, 재처리 실수)로 들어온 중복을 DB 가 막아주지 못한다.

어느 쪽이든 **삭제 범위는 소급 재계산 구간 W 와 같다.** 그래야 병합·임계값 변경으로 사라져야 할 행이 실제로 사라진다.

## 7. 스팸과 이상치 억제

자동 발견 방식에서 이건 선택이 아니다.

| 신호 | 처리 | 어디서 |
| --- | --- | --- |
| 근사 중복 문서 | 집계에서 제외 | [03 §6](03-normalization-spec.md) 에서 `dup_of` 표시, 여기서 제외 |
| 한 저자가 하루에 문서 다수 | **저자당 일별 기여 상한** | 여기 |
| 한 문서에서 같은 키워드 반복 | 언급량 정의상 자동 해소 | [§1](#1-언급량) |
| 단일 소스 집중 | `NEW`·`RISING` 판정에서 제외 | [§5](#5-trend_metrics--기간-지표) |

### 저자당 기여 상한

> 한 저자가 하루에 같은 키워드에 기여하는 언급량을 상한 C 로 자른다.

한 사람이 하루에 자기 프로젝트 이름을 100개 글에 쓰면 언급량 100이 아니라 C 다.

**문서를 지우지 않고 기여도만 자르는 이유** — [03 §6](03-normalization-spec.md) 에서 정한 대로다. 문서는 `contents` 에 남아 "관련 콘텐츠"에 나오고, 통계에만 상한이 걸린다. 활발한 정상 사용자를 침묵시키지 않으면서 봇을 누른다.

`author` 가 `null` 인 문서(익명 소스)는 상한을 적용할 수 없다. 이건 한계이고, 해당 소스가 통계를 흔들면 소스 단위 가중치로 대응한다.

### 소스 가중치

**초기에는 모든 소스 가중치를 1.0 으로 둔다.**

가중치를 다르게 주는 순간 "이 숫자가 왜 이래?"에 답하기 어려워지고, 어떤 값이 맞는지 정할 근거도 없다. 설정으로 열어만 두고 실제 문제가 관측될 때 건드린다.
