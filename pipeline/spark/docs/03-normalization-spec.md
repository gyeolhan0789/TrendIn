# 03 — 정제 규격

`ingest` Job 의 후반부. `article.json` 을 표준 문서로 접고, 텍스트를 씻고, 중복과 쓰레기를 걸러낸다. [04](04-keyword-extraction-spec.md) 의 품질은 여기서 얼마나 잘 씻었는지에 크게 좌우된다.

**입력이 이미 공통 스키마다.** 생산자가 소스별 차이를 `article.json` 에서 이미 흡수했다 (`web-collect.md` #5.3). 배치 계약 시절 이 문서는 "소스마다 다른 객체를 하나의 표준 문서로 접는" 일을 전제했는데, 그 일의 절반이 생산자 쪽으로 갔다. 남은 것은 텍스트 정제와 중복 제거다.

## 1. 표준 문서 스키마

MinIO `curated` 에 Parquet 으로 쓰는 형태다. 서비스 `contents` 와는 다르다 — `contents` 에는 본문이 없고 `body_object_key` 가 이 파일을 가리킨다.

| 컬럼 | 타입 | 설명 | `article.json` 출처 |
| --- | --- | --- | --- |
| `url_hash` | binary(32) | `sha256(normalized_url)`. **파이프라인 내부에서의 문서 정체성** | `url` 을 정규화해 계산 |
| `source_id` | string | `vogue` · `gqkorea` · `wkorea` · `allure` · `marieclaire` · `harpersbazaar` · `cosmopolitan` · `hn` | `source` |
| `source_document_id` | string | 소스 내부 식별자 | `article_id` |
| `domain` | string | 이벤트의 `domain` 슬러그 (`fashion` / `dev`) | `domain` |
| `route` | string | `rss` / `listing` / `api`. 소스 내 경로 구분 | `route` |
| `url` | string | 정규화된 URL | `url` 정규화 결과 |
| `url_raw` | string | 정규화 전 원본 URL | `url` |
| `title` | string | 정제된 제목. **필수 필드라 `null` 이 아니다** | `title` |
| `body` | string | 정제된 본문. **없을 수 있다** ([§2](#2-본문이-없는-문서)) | `body_text` |
| `body_code` | string | 본문에서 분리한 코드 블록 | `body_text` 에서 분리 |
| `summary` | string | 소스가 준 요약. 본문이 없을 때의 유일한 텍스트 | `summary` |
| `lang` | string | `ko` / `en` / `mixed` / `unknown` | 판별 결과 |
| `author` | string | 저자 식별자. 스팸 억제용 | `author` |
| `categories` | array&lt;string&gt; | 소스가 준 섹션. 목록 소스는 발견한 섹션이 들어온다. `ARTICLE_SCHEMA` 가 `ArrayType(StringType())` 으로 받는다 — 171 에서 더했다 ([02 §3](02-input-contract.md)) | `categories` |
| `members_only` | boolean | 회원 전용이라 본문이 없음 | `members_only` |
| `published_at` | timestamp | 소스가 준 시각. **원본 보존** | `published_at` |
| `published_date` | date | `published_at` 의 KST date. 파티션 키 | 계산 |
| `ingest_run_id` | string | 이 문서를 쓴 `ingest` 실행 ([01 §3](01-architecture.md)) | 없음. Spark 가 만든다 |
| `collected_at` | timestamp | 수집 기준 시각. `contents.collected_at` 이 된다 | `collected_at` |
| `content_len` | int | 정제 후 본문 길이. 필터·가중치용 | 계산 |
| `dup_of` | binary(32) | 근사 중복이면 대표 문서의 `url_hash`. 아니면 `null` | 계산 |

`body_code` 를 따로 두는 이유는 [§4](#4-텍스트-정제) 에 있다.

**`ingest_run_id` 는 생산자의 `run_id` 가 아니다.** 기사 이벤트의 `run_id` 는 그 기사를 **발급한** 수집 실행이고(`web-collect.md` #6), 재처리 단위는 이 Job 의 실행이라 여기에는 이 Job 의 실행 식별자를 넣는다. 근거와 대가는 [01 §3](01-architecture.md).

**`route` 를 남기는 이유** — 같은 소스가 경로에 따라 본문 위치가 다르다. `harpersbazaar` 는 `listing` 이라 기사 페이지 HTML 을 파싱한 결과이고, 두산 4곳은 `rss` 라 피드 `content:encoded` 전문이다. 정제 품질이 갈리면 이 컬럼으로 구분해 재본다.

## 2. 본문이 없는 문서

**본문 없는 문서가 정상적으로 들어온다.** 배치 계약 시절 이 문서는 모든 문서에 본문이 있다고 전제했다.

| 경우 | 규모 | 있는 것 |
| --- | --- | --- |
| `members_only == true` | fashion 의 **7.4%** | 제목 · URL · 발행일 · 요약 |
| `hn` (route `api`) | **dev 전량** | 제목 · URL · 발행일 · 점수 · 댓글수 |

`article.json` 에서 `body_text` 키가 아예 없다 — `exclude_none=True` 직렬화이기 때문이다 ([02 §3](02-input-contract.md)).

**이 문서들을 버리지 않는다.** 제목만으로도 키워드가 나오고, 무엇보다 dev 도메인은 이것 말고 입력이 없다. 대신 [§6](#6-필터) 의 "본문 길이 하한" 필터가 이 문서들을 전부 걸러내므로, **필터를 본문 유무로 분기해야 한다.**

| 입력 | 필터 |
| --- | --- |
| `body` 있음 | 기존 규칙대로 |
| `body` 없고 `summary` 있음 | `summary` 를 본문 대용으로 쓰고 `content_len` 을 그 길이로 센다 |
| `body` · `summary` 둘 다 없음 | **제목만으로 통과시킨다.** 제외하지 않는다 |

**추출 쪽 영향이 크다.** 문서당 토큰이 10개 안팎이면 [04 §6](04-keyword-extraction-spec.md) 의 위치 가중치가 사실상 제목 가중치 하나가 되고, [06](06-related-keyword-spec.md) 의 동시출현은 거의 안 선다. 이건 정제 규격으로 덮을 문제가 아니라 도메인별 추출 경로 문제이고, [00 §7](00-overview.md) 한계 19번으로 올렸다. **결론이 나기 전에 04~07 의 임계값을 정하면 안 된다.**

## 3. `published_at` 처리

**`article.json` 에서 `published_at` 은 필수 필드다** (불변식 9). 생산자가 없는 기사를 저장하지 않으므로, 배치 계약 시절의 "시각이 없음" 분기는 발생하지 않는다.

| 상황 | 처리 |
| --- | --- |
| 정상 | 그대로 보존. 소스가 준 오프셋 포함 |
| 미래 시각 | 수집 시각보다 미래면 `collected_at` 으로 대체하고 경고 |
| 시각이 없음 · 못 읽음 · 오프셋 없음 | **발생하지 않는다.** 셋 다 [02 §3](02-input-contract.md) 의 `ARTICLE_CONTRACT_VIOLATION` 으로 DLQ 에서 잡힌다 — 있기만 한 값(`"invalid-date"`)도 막는다. 계약 판별과 정제가 같은 파서(`io/contract.parse_offset_datetime`)를 써서 판별은 통과하고 정제는 `None` 을 내는 값이 없다. 정제에 그 값이 오면 `INVALID_PUBLISHED_AT` 으로 버린다 ([§6](#6-필터)) — `published_date` 없는 파티션(`__HIVE_DEFAULT_PARTITION__`)을 만들지 않기 위한 마지막 방어선이다 |

**타임존이 없는 값도 오지 않는다.** `Article._needs_offset` 이 오프셋 없는 시각을 생산자 쪽에서 거부한다. 그리고 생산자 수집 이력은 `timestamptz` 라 오프셋 표기를 버리는데, `published_at_offset` 컬럼에 따로 남겨 발행 시점에 되살린다 (`ledger.restore_offset`). 즉 **한국 매체의 `+09:00` 이 `+00:00` 으로 바뀌어 오지 않는다.**

`published_at_offset` 이 없는 행(그 컬럼이 생기기 전에 적힌 행)은 읽은 그대로 나가므로 오프셋이 UTC 로 보일 수 있다. 순간은 같으니 `published_date` 계산에는 영향이 없다 — KST 로 변환해서 자르기 때문이다.

**미래 시각을 방어하는 이유** — 소스가 예약 발행이나 타임존 버그로 미래 날짜를 주는 일이 실제로 있다. 그대로 두면 아직 오지 않은 날짜에 언급량이 쌓이고, 그 행은 프론트 그래프의 오른쪽 끝을 이상하게 만든다. 보정 건수는 [§7](#7-버린-것과-고친-것을-센다) 에서 센다.

## 4. 텍스트 정제

**입력은 HTML 이다.** `body_text` 의 출처가 피드의 `content:encoded`(rss 소스)이거나 기사 페이지의 `div.atc_body_cont`(listing 소스)라, 마크업이 섞여 있다. 마크다운은 오지 않는다 — 커뮤니티 소스가 없기 때문이다.

순서가 중요하다. HTML 을 지우기 전에 코드 블록을 뽑아야 `<` 가 든 코드가 살아남는다.

```
1. 코드 블록 분리        <pre>, <code> → body_code 로 이동
2. HTML 태그 제거        나머지 마크업 제거. 엔티티 디코드
3. 링크 처리             앵커 텍스트만 남기고 href 는 버린다
4. URL 제거              본문에 그대로 박힌 http(s)://...
5. 유니코드 정규화        NFKC
6. 제어문자 · 이모지 제거
7. 공백 정규화           연속 공백 → 하나, 앞뒤 트림
8. 상투 요소 제거        관련기사 위젯 · 쇼핑 앵커 · 사진 크레딧 · 번역 고지
```

**8 이 7 뒤인 이유** — 줄 단위로 판정하므로 줄바꿈 하나가 남고 줄 앞뒤가 트림된 상태를 전제한다. 구현은 `normalize/boilerplate.py` 다.

### 단계 8 — 상투 요소 제거 (2026-09-09 추가)

**생산자의 제거는 `listing` 에만 듣는다.** `web-collect.md` #2 가 로그인 마스크(`atc_mask_login`)와 관련기사(`ab_related_article`)를 뽑는 단계에서 제거한다고 적었고, 그건 사실이다 — 다만 **기사 페이지를 파싱하는 `listing` 소스에서만**이다. `rss` 소스는 피드의 `content:encoded` 를 그대로 받으므로 그 안에 든 위젯이 함께 온다. 2026-09-09 스냅숏(373건) 실측:

| 상투 요소 | 나타나는 소스 | 문서 수 |
| --- | --- | --- |
| `관련기사` 위젯 | **rss 4곳만** (vogue 23 · wkorea 16 · gqkorea 15 · allure 7) | 61 |
| `상품 자세히 보기` | listing 2곳 (cosmopolitan 23 · harpersbazaar 3) | 26 |
| `구매하러 가기` | 양쪽 (rss 22 · listing 1) | 23 |
| `\| 인스타그램 @…` 캡션 크레딧 | 주로 listing (cosmopolitan 58) | 73 |
| `출처 게티 이미지` · `Photo by …` | listing 2곳 | 25 |
| `*… 기사를 리프트 하여 작성 되었습니다` | cosmopolitan 20 | 20 |

**스코어링으로는 못 막는다.** 같은 실측에서 이것들이 진짜 키워드보다 [04 §6](04-keyword-extraction-spec.md) 점수가 높았다 — `자세히 보기` 0.415 · `게티` 0.354 · `인스타그램` 0.384 대 `데님` 0.325. 짧은 블록에 반복 등장하고 문서 수가 적당해서, BM25 관점에서는 모범적인 키워드다. [04 §5](04-keyword-extraction-spec.md) 의 노이즈 사전도 답이 아니다 — n-gram 의 **모든** 토큰이 사전에 있어야 버리므로 `게티 이미지` · `상품 자세히 보기` 같은 변형을 계속 놓친다. **본문에 들어오지 않게 하는 것이 유일한 처방이고, 그 자리가 여기다.**

규칙은 세 모양이다.

| | 무엇 | 왜 그 모양인가 |
| --- | --- | --- |
| 꼬리 절단 | `관련기사` 줄부터 문서 끝까지 | 그 뒤는 전부 위젯이다 — 카테고리 · 다른 기사 제목 · `2026.08.31by 원예하` 서명 |
| 줄 제거 | 줄 전체가 쇼핑 앵커이거나, 번역 고지가 든 줄 | 앵커는 상품명 다음 줄에 문구만 있다 |
| **꼬리 자르기** | 줄 안의 크레딧 부분만 | 앞부분이 캡션이고 거기 브랜드명이 있다 — `반클리프 아펠 주얼리 \| 인스타그램 @vancleefarpels` 에서 줄을 통째로 버리면 `반클리프 아펠` 이 함께 사라진다 |

**⚠️ 목록은 fashion 7 매체를 보고 만들었다.** 소스가 늘면 그 매체의 상투 요소를 실측해서 추가한다 — [04 §9](04-keyword-extraction-spec.md) 의 상위 100 후보 검수에서 드러난다.

**멘션 제거는 없다.** `u/user`·`r/sub` 는 reddit 표기이고 이 소스 셋에 없다. 매체 기사에는 크레딧(`글 홍길동`)이 붙는데 그건 생산자가 `author` 로 분리하거나 본문 끝에 남기며, 토큰 하나라 통계에 영향이 없다.

### 코드 블록을 왜 분리하나

개발 도메인에서 코드 블록은 양날이다. 진짜 키워드(`kubectl`, `useEffect`)가 거기 있지만, 변수명·경로·스택트레이스 같은 잡음이 훨씬 많다. 본문에 섞어두면 [04](04-keyword-extraction-spec.md) 의 문서 빈도 통계가 오염된다.

그래서 **분리해서 보관하되 기본적으로는 쓰지 않는다.** `body` 만으로 추출하고, `body_code` 는 나중에 "코드 블록도 포함" 실험을 할 수 있게 남겨둔다. 버리지 않는 이유는 다시 만들려면 객체부터 다시 읽어야 하기 때문이다.

**⚠️ 지금 이 단계는 사실상 놀고 있다.** dev 도메인이 `hn` 하나이고 본문이 없다 ([§2](#2-본문이-없는-문서)). 코드 블록이 들어올 자리가 없다. 패션 기사에 `<pre>` 가 있을 일은 드물다. [00 §7](00-overview.md) 한계 19번이 정리되면 다시 값을 한다 — `hn` 댓글을 받기로 하면 코드가 대량으로 들어온다.

### 링크 텍스트는 남기고 URL 은 버리는 이유

앵커 텍스트는 사람이 고른 표현이라 키워드 후보로 값지다. URL 은 도메인명·경로 조각이 토큰으로 튀어나와 잡음이 된다.

**패션 기사에서는 이게 특히 중요하다.** 본문에 브랜드 공식 계정·쇼핑 링크가 많고, 앵커 텍스트가 곧 브랜드명인 경우가 잦다. URL 을 남기면 `www`·`com`·`kr` 같은 조각이 상위 후보로 올라온다.

## 5. 언어 판별

| 값 | 조건 |
| --- | --- |
| `ko` | 한글 문자 비율이 임계값 이상 |
| `en` | 라틴 문자 비율이 임계값 이상 |
| `mixed` | 둘 다 유의미한 비율 |
| `unknown` | 본문이 너무 짧거나 판별 불가 |

**문자 비율로 판별하고 언어 판별 라이브러리를 쓰지 않는다.** 이유는 (a) 우리가 구분해야 하는 것이 사실상 한/영 둘뿐이고 (b) 개발 도메인 텍스트는 코드·식별자가 섞여 있어 일반 언어 판별기가 자주 틀리며 (c) 의존성이 하나 줄기 때문이다.

`lang` 이 필요한 이유는 [04 §2](04-keyword-extraction-spec.md) 에서 토크나이저를 고르기 때문이다. `mixed` 는 두 토크나이저를 모두 돌린다. `unknown` 은 [§6](#6-필터) 에서 대개 걸러진다.

## 6. 필터

### 중복 제거 — 세 단계

| 단계 | 판별 | 처리 |
| --- | --- | --- |
| 1. 동일 문서 | 같은 `(source_id, source_document_id)` | 나중 것을 버린다 |
| 2. 같은 URL | 같은 `url_hash` | 대표 하나만 남긴다 |
| 3. 근사 중복 | 본문 SimHash 해밍 거리 ≤ 임계값 | `dup_of` 에 대표를 기록하고 **집계에서 제외** |

**1단계는 생산자 쪽에서 거의 다 걸러져 온다.** 불변식 7 이 `(source, article_id)` 하나에 수집 이력 행 하나·MinIO 키 하나를 보장하고, 불변식 12 가 수집 이력에 있는 기사를 다시 받지 않는다. 그래도 이 단계를 두는 이유는 at-least-once 다 — 같은 이벤트가 두 번 오면 `event_id` 처리 이력이 먼저 막지만([01 §4](01-architecture.md) 중복 차단 2), 처리 이력을 우회한 재처리(`--force`)에서는 이 단계가 마지막 방어선이다.

**3단계는 소스 셋이 바뀌면서 덜 중요해졌다.** 배치 계약 시절 상정한 것은 reddit·github 간 크로스포스트였다. 실제 소스는 국내 패션 매체 7곳과 Hacker News 라 서로 퍼나르지 않는다. 대신 **같은 매체 안에서 하위 섹션이 겹친다** — `harpersbazaar` 는 `/fashion` 과 `/fashion/{news,style,trend,…}` 를 함께 도는데(`web-collect.md` #2) 같은 기사가 두 목록에 나온다. 이건 `article_id` 가 같아 1단계에서 잡히므로 3단계까지 갈 일이 아니다.

**3단계를 유지하는 이유** — 두산매거진 4곳(`vogue`·`gqkorea`·`wkorea`·`allure`)이 같은 WordPress 템플릿을 쓰는 계열사다. 같은 보도자료를 각각 올리는 경우가 있고, 그건 `article_id` 도 URL 도 달라서 SimHash 말고는 잡히지 않는다.

**URL 정규화** (2단계의 전제):

```
소문자 스킴·호스트 → 기본 포트 제거 → 추적 파라미터 제거(utm_*, fbclid, ref, source)
→ 프래그먼트(#...) 제거 → 후행 슬래시 정리 → 쿼리 파라미터 키 정렬
```

**3단계를 지우지 않고 표시만 하는 이유** — 근사 중복 판별은 임계값에 민감해서 틀릴 수 있다. 지워버리면 임계값을 조정했을 때 되살릴 방법이 객체 재처리뿐이다. `dup_of` 로 표시해두면 집계 쿼리의 조건만 바꿔 다시 실험할 수 있다.

**3단계가 필요한 이유** — 크로스포스트, 미러 사이트, 봇이 퍼나른 같은 글이 여러 소스에서 들어온다. 이걸 안 잡으면 특정 키워드의 언급량이 실제보다 부풀고, 그게 곧 잘못된 급상승 판별이 된다 ([07 §5](07-metrics-and-ranking-spec.md)).

SimHash 를 쓰는 이유는 단일 노드에서 MinHash + LSH 를 돌리는 것보다 단순하고, 실행당 수백 건 규모에서는 밴딩 없이 비교해도 감당되기 때문이다. 규모가 커지면 밴딩을 넣는다.

**본문이 없는 문서는 3단계를 건너뛴다.** 제목만으로 SimHash 를 계산하면 해밍 거리가 우연히 가까워지는 일이 흔하다 — dev 도메인 전량이 서로 중복으로 판별될 수 있다.

### 품질 필터

**본문 유무로 분기한다** ([§2](#2-본문이-없는-문서)). 아래 표는 `body` 가 있는 문서에 적용된다.

| 조건 | 처리 | 이유 |
| --- | --- | --- |
| 본문 길이가 하한 미만 | 제외 | 키워드를 뽑을 것이 없다 |
| 빈 본문 (정제 후) | 제외 | 정제가 다 걷어낸 경우 |
| `lang = unknown` | 제외 | 토크나이저를 고를 수 없다 |
| `published_date` 가 없다 | 제외 (`INVALID_PUBLISHED_AT`) | 날짜 파티션 키가 없다. 계약 판별이 먼저 막으므로 여기 오면 배선이 깨진 것이다 ([§3](#3-published_at-처리)) |
| 링크만 있고 텍스트가 없음 | 제외 | 정제 후 본문이 비는 경우 |
| 같은 `author` 가 한 실행에서 상한 초과 | **제외하지 않고 표시** | [07 §7](07-metrics-and-ranking-spec.md) 에서 기여 상한으로 처리 |

`body` 가 애초에 없는 문서(`members_only`, `hn`)는 위 필터를 타지 않는다. 대신 **제목 길이 하한**만 본다. 제목은 필수 필드라 비어 있을 수 없지만(불변식 9), 한두 글자짜리는 걸러낸다.

**소스별 삭제 표식(`[deleted]`·`[removed]`)은 없다.** 그건 커뮤니티 소스의 관습이고, 매체 기사에는 해당하지 않는다. 소스가 기사를 내리면 우리 쪽에는 그냥 안 들어오고, 이미 받은 것은 수집 이력과 MinIO 에 남는다.

**봇 의심 문서를 여기서 지우지 않는 이유** — 저자별 문서 수 상한은 정상적인 활발한 사용자도 걸린다. 문서 단계에서 지우면 그 사람의 글이 통째로 사라지는데, 집계 단계에서 가중치로 누르면 언급량만 조정되고 콘텐츠 목록에는 남는다. 프론트의 "관련 콘텐츠"가 비는 것보다 낫다.

**⚠️ `author` 기반 봇 방어가 이 소스 셋에서는 거의 의미가 없다.** 매체 기사의 저자는 소속 기자라 문서 수가 원래 많고, `hn` 은 `author` 가 투고자라 스팸 신호가 아니다. [07 §7](07-metrics-and-ranking-spec.md) 의 `author_count` 기반 판별을 그대로 쓰면 정상 기자를 봇으로 누른다. 소스 셋이 커뮤니티에서 매체로 바뀐 결과이고, 임계값을 실제 분포로 재기 전까지는 이 방어를 끄는 편이 안전하다.

## 7. 버린 것과 고친 것을 센다

**필터로 사라진 문서를 조용히 넘기지 않는다.** 실행마다 `pl_batch_stat` 에 기록한다 ([08 §3](08-storage-schema.md)).

**세는 것은 배치마다, 쓰는 것은 실행 끝에 한 번이다** (`io/stats.RunStats`). `Trigger.AvailableNow` 가 배치를 여럿 내면 전부 같은 `ingest_run_id` 라, 배치마다 upsert 하면 뒤 배치가 앞 배치를 덮는다. 건수는 누적하고 비율·분포는 끝에 누적 원자료에서 다시 계산한다. 쓸 때는 그 실행의 옛 행을 지우고 다시 넣는다 — 재처리에서 사라진 `(지표, 차원)` 행이 옛 값으로 남지 않게. `curated` · `contents` 쓰기가 전부 끝난 뒤이므로, 쓰기가 죽은 실행의 통계는 남지 않는다 (2026-09-09 리뷰).

| 항목 | 왜 |
| --- | --- |
| 단계별 제외 건수 (중복 1·2·3, 품질 필터별) | 어느 필터가 과하게 무는지 |
| **본문 없는 문서 수 — `members_only` / `route=api` 별로** | 7.4% 라는 실측값에서 벗어나면 회원 전용 판별(`div.membershipLine`)이 깨진 신호다 |
| 미래 시각 보정 건수 | 소스 이상 신호 |
| `lang` 분포 | 토크나이저 선택이 맞는지 |
| 입력 건수 대비 생존율 | 전체 건강도 |
| **`route` 별 본문 길이 분포** | `listing` 소스는 기사 페이지 HTML 을 파싱한 결과라 마스크·관련기사가 섞여 들어올 수 있다 |

생존율이 갑자기 떨어지면 소스가 HTML 구조를 바꼈거나 생산자 어댑터가 깨진 것이다. 이 숫자가 없으면 "왜 이번 주 언급량이 줄었지" 에 답할 수 없다.

**`published_at` 대체 건수는 세지 않는다.** 대체가 일어나지 않는다 ([§3](#3-published_at-처리)) — 그 값이 없는 기사는 생산자가 저장하지 않는다. 0 이 나올 것이 확실한 지표를 세면 대시보드만 길어진다.

**본문 없는 문서 수가 이 목록에서 가장 값진 지표다.** 회원 전용 판별은 `div.membershipLine` 이라는 CSS 선택자 하나에 달려 있고(`web-collect.md` #2), 매체가 템플릿을 바꾸면 조용히 깨진다. 깨지는 방향이 둘인데 둘 다 나쁘다 — 전부 회원 전용으로 판별하면 본문이 통째로 안 오고, 전부 일반으로 판별하면 저장하면 안 되는 본문을 저장한다. 후자는 법적 문제다(불변식 2). 비율이 튀면 즉시 담당 1 에게 알린다.

## 8. `contents` 적재

표준 문서에서 서비스 테이블로 옮긴다. 매핑은 대부분 1:1 이고, 주의할 것만 적는다.

| `contents` 컬럼 | 값 |
| --- | --- |
| `title` | 정제된 제목. **대체 규칙이 필요 없다** — 필수 필드다 |
| `source` | 이벤트의 `source_id`(`vogue`·`hn` 등). 값 규약 확정 필요 ([00 §7](00-overview.md) 18번) |
| `url` | 정규화된 URL |
| `body_object_key` | 그 문서가 든 `curated` Parquet 의 객체 키 ([01 §3](01-architecture.md)) |
| `published_at` | 소스가 준 시각. 늘 있다 |
| `collected_at` | 이벤트의 `collected_at` |

컬럼이 일곱 개(`id` 포함)뿐이다. **v2 에서 `summary` 가 없어졌다** ([erd](erd/erd-00-current.md)).

**`title` 대체 규칙이 사라졌다.** 배치 계약 시절에는 "소스에 제목 개념이 없으면 `null`" 이라 `contents.title` 을 채우려고 본문 앞부분을 잘라 넣는 규칙이 있었다. `article.json` 의 `title` 은 필수이고 공백만 있어도 생산자가 거부하므로(불변식 9), 이제 표준 문서와 `contents` 둘 다 제목이 있다. **제목 위치 가중치([04 §6](04-keyword-extraction-spec.md))가 오염될 경로가 없어졌다.**

**표준 문서의 `summary` 는 채우지만 서비스로 내보내지 않는다.** 그건 소스가 준 리드문이고 매체의 저작물이라, 화면에 나가면 불변식 3(본문·리드는 내부 저장소에만)을 깬다. v1 에서는 `contents.summary` 라는 빈 컬럼이 있어 "여기에 넣지 마라" 를 규칙으로 지켜야 했는데, **v2 에는 그 컬럼이 아예 없어서 스키마가 대신 막아준다.** 리드문은 `curated` Parquet 안에만 있고 [04](04-keyword-extraction-spec.md) 의 추출 입력으로만 쓰인다.

키워드 단위 요약 자리인 `trends.summary` 는 다른 것이다. 그건 LLM 이 채울 자리이고 MVP 에서는 `NULL` 로 둔다 ([00 §4](00-overview.md)). **소스 리드문을 거기 넣는 것도 같은 이유로 안 된다.**

`published_at` 이 항상 있으므로 관련 콘텐츠 목록의 발행일순 정렬이 늘 성립한다. `published_date`([§3](#3-published_at-처리))는 집계용 내부 값이고 `contents` 로 나가지 않는다.

### ⚠️ `url` 이 varchar UK 다

`contents.url` 에 직접 UNIQUE 가 걸려 있다. 두 가지 위험이 있다.

**1. 긴 URL 에서 삽입이 실패할 수 있다.** PostgreSQL B-tree 인덱스 항목 상한은 약 2704바이트다. 멀티바이트 문자가 섞인 긴 URL 이 이걸 넘으면 `INSERT` 가 오류로 죽는다. 배치 하나가 통째로 실패한다.

**2. 정규화 결과가 곧 유일성 기준이다.** [§6](#6-필터) 의 URL 정규화가 곧 중복 판별 규칙이 된다. 정규화 규칙을 바꾸면 이미 들어간 행과 새로 들어올 행의 기준이 달라져 중복이 생긴다.

**이 묶음의 방어** — 적재 전에 URL 바이트 길이를 검사하고, 상한을 넘으면 문서를 제외하고 [§7](#7-버린-것과-고친-것을-센다) 에 센다. 실제로는 드물지만, 드물게 배치 전체를 죽이는 종류의 문제라 반드시 막는다.

**백엔드에 요청할 것** — `url` 의 varchar 길이 제한과, 가능하면 `sha256(url)` 해시 컬럼에 UNIQUE 를 옮기는 것. 후자가 근본 해결이다. [00 §7](00-overview.md) 13번(`contents.url` 길이·인덱스).

### `contents.id` 를 받아오는 문제

`keyword_contents` 는 `content_id bigint` 를 요구하는데, `contents.id` 는 DB 가 발행하는 시퀀스 값이다. Spark 는 이 값을 미리 모른다.

**2단계로 처리한다.**

1. `contents` 를 `url` 기준 upsert. `INSERT ... ON CONFLICT (url) DO UPDATE ... RETURNING id, url`
2. 반환된 `(url → id)` 매핑을 내부 테이블에 두고 `extract` 가 읽는다.

`DO NOTHING` 이 아니라 `DO UPDATE` 를 쓰는 이유는 `DO NOTHING` 이 충돌한 행에 대해 `RETURNING` 을 내주지 않아서, 이미 있는 문서의 `id` 를 못 받기 때문이다. 재처리 시 이게 곧바로 문제가 된다.

내부 매핑 테이블은 `url_hash` 를 키로 둔다 ([§1](#1-표준-문서-스키마)). 긴 URL 을 조인 키로 쓰면 매번 문자열 비교가 일어나고, 파이프라인 내부에서는 그럴 이유가 없다.
