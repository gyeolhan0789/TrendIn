# 04 — 키워드 추출

`extract` Job 의 전반부. 정제 문서에서 키워드 **후보**를 뽑고 점수를 매긴다.

사전 화이트리스트를 쓰지 않고 통계로 발견한다. 서비스가 파는 것이 "새로 뜨는 트렌드"라 미리 아는 단어만 세면 핵심이 사라지기 때문이다. 대신 노이즈가 필연이므로 **이 문서는 재현율(recall)을 담당하고, [05](05-keyword-registry-spec.md) 가 정밀도(precision)를 담당한다.** 여기서는 넓게 뽑고 거기서 좁게 승격한다. 이 역할 분담이 두 문서를 나눈 이유다.

## 1. 파이프라인

```
정제 문서 (curated Parquet)
  ↓ 토큰화              언어별 분기
  ↓ 후보 생성            n-gram · 약어 · 코드 식별자 · 해시태그
  ↓ 표층 정규화          비교키 생성, 대표 표기 선정
  ↓ 필터                불용어 · 빈도 · 형태
  ↓ 스코어링             C-value · 문서 내 중요도 · 위치
  ↓ 선별                문서당 상위 K
문서-후보 매핑 + 후보 통계  (내부 테이블)
  ↓
[05] 정규화 · 통합 · 승격 → keywords · keyword_contents
```

문서-후보 매핑은 **모두** 내부 테이블에 남긴다. 승격되지 않은 후보도 버리지 않는다. 임계값을 낮췄을 때 문서를 다시 읽지 않고 재평가하기 위해서다.

## 2. 토큰화

`lang` ([03 §5](03-normalization-spec.md)) 으로 분기한다. `mixed` 는 둘 다 돌리고 결과를 합친다.

### 한국어

형태소 분석기(kiwipiepy)로 품사를 얻고, 아래 태그만 남긴다.

| 태그 | 무엇 | 남기는 이유 |
| --- | --- | --- |
| `NNG` | 일반명사 | 키워드의 본체 |
| `NNP` | 고유명사 | 브랜드·제품명 |
| `SL` | 외국어 | 한국어 문서 속 영문 용어 |
| `SH` | 한자 | |
| `SN` | 숫자 | 단독으로는 버리지만 복합어의 일부로 필요 (`Python 3`) |

동사·형용사·조사·어미는 버린다. 트렌드 키워드는 사실상 명사구라서다.

**복합명사는 원형과 분해형을 둘 다 후보로 낸다.** 분석기가 `개발자경험` 을 `개발자` + `경험` 으로 쪼개면 원형이 사라지는데, 트렌드 용어는 대개 붙여 쓴 복합어다. 둘 다 내고 [§6](#6-스코어링) 의 C-value 가 어느 쪽이 살아남을지 정하게 한다.

### 영어

형태소 분석기를 쓰지 않는다. 이유는 (a) 의존성이 하나 늘고 (b) 개발 도메인 텍스트는 코드·식별자가 섞여 있어 일반 POS 태거가 자주 틀리며 (c) 아래 방식으로 충분하기 때문이다.

```
공백·구두점으로 분리
  → 소유격('s) 제거
  → 코드 식별자 보존:  camelCase, snake_case, dotted.path, kebab-case
  → 버전 문자열 보존:  3.12, v2, ES2023
  → 대문자 약어 보존:  MCP, LLM, API   (2~6자 전부 대문자)
```

**원표기를 보존한다.** 소문자로 접는 것은 [§4](#4-표층-정규화) 의 비교키에서만 하고, 토큰 자체는 대소문자를 유지한다. `MCP` 와 `mcp` 를 같게 보되 화면에는 `MCP` 를 내야 하기 때문이다.

## 3. 후보 생성

### 연속 토큰 구간

**불용어와 구두점을 경계로 잘라, 그 사이의 연속 토큰을 후보로 삼는다.** POS 태거 없이 명사구를 근사하는 방법이다.

```
"the new agentic workflow is changing how we build"
 ────         ──────────────── ──                 ─────
 불용어        후보 구간         불용어              불용어

→ 후보: "new agentic workflow", "agentic workflow", "workflow", "new agentic", ...
```

구간에서 길이 1~3 의 모든 n-gram 을 낸다. 길이 상한을 3 으로 두는 이유는 4 이상이 거의 항상 문장 조각이고, 후보 수가 조합적으로 늘기 때문이다.

한국어도 같다. 남긴 품사 태그가 연속된 구간을 잡고 그 안에서 n-gram 을 낸다.

### 별도 규칙으로 잡는 것

| 유형 | 규칙 | 왜 따로 |
| --- | --- | --- |
| 대문자 약어 | 2~6자 전부 대문자 | 불용어 경계 규칙으로는 단독 토큰이라 놓치기 쉽다 |
| 약어 전개형 | `Model Context Protocol (MCP)` 패턴 | **[05 §3](05-keyword-registry-spec.md) 통합의 결정적 증거**다. 쌍으로 기록한다 |
| 코드 식별자 | camelCase · snake_case · dotted | 공백이 없어 n-gram 으로는 안 잡힌다 |
| 해시태그 | `#` 로 시작 | 사람이 직접 고른 표현이라 값지다. 특히 패션 도메인 |
| 버전 붙은 이름 | `Python 3.12`, `React 19` | 숫자 필터에 걸리지 않게 예외 처리 |

해시태그가 살아 있는 이유는 [03 §4](03-normalization-spec.md) 가 멘션과 URL 만 지우고 해시태그는 남기기 때문이다.

## 4. 표층 정규화

후보마다 **비교키**와 **대표 표기**를 만든다.

| | 만드는 법 | 쓰는 곳 |
| --- | --- | --- |
| 비교키 `normalized_key` | NFKC → 소문자 → 하이픈·언더스코어·연속공백을 단일 공백 → 앞뒤 구두점 제거 | 같은 것인지 판정 |
| 대표 표기 `surface` | 그 비교키를 가진 원표기 중 **코퍼스에서 가장 빈번한 것** | 화면에 내보내는 값 |

대표 표기를 빈도로 고르는 이유는, 같은 것을 사람들이 `AI agent`·`AI Agent`·`ai agent` 로 쓸 때 다수가 쓰는 표기가 대개 옳기 때문이다. 첫 등장이나 사전순으로 고르면 이상한 표기가 대표가 된다.

**영어 복수형은 이 단계에서 접지 않는다.** `-s`/`-es` 제거는 `glasses`→`glasse`, `CSS`→`CS` 같은 과교정을 낳는다. [05 §2](05-keyword-registry-spec.md) 에서 빈도 근거를 갖고 처리한다.

이 단계가 만드는 비교키는 `keywords.normalized_name` 의 값이 된다.

## 5. 필터

순서대로 적용한다. 싼 것부터 거른다.

| # | 필터 | 기준 | 무엇을 잡나 |
| --- | --- | --- | --- |
| 1 | 형태 | 숫자만 / 특수문자만 / 단일 문자 | 파편 |
| 2 | 길이 | 하한·상한 (문자 수) | 조각과 문장 |
| 3 | 불용어 | 언어별 + 도메인별 목록 | `것`, `사람`, `thing`, `people` |
| 4 | 노이즈 사전 | 파일 확장자, HTTP 상태, 흔한 변수명(`foo`, `tmp`) | 코드 잔재 |
| 5 | **DF 하한** | 서로 다른 문서 N개 이상 | **오타·1회성.** 가장 많이 거른다 |
| 6 | **DF 상한** | 코퍼스의 X% 초과 시 제거 | `개발`, `패션`, `code` 같은 무정보어 |
| 7 | 소스 편중 | 단일 소스에만 존재 | 승격 보류 (제거 아님) → [05 §5](05-keyword-registry-spec.md) |

**5번과 6번이 이 방식의 핵심 방어선이다.**

DF 하한이 없으면 오타·고유명사·일회성 문자열이 후보 풀의 대부분을 차지한다. 자동 발견 방식이 실패하는 가장 흔한 이유다.

DF 상한이 필요한 이유는 도메인 코퍼스 안에서 도메인 이름 자체가 무정보이기 때문이다. 개발 코퍼스에서 `code` 는 절반 이상의 문서에 나오고, 그건 트렌드가 아니다. TF-IDF 의 IDF 항이 이걸 어느 정도 눌러주지만, 아예 후보에서 빼는 편이 하류 계산을 가볍게 한다.

**두 임계값 모두 절대값이 아니라 코퍼스 크기에 대한 비율로 둔다.** 수집량이 늘면 절대값 기준은 저절로 빡빡해진다.

### 불용어 목록을 어떻게 만드나

초기 목록은 표준 한국어·영어 불용어에서 시작하고, **DF 상한에 걸린 후보를 주기적으로 검토해 도메인 불용어로 승격한다.** 손으로 처음부터 쓰지 않는다. 자동 발견 방식의 부산물로 얻는 것이 정확하다.

## 6. 스코어링

세 축을 정규화해 가중합한다. 가중치는 설정값이다.

### C-value — 복합어 우선

같은 구간에서 나온 n-gram 들 사이의 포함 관계를 본다. 짧은 후보가 항상 더 긴 후보의 일부로만 나타나면 짧은 쪽을 감점한다.

```
C-value(a) = log2(|a|) × ( f(a) − (1/|T_a|) × Σ_{b ∈ T_a} f(b) )

|a|   : a 의 토큰 수
f(a)  : a 의 빈도
T_a   : a 를 포함하는 더 긴 후보들
```

**이게 필요한 이유** — `agentic workflow` 가 200회 나오고 `workflow` 도 200회 나오는데 그 200회가 전부 `agentic workflow` 안이라면, `workflow` 는 독립된 키워드가 아니다. C-value 가 이걸 잡는다. 반대로 `workflow` 가 독립적으로도 500회 나오면 둘 다 살아남는다.

`log2(|a|)` 항이 긴 후보에 가산점을 주는데, 트렌드 키워드가 대개 복합어(`Vibe Coding`, `Ballet Sneakers`)라서 이 편향이 우리에게 유리하다.

### 문서 내 중요도

BM25 로 계산한다. TF-IDF 보다 나은 이유는 **문서 길이 정규화**가 들어 있어서다. 소스마다 글 길이가 크게 다른데(깃허브 이슈 vs 스택오버플로 답변), TF-IDF 는 긴 문서의 키워드를 과대평가한다.

### 위치 가중

`title` 에 등장하면 가중치를 곱한다. 제목은 글쓴이가 주제를 압축한 자리라 신호가 가장 세다. [03 §2](03-normalization-spec.md) 가 제목에 본문을 채워 넣지 못하게 막은 것이 이 가중치를 지키기 위해서다.

### 결합

세 축을 각각 문서 내에서 0~1 로 정규화한 뒤 가중합한다. 원값끼리 더하면 스케일이 큰 축이 다 먹는다.

## 7. 선별

| 대상 | 기준 |
| --- | --- |
| `keyword_contents` 로 나갈 것 | 문서당 점수 상위 K개 **이고** 점수 하한 이상 |
| 내부 후보 통계에 남길 것 | 필터를 통과한 **전부** |

문서당 상한 K 를 두는 이유는 긴 문서가 연관 키워드 그래프를 지배하는 것을 막기 위해서다 ([06 §2](06-related-keyword-spec.md)). 만 단어짜리 글에서 200개 키워드를 뽑으면 그 안의 모든 쌍이 동시출현으로 기록되어 통계가 그 문서 하나에 휘둘린다.

점수 하한을 함께 두는 이유는 키워드가 실제로 적은 문서에서 억지로 K개를 채우지 않기 위해서다.

## 8. 도메인별 차이

같은 코드에 설정만 다르게 준다. 도메인마다 코드를 갈라놓으면 개선이 한쪽에만 반영된다.

| | 개발 | 패션 |
| --- | --- | --- |
| 주 언어 | 영어 우세 | 한국어 우세 |
| 코드 식별자 규칙 | 활성 | 비활성 (잡음만 는다) |
| 해시태그 | 낮은 가중 | **높은 가중** |
| 노이즈 사전 | 파일 확장자·스택트레이스·HTTP 상태 | 가격·사이즈 표기·쇼핑몰 상투어 |
| 불용어 | `code`, `error`, `issue`, `version` | `구매`, `배송`, `할인`, `추천` |

패션 쪽 불용어에 쇼핑 상투어가 들어가는 이유는 커머스 문서가 섞여 들어오면 `무료배송` 같은 것이 상위 트렌드로 올라오기 때문이다.

## 9. 품질을 어떻게 재나

정답셋이 없다. 만들 시간도 없다. 그래서 세 가지를 병행한다.

### 수동 검수 — precision@K

무작위 문서 100건을 뽑아 각 문서의 상위 10개 후보가 "이 글의 키워드로 타당한가"를 사람이 O/X 로 매긴다. 비율이 precision@10 이다.

- 절대 수치보다 **변경 전후 비교**가 목적이다. 임계값을 바꾸고 같은 100건에 다시 매기면 개선인지 개악인지 안다.
- 100건은 통계적으로 넉넉하진 않지만 한 사람이 한 시간에 할 수 있는 규모다. 안 하는 것보다 훨씬 낫다.
- 검수한 결과는 파일로 남긴다. 다음 검수 때 같은 문서를 쓴다.

### 회귀 스냅샷

고정 샘플 문서 30건을 테스트 픽스처로 두고, 추출 결과를 스냅샷으로 저장한다. 코드를 고쳤을 때 스냅샷이 바뀌면 테스트가 실패한다.

**의도한 변경이면 스냅샷을 갱신하고 diff 를 커밋에 남긴다.** 목적은 변경을 막는 게 아니라 **의도하지 않은 변경을 드러내는 것**이다. 리팩터링 한 줄이 추출 결과를 바꾸는 일이 실제로 자주 있다. 자세한 것은 [09 §4](09-dev-and-test.md).

### 분포 모니터링

배치마다 자동으로 기록하고, 급변하면 사람이 본다.

| 지표 | 급변이 뜻하는 것 |
| --- | --- |
| 문서당 평균 후보 수 | 정제 실패 또는 필터 오작동 |
| 신규 후보 유입률 | 급증하면 노이즈, 급감하면 필터 과잉 |
| DF 하한에 걸려 탈락한 비율 | 코퍼스 대비 임계값이 안 맞음 |
| 후보 길이 분포 | 파편 증가 신호 |
| 상위 100 후보 목록 | **사람이 직접 훑는다.** 오타나 조각이 보이면 즉시 문제 |

마지막 줄이 가장 값싸고 효과적이다. 상위 100개를 눈으로 보면 뭔가 잘못됐을 때 30초 안에 안다.

## 10. 튜닝과 재추출

임계값은 **설정 파일**에 둔다 ([01 §7](01-architecture.md)). 코드 상수로 두면 튜닝 한 번에 이미지 재빌드가 필요하다.

```yaml
extraction:
  ngram_max: 3
  df_min_ratio: ...
  df_max_ratio: ...
  score_weights: { c_value: ..., bm25: ..., title: ... }
  per_document_top_k: ...
  score_floor: ...
```

### 설정을 바꾸면 어디까지 다시 도나

| 바꾼 것 | 재실행 범위 |
| --- | --- |
| 스코어링 가중치, `top_k`, `score_floor` | `extract` 만. curated 부터 |
| 토큰화·후보 생성 규칙 | `extract` 만. curated 부터 |
| 불용어·노이즈 사전 | `extract` 만. curated 부터 |
| 정제 규칙 ([03](03-normalization-spec.md)) | `ingest` 부터. MinIO 원문부터 |

**대부분의 튜닝이 `extract` 재실행으로 끝난다.** [01 §2](01-architecture.md) 에서 `extract` 를 분리한 값어치가 여기서 나온다.

### 변경 이력을 남긴다

설정을 바꿀 때마다 **적용 시점과 값을 내부 테이블에 기록한다.** 이게 없으면 "9월 1일 이전과 이후의 언급량 추이가 왜 끊겼는지"를 설명할 수 없다. 임계값을 낮추면 모든 키워드의 언급량이 한꺼번에 올라가는데, 기록이 없으면 그게 실제 트렌드 변화로 보인다.

이력을 남기는 것만으로는 부족하고, **임계값을 바꾸면 영향 범위의 통계를 재계산해야 한다.** 재계산 없이 두면 경계 날짜에 계단이 생긴다. 범위 판단은 [07 §3](07-metrics-and-ranking-spec.md).
