# 06 — 연관 키워드

`aggregate` Job 의 일부. 키워드 사이의 연관도를 계산해 `keyword_relations` 를 채운다. 트렌드 상세 화면의 "연관 키워드" 영역이 이 값을 쓴다.

[05](05-keyword-registry-spec.md) 와 짝이다. **05 는 "같은 것"을 찾고 이 문서는 "함께 나오는 것"을 찾는다.** 둘은 통계적으로 헷갈리기 쉬워서 [§6](#6-동의어와-연관어의-구분선) 에서 구분선을 정의한다.

## 1. 채울 수 있는 것과 없는 것

`keyword_relations` 의 컬럼은 여섯 개다.

| 컬럼 | 채우나 |
| --- | --- |
| `source_keyword_id` · `target_keyword_id` | PK |
| `relation_score` numeric | [§4](#4-relation_score) |
| `co_occurrence_count` bigint | [§2](#2-동시출현의-단위--문서) |
| `updated_at` | 계산 시각 |

**표현할 수 없는 것이 세 가지 있다.** 스키마에 자리가 없어서다.

| 없는 것 | 결과 |
| --- | --- |
| `period` | **기간별 연관도를 담을 수 없다.** 하나의 기준 기간으로만 계산한다 ([§3](#3--기준-기간을-하나-골라야-한다)) |
| 이전 점수 · 변화율 | 연관도가 오르는 중인지 내려가는 중인지 보여줄 수 없다 |
| 상태 (신규 / 상승 / 유지) | 새로 생긴 연관인지 원래 있던 연관인지 구분할 수 없다 |

셋 다 우회 방법이 없다. [00 §7](00-overview.md) 한계 2·3번이다.

## 2. 동시출현의 단위 — 문서

두 키워드가 **같은 문서에 등장하면** 동시출현 1회다. 문장 단위나 슬라이딩 윈도우를 쓰지 않는다.

| 방식 | 채택 여부 | 이유 |
| --- | --- | --- |
| 문서 단위 | **채택** | 우리 문서는 짧다. 소셜 게시글·이슈·질문 하나가 대개 한 주제다 |
| 문장 단위 | 기각 | 신호가 너무 희박해진다. 문장 하나에 키워드 둘이 같이 있는 경우가 드물다 |
| N 토큰 윈도우 | 기각 | 윈도우 크기라는 임의 파라미터가 하나 더 늘고, 문서가 짧아 문서 단위와 결과가 거의 같다 |

**문서당 키워드 수 상한 K 가 여기서 결정적이다** ([04 §7](04-keyword-extraction-spec.md)). 상한이 없으면 긴 문서 하나가 K²/2 개의 쌍을 만들어 통계를 혼자 지배한다. 만 단어짜리 글에서 200개 키워드를 뽑으면 그 글 하나가 약 2만 쌍을 기여한다.

**근사 중복 문서(`dup_of` 가 있는 것)는 제외한다** ([03 §6](03-normalization-spec.md)). 크로스포스트된 같은 글이 같은 쌍을 반복 기여하면 연관도가 부풀려진다.

`co_occurrence_count` 에 이 값을 그대로 넣는다. 점수와 달리 해석이 필요 없는 원자료라, 나중에 점수 공식을 바꿔도 이 값은 그대로 쓸 수 있다.

## 3. ⚠️ 기준 기간을 하나 골라야 한다

`keyword_relations` 에 `period` 가 없으므로, **어느 구간의 문서로 계산할지를 정해서 그것만 유지한다.**

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| `24H` | 지금 뜨는 조합을 즉시 반영 | 표본이 적어 NPMI 가 요동친다. 매일 연관 키워드가 통째로 바뀐다 |
| `7D` | 균형 | |
| **`30D`** | **표본이 가장 안정적** | 최근 생긴 연관을 늦게 잡는다 |

**`30D` 를 제안한다.** 이유는 두 가지다.

1. **연관 키워드는 자주 바뀌면 안 된다.** 사용자가 어제 본 연관 키워드가 오늘 전부 달라져 있으면 신뢰를 잃는다. 언급량 순위는 바뀌는 게 정보지만, 연관 관계는 안정성이 정보다.
2. **[§6](#6-동의어와-연관어의-구분선) 의 동의어 판정이 이 값을 쓴다.** 그 판정은 되돌리기 어려운 결정이라 가장 안정된 통계여야 한다.

**한계** — 새로 뜬 키워드는 30일 표본이 없어 연관 키워드가 비거나 부실하다. `NEW` 로 뜬 트렌드의 상세 화면이 가장 볼 만해야 하는데 거기가 제일 비는 셈이다.

완화책은 **관측 기간이 짧은 키워드에 한해 가용한 전 구간을 쓰는 것**이다. `first_seen_at` 이후 30일이 안 됐으면 있는 만큼으로 계산한다. 표본이 적은 것은 [§4](#4-relation_score) 의 최소 동시출현 임계값이 걸러준다.

기준 기간은 설정값으로 두고 [04 §10](04-keyword-extraction-spec.md) 과 같은 방식으로 이력을 남긴다.

## 4. `relation_score`

### NPMI

날것의 동시출현 횟수를 점수로 쓰지 않는다. 흔한 키워드끼리가 항상 1위가 되기 때문이다. 개발 도메인에서 `AI` 와 `개발` 은 자주 함께 나오지만 그건 둘 다 흔해서지 서로 관련이 깊어서가 아니다.

**PMI** 는 이 편향을 없애지만 저빈도 쌍이 폭발한다. 각각 3번씩 나오고 그 3번이 전부 같은 문서였던 두 키워드가 최고점을 받는다.

**NPMI** 를 쓴다. PMI 를 `-1 ~ 1` 로 정규화한 것이다.

```
p(a)   = a 가 등장한 문서 수 / 전체 문서 수
p(a,b) = a 와 b 가 함께 등장한 문서 수 / 전체 문서 수

PMI(a,b)  = log( p(a,b) / (p(a)·p(b)) )
NPMI(a,b) = PMI(a,b) / ( −log p(a,b) )
```

| NPMI | 뜻 |
| --- | --- |
| 1 | 항상 함께만 나온다 |
| 0 | 독립 |
| −1 | 함께 나오지 않는다 |

### 최소 동시출현 임계값은 필수다

**NPMI 만으로는 저빈도 폭발을 막지 못한다.** 정규화가 값의 범위를 눌러줄 뿐, 표본이 적으면 추정 자체가 불안정하다.

그래서 `co_occurrence_count` 하한을 둔다. 이 하한 없이 PMI 계열을 쓰는 것이 이 종류의 계산에서 가장 흔한 실수다.

하한은 절대값이 아니라 **각 키워드의 문서 수에 대한 상대 조건**을 함께 본다. 문서 5건짜리 키워드와 5000건짜리 키워드에 같은 절대 하한을 적용하면 전자는 너무 쉽게 통과하고 후자는 의미 있는 쌍이 잘린다.

### 임베딩과 결합

```
base      = clip(NPMI, 0, 1)                       음수는 0. "덜 관련"과 "무관"을 구분할 필요가 없다
semantic  = clip(cosine(emb_a, emb_b), 0, 1)       [01 §5]
score     = α · base + (1 − α) · semantic          α 는 설정값
```

**임베딩을 섞는 이유** — 동시출현만 보면 "표현은 다르지만 같은 흐름"인 키워드를 놓친다. 두 키워드가 다른 커뮤니티에서 따로 쓰이면 같은 문서에 안 나오지만, 사용자에게는 연관으로 보이는 게 맞다.

**α 를 0.5 로 두지 않고 동시출현 쪽에 무게를 싣는다.** 임베딩은 [05 §4](05-keyword-registry-spec.md) 에서 봤듯 "관련 있음"을 너무 넉넉하게 판정한다. 실제 데이터에 근거한 동시출현이 주 신호이고 임베딩은 보정이다.

### 값 범위

`relation_score` 는 numeric 이고 0~1 로 사상한다. 다이어그램에 정밀도가 없으므로 **소수 자릿수를 확인해야 한다.** `numeric(5,4)` 같은 제약이 걸려 있으면 반올림 자리를 맞춰야 하고, 무제약 numeric 이면 그대로 넣어도 된다.

## 5. 저장 — 방향별 상위 N

### 양방향 2행

PK 가 `(source_keyword_id, target_keyword_id)` 이므로 `(a,b)` 와 `(b,a)` 가 별개 행이다. 쌍을 정렬해 한 행만 두는 방식(`a < b`)을 쓰지 않는다.

조회가 항상 `source_keyword_id` 기준(트렌드 → 연관 키워드, 관심 키워드 → 연관 트렌드)이라, 한쪽만 저장하면 반대 방향 조회에 `UNION` 이 필요해진다.

### 상위 N 상한

**`source_keyword_id` 기준 `relation_score` 상위 N 개만 저장한다.**

```
행 수 = 승격 키워드 수 × N
```

`period` 가 없으므로 [00 §7](00-overview.md) 의 마크다운 제안본이 걱정하던 "기간 3벌 × 양방향 = 쌍당 6행" 문제는 없다. 그래도 상한은 둔다 — 상한이 없으면 키워드 수의 제곱으로 자란다.

N 의 근거는 **실제 노출량**이다. 상세 화면이 연관 키워드를 한 화면에 보여주므로 몇 페이지 분량이면 충분하고, 그 이상은 저장해도 아무도 보지 않는다.

방향별로 자르므로 **비대칭이 생긴다.** `b` 가 `a` 의 상위 N 에 있어도 `a` 가 `b` 의 상위 N 에는 없을 수 있다. 이건 정상이다. 흔한 키워드의 연관 목록에 희귀 키워드가 들어가지 않는 것이 오히려 맞다.

### 자기 자신 제외

`source == target` 행은 계산 단계에서 먼저 거른다. 다이어그램에 `CHECK` 가 표시돼 있지 않으므로 **DB 가 막아주지 않을 수 있다.** 자기 자신이 연관 키워드 1위로 나오는 화면은 명백한 버그로 보인다.

## 6. 동의어와 연관어의 구분선

두 키워드가 관련 있다는 신호는 여러 갈래인데, 그중 어느 것이 "같음"이고 어느 것이 "함께 나옴"인지가 이 묶음에서 가장 헷갈리는 지점이다.

**핵심 관찰: 동의어는 같은 문서에 함께 나오지 않는다.** 한 글쓴이는 `MCP` 든 `Model Context Protocol` 이든 하나를 골라 쓴다. 반면 연관어는 함께 나온다 — 그게 연관어의 정의다.

| | NPMI | 임베딩 유사도 | 판정 | 처리 |
| --- | --- | --- | --- | --- |
| A | 높음 | 높음 | **연관어** | 이 문서. `keyword_relations` |
| B | **낮음** | **높음** | **동의어 후보** | [05 §4](05-keyword-registry-spec.md) 검수 큐 |
| C | 높음 | 낮음 | 연관어 (문맥적) | 이 문서 |
| D | 낮음 | 낮음 | 무관 | 버린다 |

**B 를 이 문서에서 저장하지 않는다.** 동의어일 가능성이 있는 쌍을 연관 키워드로 보여주면 사용자에게 같은 것이 두 번 나온다. `AI Agent` 의 연관 키워드 1위가 `AI 에이전트` 인 화면은 버그로 보인다.

**단, B 는 검수 큐로 보내되 병합되기 전까지는 연관 목록에서도 뺀다.** 검수가 밀려 있어도 화면 품질이 유지된다.

## 7. 재계산

매 실행이 덮어쓴다. 이전 점수를 이월하는 컬럼이 없으므로 [07 §6](07-metrics-and-ranking-spec.md) 의 "같은 날 재실행 오염" 문제가 여기에는 **없다.** 몇 번을 돌려도 결과가 같다.

다만 상위 N 으로 자르기 때문에 **단순 upsert 로는 안 된다.**

```sql
BEGIN;
DELETE FROM keyword_relations
 WHERE source_keyword_id IN (SELECT DISTINCT source_keyword_id FROM pl_stage_relations);
INSERT INTO keyword_relations (...) SELECT ... FROM pl_stage_relations;
COMMIT;
```

**upsert 로는 "이번에 상위 N 에서 밀려난 행"을 지울 수 없다.** 그러면 오래된 연관이 영원히 남아, 시간이 지날수록 목록이 과거 조합으로 채워진다.

이번에 계산된 `source_keyword_id` 만 지운다. 전체를 지우면 계산 대상이 아니었던 키워드의 연관까지 사라진다 — 문서가 없어 이번 배치에 안 잡힌 키워드가 그렇다.

한 트랜잭션 안에서 한다. 나누면 그 사이에 조회한 사용자가 빈 목록을 본다.
