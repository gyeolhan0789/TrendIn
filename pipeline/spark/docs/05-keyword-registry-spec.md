# 05 — 키워드 레지스트리

`extract` Job 의 후반부. [04](04-keyword-extraction-spec.md) 가 넓게 뽑은 후보를 **정규화하고, 같은 것끼리 통합하고, 승격한다.** 04 가 재현율을 맡았다면 이 문서는 정밀도를 맡는다.

승격된 것만 `keywords` 에 들어가고, 그때부터 사용자에게 보인다. **한 번 들어가면 사실상 되돌릴 수 없으므로** ([§1](#1-절대-제약--키워드를-삭제하지-않는다)) 이 관문이 이 묶음에서 가장 보수적인 지점이다.

## 1. 절대 제약 — 키워드를 삭제하지 않는다

`keywords` 행 하나에 네 가지가 매달려 있다.

| 참조하는 곳 | 잃는 것 |
| --- | --- |
| `member_interest_keywords.keyword_id` | **사용자가 등록한 관심 키워드** |
| `trends.keyword_id` | 트렌드와 그에 딸린 모든 지표 |
| `keyword_contents.keyword_id` | 관련 콘텐츠 연결 |
| `keyword_relations.source/target_keyword_id` | 연관 관계 |

**FK 의 `ON DELETE` 동작이 다이어그램에 표시돼 있지 않다.** 어느 쪽이든 결과가 나쁘다.

| 정책 | 결과 |
| --- | --- |
| `RESTRICT` (기본값) | 참조가 하나라도 있으면 **삭제가 실패한다.** 배치가 죽는다 |
| `CASCADE` | 사용자의 관심 키워드가 **말없이 사라진다** |
| `SET NULL` | 관심 키워드 행이 가리키는 대상을 잃는다 |

셋 다 받아들일 수 없으므로 **삭제하지 않는다.** 실제 정책 확인은 [00 §7](00-overview.md) 14번(FK `ON DELETE` 정책)이지만, 확인 결과와 무관하게 이 규칙은 유지한다.

### 그래서 병합은 승격 **전**에만 한다

`keywords` 에는 병합 상태를 표현할 컬럼이 없다. `merged_into_id` 도 `status` 도 없고 `normalized_name` 뿐이다. 그러니 **파이프라인 내부에서 통합을 끝낸 다음, 대표 하나만 `keywords` 에 넣는다.**

```
후보 풀(내부)  →  통합  →  승격 심사  →  keywords INSERT
                                          ↑ 여기부터는 되돌릴 수 없다
```

### 승격 후 병합이 필요해지면

**MVP 에서는 하지 않는다.** 필요해지면 백엔드와 함께 아래 순서로 수동 진행한다.

1. 흡수될 키워드를 참조하는 `member_interest_keywords` 를 대표로 옮기고, 같은 회원에게 중복이 생긴 행을 정리
2. `trends`, `keyword_contents`, `keyword_relations` 를 대표로 이관
3. 그다음 삭제

2번에서 `trends.keyword_id` 에 **UK 가 걸려 있다는 점**을 주의한다. 두 키워드가 모두 트렌드였다면 대표로 옮기는 순간 UK 위반이 난다. 흡수되는 쪽의 `trends` 행과 그 `trend_metrics` 를 먼저 처리해야 하는데, 그건 지표 이력을 버리는 것이라 간단하지 않다.

**잘못 승격된 키워드는 남는다.** 이게 이 설계의 비용이다. 완화책은 승격 문턱을 높이는 것([§5](#5-승격))과, `keywords` 에 있는 것과 트렌드로 노출되는 것을 분리하는 것이다 — `trends` 행을 만들지 않으면 목록·상세에 나오지 않고 키워드 검색에만 걸린다.

## 2. 층 1 — 결정적 규칙

증거 없이 항상 적용한다. 틀릴 여지가 거의 없는 것만 여기 둔다.

| 규칙 | 예 |
| --- | --- |
| NFKC 정규화 | 전각 → 반각 |
| 대소문자 접기 (비교키만) | `MCP` = `mcp` |
| 하이픈·언더스코어·연속공백 → 단일 공백 | `multi-agent` = `multi agent` = `multi_agent` |
| 앞뒤 구두점 제거 | `React.` → `React` |
| 소유격 제거 | `React's` → `React` |

대부분 [04 §4](04-keyword-extraction-spec.md) 의 비교키 생성에서 이미 적용된다. 이 표는 그 규칙의 정의 위치다.

### 복수형은 조건부로만

`-s`/`-es` 제거는 과교정이 잦다 (`CSS`→`CS`, `glasses`→`glasse`). 그래서 **양쪽 표기가 모두 코퍼스에 존재하고, 한쪽 DF 가 다른 쪽을 압도할 때만** 접는다. 근거 없이 규칙으로 밀지 않는다.

## 3. 층 2 — 통계 증거로 병합

증거가 있으면 자동 병합한다. 증거는 세 종류다.

### 약어 ↔ 전개형 (가장 강한 증거)

[04 §3](04-keyword-extraction-spec.md) 이 `Model Context Protocol (MCP)` 패턴을 쌍으로 기록한다. **글쓴이가 직접 "이 둘은 같다"고 선언한 것**이라 다른 어떤 신호보다 강하다.

| 조건 | |
| --- | --- |
| 괄호 패턴이 서로 다른 문서 N건 이상에서 관측 | 한 사람의 오기가 아님 |
| 약어의 각 글자가 전개형 단어들의 첫 글자와 대응 | `MCP` ↔ `Model Context Protocol` ✓ |
| 서로 다른 소스 2곳 이상 | 한 커뮤니티의 관용이 아님 |

대표 표기는 **빈도가 높은 쪽**을 고른다. 대개 약어가 이긴다.

### 표기 변형 흡수 (오타)

편집 거리가 1~2 이고 한쪽 DF 가 다른 쪽을 크게 압도하면, 적은 쪽을 오타로 보고 흡수한다.

**짧은 문자열에는 적용하지 않는다.** 4자 이하에서 편집 거리 1은 완전히 다른 단어인 경우가 흔하다 (`Vue` ↔ `Sue`, `Go` ↔ ` Go`).

### 대체 가능성

같은 것을 가리키는 두 표기는 **한 문서 안에 함께 나오지 않는 경향**이 있다. 한 글쓴이는 둘 중 하나만 쓰기 때문이다. 반대로 연관어는 함께 나온다.

| 신호 | 동의어 | 연관어 |
| --- | --- | --- |
| 동시출현 (NPMI) | **낮다** | **높다** |
| 문맥 분포 유사도 | 높다 | 중간 |
| 임베딩 유사도 | 높다 | 높다 |

**이 표가 05 와 [06](06-related-keyword-spec.md) 을 잇는 지점이다.** 임베딩 유사도만으로는 둘을 구분할 수 없고, NPMI 를 함께 봐야 갈린다. NPMI 계산은 06 이 하고, 05 는 그 값을 읽어 판정에 쓴다.

이 신호는 **자동 병합에 쓰지 않고 검수 큐로 보낸다.** 상관이지 증거가 아니기 때문이다.

## 4. 층 3 — 임베딩은 후보만 만든다

문장 임베딩으로 표기 벡터를 만들고 코사인 유사도를 본다. 계산 방식은 [01 §5](01-architecture.md).

### 자동 병합을 금지하는 이유

**임베딩은 "관련 있음"과 "같음"을 구분하지 못한다.**

`React` 와 `Vue` 는 유사도가 매우 높다. 같은 문맥에서 같은 자리에 쓰이니 당연하다. 하지만 병합하면 서비스가 망가진다. `Kubernetes`/`Docker`, `Neo Vintage`/`Archive Fashion` 도 마찬가지다.

그리고 [§1](#1-절대-제약--키워드를-삭제하지-않는다) 때문에 **잘못 병합하면 되돌리기가 거의 불가능하다.** 자동화의 이득보다 사고 비용이 훨씬 크다.

### 그래서 하는 일

| 상황 | 처리 |
| --- | --- |
| 유사도 높음 + 층 2 증거 있음 | 층 2 규칙대로 자동 병합. 임베딩은 확인 역할 |
| 유사도 높음 + NPMI 낮음 | **검수 큐**로. 동의어 후보 |
| 유사도 높음 + NPMI 높음 | 병합하지 않는다. 연관어다 → [06](06-related-keyword-spec.md) |
| 유사도 낮음 | 무관 |

### 한국어 ↔ 영어

`에이전트` ↔ `Agent`, `쿠버네티스` ↔ `Kubernetes` 는 결정적 규칙으로 못 잡는다. 음차 표기 규칙을 만들 수도 있지만 예외가 너무 많다.

**다국어 임베딩 모델이면 잡히지만, 자동 병합하지 않고 검수 큐로 보낸다.** 위와 같은 이유다. 음차 쌍은 특히 위험한데, `밴드`(band/bend/band-aid)처럼 하나의 한글 표기가 여러 영어 단어에 대응하는 경우가 흔하다.

## 5. 승격

후보가 `keywords` 로 들어가는 관문이다. 모든 조건을 **함께** 만족해야 한다.

| 조건 | 무엇을 막나 |
| --- | --- |
| 누적 문서 수 ≥ 하한 | 일회성 |
| 관측 일수 ≥ 하한 (연속일 필요 없음) | 하루 반짝하는 이벤트·스팸 |
| 서로 다른 **소스** ≥ 2 | 한 커뮤니티의 은어 |
| 서로 다른 **저자** ≥ 하한 | **봇·자기홍보** |
| `dup_of` 가 있는 문서를 제외한 기준 | 크로스포스트로 부풀린 것 |
| 대표 표기 비율 ≥ 하한 | 표기가 안 잡힌 것 |

**저자 다양성이 가장 중요하다.** 자동 발견 방식이 실패하는 대표적 형태가 "한 사람이 자기 프로젝트 이름을 30개 글에 뿌린 것"이 신규 트렌드로 올라오는 것이다. 문서 수만 보면 통과하지만 저자 수를 보면 1이다.

**소스 다양성은 그다음이다.** 특정 서브레딧에서만 쓰는 밈이 트렌드로 올라오는 것을 막는다.

승격은 되돌릴 수 없으므로 **의심스러우면 보류한다.** 보류된 후보는 내부에 남아 다음 배치에서 다시 심사된다. 조건을 넘으면 그때 승격한다. 하루 늦게 잡히는 것은 문제가 아니지만, 잘못 승격된 것은 영구히 남는다.

### `keywords` 적재

| 컬럼 | 값 |
| --- | --- |
| `domain` | enum 상수명. `development` → `DEVELOP`, `fashion` → `FASHION` ([01 §6](01-architecture.md)) |
| `name` | 대표 표기 (`surface`) |
| `normalized_name` | 비교키 ([04 §4](04-keyword-extraction-spec.md)) |
| `first_seen_at` | **최초 관측 시각.** 승격 시각이 아니다 |

**`first_seen_at` 이 승격 시각이 아니라는 점이 중요하다.** 이 값은 [07 §5](07-metrics-and-ranking-spec.md) 의 `NEW` 판정 근거다. 승격 시각을 넣으면 며칠간 관측되다 승격된 키워드가 승격일에 `NEW` 로 떠서, "새로 뜨는 트렌드"가 실제보다 늦게 나타난다.

값은 내부 후보 테이블(`pl_candidate`)이 갖고 있다 ([08 §3](08-storage-schema.md)). 승격 시점에 그 값을 그대로 옮긴다. **이미 있는 행이면 갱신하지 않는다** — 최초는 한 번뿐이다.

```sql
INSERT INTO keywords (domain, name, normalized_name, first_seen_at)
SELECT domain, name, normalized_name, first_seen_at FROM pl_stage_keywords
ON CONFLICT (domain, normalized_name) DO UPDATE SET
  name = EXCLUDED.name          -- 대표 표기는 바뀔 수 있다
                                -- first_seen_at 은 건드리지 않는다
RETURNING id, domain, normalized_name;
```

`RETURNING` 으로 `id` 를 받아 내부 매핑 테이블에 둔다. `keyword_contents` 가 `keyword_id` 를 요구하기 때문이며, [03 §8](03-normalization-spec.md) 의 `contents.id` 처리와 같은 이유로 `DO NOTHING` 이 아니라 `DO UPDATE` 를 쓴다.

**`name` 을 갱신하는 이유** — 대표 표기는 빈도로 정하므로 코퍼스가 자라면 바뀔 수 있다 (`ai agent` → `AI Agent`). 비교키가 같으면 같은 키워드이므로 표기만 고친다.

### ⚠️ `(domain, normalized_name)` UNIQUE 가 선행 조건이다

**합의됐지만 아직 적용되지 않았다.** 위 SQL 은 이 제약이 실제로 있어야만 동작한다 — `ON CONFLICT` 는 유니크 제약을 참조하기 때문이다.

제약 없이 그냥 INSERT 하면 **매 배치마다 같은 키워드가 새 행으로 쌓인다.** `Kubernetes` 가 100개 행이 되고, 언급량이 100 갈래로 흩어지고, 사용자가 관심 키워드로 등록한 행과 트렌드가 붙은 행이 서로 다른 `id` 가 된다.

**나중에 붙일 수 없다는 점이 핵심이다.** 중복이 쌓인 뒤에 UNIQUE 를 걸려면 먼저 청소해야 하는데, `keyword_contents` 는 3번 행을, `member_interest_keywords` 는 47번 행을, `trends` 는 88번 행을 가리키고 있는 상태에서 무엇이 진짜인지 판정할 수 없다. DB 가 초기 버전이라 대부분은 구현하면서 고쳐도 되지만([08 §6](08-storage-schema.md)) **이건 그 예외다.**

**애플리케이션에서 SELECT 후 INSERT 로 우회하지 않는다.** 경쟁 조건이 있고, 무엇보다 제약이 없으면 한 번 어긋난 데이터를 나중에 정리할 수 없다.

`normalized_name` 단독이 아니라 `domain` 과의 복합이어야 한다. 단독이면 개발의 `모델` 과 패션의 `모델` 이 충돌해 한쪽이 들어가지 못한다 ([§6](#6-동형이의어)).

## 6. 동형이의어

같은 표기가 다른 것을 가리키는 경우다.

**도메인이 다르면 분리된다.** `(domain, normalized_name)` 복합 UNIQUE 덕분에 개발의 `모델` 과 패션의 `모델` 은 별개 행이 된다 ([§5](#5-승격)). 단독 UNIQUE 로 걸면 이 분리가 깨진다.

**같은 도메인 안의 동형이의어는 구분하지 못한다.** 개발 도메인의 `Swift`(언어)와 `Swift`(결제망) 같은 경우다. 문맥 클러스터링으로 나눌 수는 있지만, 판정이 불안정하고 `keywords` 스키마에 의미 구분을 표현할 자리가 없다.

**이 묶음은 이걸 해결하지 않는다.** 한계로 인정하고 문서에 남긴다. 실제로 문제가 되는 사례가 관측되면 그때 다룬다.

## 7. 검수 큐

층 2·3 이 자동 판정하지 못한 것들이 모인다. 내부 테이블이며 서비스 스키마가 아니다.

| 항목 | |
| --- | --- |
| 후보 쌍 | 대표 후보, 흡수 후보 |
| 근거 | 임베딩 유사도, NPMI, 문맥 유사도, 층 2 신호 유무 |
| 상태 | `PENDING` / `APPROVED` / `REJECTED` |
| 우선순위 | 두 후보의 문서 수 합 — **영향이 큰 것부터** |

**`REJECTED` 를 반드시 기록한다.** 기록하지 않으면 같은 쌍이 매 배치마다 다시 큐에 올라와 검수자를 지치게 한다.

승인된 병합은 다음 `extract` 실행부터 적용된다. **이미 승격된 키워드끼리의 병합 승인은 [§1](#1-절대-제약--키워드를-삭제하지-않는다) 의 사후 병합이라 자동 적용하지 않는다.** 큐에 남겨두고 백엔드와 함께 처리한다.

### 검수를 안 하면 어떻게 되나

큐가 비어 있어도 파이프라인은 정상 동작한다. 층 1·2 자동 병합만 적용되고, 층 3 후보는 병합되지 않은 채 각각 별개 키워드로 남는다. **의미적 동의어가 갈라져 있는 상태**이고, 그건 잘못 합쳐진 것보다 훨씬 낫다.

검수는 품질 개선 작업이지 파이프라인의 필수 경로가 아니다. 이 성질을 유지하는 것이 중요하다 — 사람 손을 파이프라인의 의존성으로 만들면 아무도 안 볼 때 파이프라인이 멈춘다.

## 8. 병합 이력과 재계산

병합할 때마다 내부 이력 테이블에 남긴다.

| 남기는 것 | 왜 |
| --- | --- |
| 대표 후보, 흡수 후보 | 무엇이 합쳐졌나 |
| 근거 (층 번호, 신호 값) | 나중에 판단을 검토하려면 |
| 적용 시점 | **통계 재계산 범위 판단** |

**병합은 과거 통계를 바꾼다.** `MCP` 와 `Model Context Protocol` 을 오늘 합치면, 어제까지 따로 세던 언급량이 하나로 합쳐져야 그래프가 이어진다. 합치지 않으면 병합 시점에 계단이 생기고, 사용자에게는 그게 실제 급증으로 보인다.

재계산 범위는 두 후보가 관측된 전 구간이다. 실무적으로는 최근 N일로 자르고, 그보다 오래된 구간의 계단은 감수한다. 구체적인 범위 정책은 [07 §3](07-metrics-and-ranking-spec.md).
