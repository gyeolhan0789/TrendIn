# 05 — 키워드 레지스트리

`extract` Job 의 후반부. [04](04-keyword-extraction-spec.md) 가 넓게 뽑은 후보를 **정규화하고, 같은 것끼리 통합하고, 승격한다.** 04 가 재현율을 맡았다면 이 문서는 정밀도를 맡는다.

승격된 것만 `keywords` 에 들어가고, 그때부터 사용자에게 보인다. **한 번 들어가면 사실상 되돌릴 수 없으므로** ([§1](#1-절대-제약--키워드를-삭제하지-않는다)) 이 관문이 이 묶음에서 가장 보수적인 지점이다.

### 구현 위치 (2026-09-09)

| 절 | 코드 |
| --- | --- |
| [§2](#2-층-1--결정적-규칙) 층 1 | 대부분 `extract/keys.py` (비교키 생성). 조건부 복수형만 `registry/normalize.py` |
| [§3](#3-층-2--통계-증거로-병합) 층 2 | `registry/merge.py` — 약어·표기 변형 판정. 대표 선정은 `registry/alias.py` |
| [§4](#4-층-3--임베딩은-후보만-만든다) 층 3 | `registry/embedding.py` — **모델은 설정이고 기본이 `null` 이다** (아래) |
| [§5](#5-승격) 승격 | `registry/promote.py`(판정) · `io/keywords.py`(적재) |
| [§7](#7-검수-큐) 검수 큐 | `registry/review.py` · `pl_review_queue` |
| [§8](#8-병합-이력과-재계산) 이력·재계산 | `io/keywords.ALIAS_MERGE_SQL` · `io/candidates.DAILY_STAT_RECOUNT` |

단계 순서는 `registry/batch.py` 에 있다. **Spark 를 쓰지 않는다** — [04](04-keyword-extraction-spec.md) 는 문서 × 후보 규모였지만 이 문서의 입력은 이미 접힌 내부 테이블이라, 집계는 PostgreSQL 이 인덱스로 하고 판정은 순수 파이썬이 후보 수천~수만 개에 대해 한다.

## 1. 절대 제약 — 키워드를 삭제하지 않는다

`keywords` 행 하나에 여섯 가지가 딸려 있다.

| 참조하는 곳 | 잃는 것 |
| --- | --- |
| `member_interest_keywords.keyword_id` | **사용자가 등록한 관심 키워드** |
| `trends.keyword_id` | 트렌드와 그 설명 텍스트 |
| `keyword_metrics.keyword_id` | 기간별 지표 |
| `keyword_metric_history.keyword_id` | **언급량 시계열 전체** |
| `keyword_contents.keyword_id` | 관련 콘텐츠 연결 |
| `keyword_relations.source/target_keyword_id` | 연관 관계 |

v2 에서 지표가 `trends` 밑에서 `keywords` 밑으로 올라왔으므로([erd](erd/erd-00-current.md)) 이 목록이 둘 늘었다. **키워드 하나를 지우면 그 키워드의 그래프가 통째로 사라진다.**

**FK 의 `ON DELETE` 동작이 다이어그램에 표시돼 있지 않다.** 어느 쪽이든 결과가 나쁘다.

| 정책 | 결과 |
| --- | --- |
| `RESTRICT` (기본값) | 참조가 하나라도 있으면 **삭제가 실패한다.** 배치가 죽는다 |
| `CASCADE` | 사용자의 관심 키워드가 **말없이 사라진다** |
| `SET NULL` | 관심 키워드 행이 가리키는 대상을 잃는다 |

셋 다 받아들일 수 없으므로 **삭제하지 않는다.** 실제 정책 확인은 [00 §7](00-overview.md) 14번(FK `ON DELETE` 정책)이지만, 확인 결과와 무관하게 이 규칙은 유지한다.

### 그래서 병합은 승격 **전**에만 한다

`keywords` 에는 병합 상태를 표현할 컬럼이 없다. `merged_into_id` 도 `status` 도 없고 `normalized_name` 뿐이다. 그러니 **파이프라인 내부에서 통합을 끝낸 다음, 대표 하나만 `keywords` 에 넣는다.**

```
후보 풀(내부)  →  통합  →  승격 심사  →  keywords INSERT
                                          ↑ 여기부터는 되돌릴 수 없다
```

### 승격 후 병합이 필요해지면

**MVP 에서는 하지 않는다.** 필요해지면 백엔드와 함께 아래 순서로 수동 진행한다.

1. 흡수될 키워드를 참조하는 `member_interest_keywords` 를 대표로 옮기고, 같은 회원에게 중복이 생긴 행을 정리
2. `trends`, `keyword_contents`, `keyword_relations`, `keyword_metrics`, `keyword_metric_history` 를 대표로 이관
3. 그다음 삭제

2번에 **유일성 충돌이 세 군데 있다.**

| 테이블 | 충돌 | 처리 |
| --- | --- | --- |
| `trends` | `keyword_id` UK — 둘 다 트렌드였으면 위반 | 흡수되는 쪽의 행을 버린다. `description`·`summary`·`reason` 이 함께 사라진다 |
| `keyword_metrics` | `(keyword_id, period)` — 같은 기간 행이 둘 | **버리지 않고 다음 회차 재계산에 맡긴다.** 병합이 반영된 원자료에서 값이 다시 나온다 |
| `keyword_metric_history` | `(keyword_id, bucket_start)` — 같은 날짜 행이 둘 | 같음. 단 재계산 구간 W 밖의 버킷은 값이 합쳐지지 않고 계단이 남는다 ([07 §2](07-metrics-and-ranking-spec.md)) |

**지표 쪽은 이관보다 재계산이 맞다.** 두 키워드의 언급량을 행 단위로 더하면 같은 문서를 두 번 세게 된다 — 병합된 두 표기가 같은 문서에 함께 나온 경우다. 원자료에서 다시 세면 그 문서가 1로 셈된다.

**잘못 승격된 키워드는 남는다.** 이게 이 설계의 비용이다. 완화책은 승격 문턱을 높이는 것([§5](#5-승격))과, `keywords` 에 있는 것과 트렌드로 노출되는 것을 분리하는 것이다 — `trends` 행을 만들지 않으면 목록·상세에 나오지 않고 키워드 검색에만 걸린다.

## 2. 층 1 — 결정적 규칙

증거 없이 항상 적용한다. 틀릴 여지가 거의 없는 것만 여기 둔다.

| 규칙 | 예 |
| --- | --- |
| NFKC 정규화 | 전각 → 반각 |
| 대소문자 접기 (비교키만) | `MCP` = `mcp` |
| 하이픈·언더스코어·연속공백 → 단일 공백 | `multi-agent` = `multi agent` = `multi_agent` |
| 앞뒤 구두점 제거 | `React.` → `React` |
| 소유격 제거 | `React's` → `React` |

대부분 [04 §4](04-keyword-extraction-spec.md) 의 비교키 생성에서 이미 적용된다. 이 표는 그 규칙의 정의 위치다.

### 복수형은 조건부로만

`-s`/`-es` 제거는 과교정이 잦다 (`CSS`→`CS`, `glasses`→`glasse`). 그래서 **양쪽 표기가 모두 코퍼스에 존재하고, 한쪽 DF 가 다른 쪽을 압도할 때만** 접는다. 근거 없이 규칙으로 밀지 않는다.

**한국어 복수형(`-들`)은 여기 오지 않는다.** [04 §2](04-keyword-extraction-spec.md) 의 형태소 분석기가 `아이템들` 을 `아이템`(NNG) + `들`(XSN) 로 갈라 표기에서 빼기 때문이다 (표기 정책 `prefixed`). **그 정책을 `word` 로 바꾸면 이 층으로 넘어온다** — 2026-09-09 실측에서 `word` 는 복수형 43쌍 · `-적` 파생형 66쌍을 어근과 따로 냈고, `사람들`(35문서) 대 `사람`(71) 처럼 **양쪽이 다 흔한** 쌍은 아래 [§3](#3-층-2--통계-증거로-병합) 의 조건(DF 압도)을 만족하지 못해 **접히지 않는다.** 토큰화에서 접는 것이 여기서 접는 것보다 싸다는 판단이고, 그 판단의 근거가 이 절이다.

### 조사가 붙은 표기는 더 이상 오지 않는다 (2026-09-09)

원래 이 문서는 [04](04-keyword-extraction-spec.md) 가 `코트가` · `컬러의` 처럼 **조사가 붙은 표기**를 흘려보내고, 아래 [§3](#3-층-2--통계-증거로-병합) 의 표기 변형 흡수가 그것을 `코트` 로 접는 것을 전제했다. 04 가 규칙 기반 토큰화를 쓸 때는 그게 불가피했다.

**형태소 분석기로 갈아탄 뒤 그 전제가 없어졌다.** 조사는 후보의 재료가 아니라 경계이므로 비교키에 남지 않는다. 이 문서가 덜 일하게 됐다는 뜻이고, 남은 일은 **진짜 오타와 진짜 표기 변형**이다 — 그쪽이 이 층의 원래 목적이었다.

⚠️ 남은 예외 하나 — 분석기가 모르는 고유명사는 조사째 한 덩이가 된다 (`메종마르지엘라의`). 1차 방어는 사용자 사전(`conf/lexicon/userdict-{domain}.txt`)이고, 그것을 빠져나온 것이 이 층에 온다. 실측에서 선별 3,520행 중 12행 규모다.

## 3. 층 2 — 통계 증거로 병합

증거가 있으면 자동 병합한다. 증거는 세 종류다.

### 약어 ↔ 전개형 (가장 강한 증거)

[04 §3](04-keyword-extraction-spec.md) 이 `Model Context Protocol (MCP)` 패턴을 쌍으로 기록한다. **글쓴이가 직접 "이 둘은 같다"고 선언한 것**이라 다른 어떤 신호보다 강하다.

| 조건 | |
| --- | --- |
| 괄호 패턴이 서로 다른 문서 N건 이상에서 관측 | 한 사람의 오기가 아님 |
| 약어의 각 글자가 전개형 단어들의 첫 글자와 대응 | `MCP` ↔ `Model Context Protocol` ✓ |
| 서로 다른 소스 2곳 이상 | 한 커뮤니티의 관용이 아님 |

**⚠️ fashion 실데이터에서는 한 건도 발동하지 않았다** (2026-09-09). 관측 쌍 21개가 전부 한국어 전개형이라 초성 대응이 없고(`ASICS` ↔ `아식스`), 문서·소스도 각각 1이었다. **조건이 옳게 막은 것이지만, 이 경로가 실측으로 검증되지 않았다는 뜻이기도 하다** — dev 도메인(영문)이 붙어야 확인된다. 곁가지로 [04 §3](04-keyword-extraction-spec.md) 의 전개형 캡처가 앞 문맥을 과하게 먹는 것이 보였다 (`ASICS` 의 전개형이 `이라는 주제로 글로벌 스포츠 브랜드 아식스`). 초성 대응이 전부 막아 주고 있어 지금 해가 없지만 [10] 후속에 올렸다.

대표 표기는 **빈도가 높은 쪽**을 고른다. 대개 약어가 우선한다.

### 표기 변형 흡수 (오타)

편집 거리가 1~2 이고 한쪽 DF 가 다른 쪽을 크게 압도하면, 적은 쪽을 오타로 보고 흡수한다.

**짧은 문자열에는 적용하지 않는다.** 4자 이하에서 편집 거리 1은 완전히 다른 단어인 경우가 흔하다 (`Vue` ↔ `Sue`, `Go` ↔ ` Go`).

#### ⚠️ 한국어는 자모로 센다 (2026-09-09)

**편집 거리를 음절 단위로 재면 한국어에서 오타 신호가 되지 않는다.** 라틴 문자는 한 글자가 한 음소지만 한글은 한 음절이 음소 두세 개를 담아, **완전히 다른 낱말이 거리 1 로 보인다.**

| 쌍 | 음절 거리 | 자모 거리 |
| --- | --- | --- |
| `데님 셔츠` ↔ `데님 팬츠` (딴 것) | 1 | 3 |
| `가을 슈즈` ↔ `플랫 슈즈` (딴 것) | 2 | 7 |
| `플렛 슈즈` ↔ `플랫 슈즈` (오타) | 1 | 1 |

실데이터 리허설에서 음절 거리로 **41쌍이 자동 병합됐고 그 대부분이 위 첫 두 줄 같은 쌍이었다** — `데님 셔츠` 가 `데님 팬츠` 에 흡수되어 키워드로 사라졌다. 길이 하한으로는 막을 수 없다 (이미 5자를 넘는다).

**그래서 사전으로 개별 패치하지 않고 거리의 정의를 고쳤다.** NFD 로 분해한 뒤 센다 — 진짜 오타는 자모 하나가 틀리고 다른 낱말은 음절째 다르므로, 같은 문턱(1~2)이 한국어에서도 뜻을 갖는다. 라틴 문자는 NFD 가 건드리지 않아 동작이 그대로다. 구현은 `registry/merge.bounded_distance`.

**⚠️ 길이 하한은 여전히 필요하다.** `모델` ↔ `모텔` 은 자모 거리도 1 이다 — 그 쌍을 막는 것은 `variant.min_length` 다.

### 대체 가능성

같은 것을 가리키는 두 표기는 **한 문서 안에 함께 나오지 않는 경향**이 있다. 한 글쓴이는 둘 중 하나만 쓰기 때문이다. 반대로 연관어는 함께 나온다.

| 신호 | 동의어 | 연관어 |
| --- | --- | --- |
| 동시출현 (NPMI) | **낮다** | **높다** |
| 문맥 분포 유사도 | 높다 | 중간 |
| 임베딩 유사도 | 높다 | 높다 |

**이 표가 05 와 [06](06-related-keyword-spec.md) 을 잇는 지점이다.** 임베딩 유사도만으로는 둘을 구분할 수 없고, NPMI 를 함께 봐야 나뉜다. NPMI 계산은 06 이 하고, 05 는 그 값을 읽어 판별에 쓴다.

**⚠️ 그 값이 아직 없다** (2026-09-09). [06](06-related-keyword-spec.md) 은 [10 §1](10-delivery-plan.md) 이 **다음 에픽**으로 뺐으므로, 지금 층 3 은 NPMI 자리를 `NULL` 로 두고 유사도만 본다. 결과는 [§4](#4-층-3--임베딩은-후보만-만든다) 표의 둘째·셋째 줄이 갈리지 않는 것 — 연관어 쌍까지 검수 큐에 올라온다. **자동 병합은 여전히 하지 않으므로 위험하지 않고, 검수자가 지친다.** `pl_review_queue.npmi` 와 `extract.registry.review.npmi_ceiling` 자리를 비워 둔 채로 뒀고, 값이 생기면 판별이 그때 갈린다.

이 신호는 **자동 병합에 쓰지 않고 검수 큐로 보낸다.** 상관이지 증거가 아니기 때문이다.

## 4. 층 3 — 임베딩은 후보만 만든다

문장 임베딩으로 표기 벡터를 만들고 코사인 유사도를 본다. 계산 방식은 [01 §5](01-architecture.md).

### 자동 병합을 금지하는 이유

**임베딩은 "관련 있음"과 "같음"을 구분하지 못한다.**

`React` 와 `Vue` 는 유사도가 매우 높다. 같은 문맥에서 같은 자리에 쓰이니 당연하다. 하지만 병합하면 서비스가 망가진다. `Kubernetes`/`Docker`, `Neo Vintage`/`Archive Fashion` 도 마찬가지다.

그리고 [§1](#1-절대-제약--키워드를-삭제하지-않는다) 때문에 **잘못 병합하면 되돌리기가 거의 불가능하다.** 자동화의 이득보다 사고 비용이 훨씬 크다.

### 그래서 하는 일

| 상황 | 처리 |
| --- | --- |
| 유사도 높음 + 층 2 증거 있음 | 층 2 규칙대로 자동 병합. 임베딩은 확인 역할 |
| 유사도 높음 + NPMI 낮음 | **검수 큐**로. 동의어 후보 |
| 유사도 높음 + NPMI 높음 | 병합하지 않는다. 연관어다 → [06](06-related-keyword-spec.md) |
| 유사도 낮음 | 무관 |

### 모델은 설정이고 기본은 꺼져 있다 (2026-09-09)

`extract.registry.embedding.model` 이 `null` 이면 이 층이 아예 돌지 않는다. **배선·캐시·테스트는 있고 모델만 없다.**

| | |
| --- | --- |
| 왜 | 실제 모델(`sentence-transformers`)이 torch 를 끌고 와 이미지가 1 GB 이상 커진다. 그리고 위 NPMI 부재 때문에 지금 켜도 판별이 반쪽이다 |
| 무엇이 이미 있나 | 제공자 인터페이스 · 모듈 수준 lazy singleton · `pl_embedding_cache` 적재·조회 · 검수 큐 배선 |
| 어떻게 확인하나 | `model: hash` 로 두면 의존성 없이 배선이 돈다. **유사도에 의미는 없다** — 큐에 잡음이 쌓이므로 확인용이다 |
| 켤 때 | 의존성을 이미지에 넣고 `model` · `review.similarity_floor` 를 채운다. 코드는 안 바뀐다 |

**⚠️ `pandas_udf` 가 아니라 드라이버에서 배치로 돈다** ([01 §5](01-architecture.md) 는 `mapInPandas`·`pandas_udf` 를 적었다). 대상이 문서가 아니라 **사용자에게 보이게 될 표기**라 수백~수천이고, executor 로 흩으면 워커마다 모델을 한 번씩 올리는 비용이 계산보다 크다. 옮겨야 할 때 바뀌는 것은 `provider_for(spec)` 를 부르는 자리 하나이고, 그 성질(spec 은 picklable · 제공자는 아님)을 층 1 테스트가 지킨다.

### 한국어 ↔ 영어

`에이전트` ↔ `Agent`, `쿠버네티스` ↔ `Kubernetes` 는 결정적 규칙으로 못 잡는다. 음차 표기 규칙을 만들 수도 있지만 예외가 너무 많다.

**다국어 임베딩 모델이면 잡히지만, 자동 병합하지 않고 검수 큐로 보낸다.** 위와 같은 이유다. 음차 쌍은 특히 위험한데, `밴드`(band/bend/band-aid)처럼 하나의 한글 표기가 여러 영어 단어에 대응하는 경우가 흔하다.

## 5. 승격

후보가 `keywords` 로 들어가는 관문이다. 모든 조건을 **함께** 만족해야 한다.

| 조건 | 무엇을 막나 |
| --- | --- |
| 누적 문서 수 ≥ 하한 | 일회성 |
| 관측 일수 ≥ 하한 (연속일 필요 없음) | 하루 반짝하는 이벤트·스팸 |
| 서로 다른 **소스** ≥ 2 | 한 커뮤니티의 은어 |
| 서로 다른 **저자** ≥ 하한 | **봇·자기홍보** |
| `dup_of` 가 있는 문서를 제외한 기준 | 크로스포스트로 부풀린 것 |
| 대표 표기 비율 ≥ 하한 | 표기가 안 잡힌 것 |

**저자 다양성이 가장 중요하다.** 자동 발견 방식이 실패하는 대표적 형태가 "한 사람이 자기 프로젝트 이름을 30개 글에 뿌린 것"이 신규 트렌드로 올라오는 것이다. 문서 수만 보면 통과하지만 저자 수를 보면 1이다.

**여섯 조건은 가중합이 아니라 AND 다.** 조건마다 막으려는 것이 서로 달라 하나가 다른 하나를 보상할 수 없다 — 점수로 합치면 "문서가 아주 많으면 저자 하나라도 통과" 가 되고, 그게 바로 위 실패 형태다. 경계는 통과 쪽이고(`≥ 하한`), 여러 조건에 걸리면 **사유는 하나만 남긴다** — 그 값이 `pl_batch_stat` 의 차원이라 여러 개를 남기면 "무엇이 가장 많이 막는가" 의 합이 후보 수를 넘는다.

### 대표 표기 비율은 병합 그룹 기준으로 잰다 (2026-09-09)

여섯째 조건의 원문은 표기 분포를 뜻하지만 **문서별 원표기가 저장되지 않는다** — [04](04-keyword-extraction-spec.md) 가 코퍼스 대표 표기 하나로 접어 `pl_document_candidate` 에 넣기 때문이다. 그래서 **그룹 전체 문서 수 중 대표 후보의 몫**으로 잰다.

| | |
| --- | --- |
| 분모 | 대표와 그 별칭 전부의 문서 **합집합** 크기 (`GROUP_OBSERVATION_SQL`) |
| 분자 | 대표 후보 하나의 문서 수 |
| 별칭이 없는 후보 | 비율이 1.0 이라 이 조건이 걸리지 않는다 |

표기가 갈려 별칭이 대표만큼 흔한 그룹의 승격을 미루는 것이고, 원래 조건이 막으려던 "표기가 안 잡힌 것" 과 같은 것을 막는다. **문서별 원표기를 남기려면 [04] 의 스키마가 바뀌고 재추출이 따르므로** 그 값이 실제로 필요해질 때 다루는 것이 맞다.

**소스 다양성은 그다음이다.** 특정 서브레딧에서만 쓰는 밈이 트렌드로 올라오는 것을 막는다.

승격은 되돌릴 수 없으므로 **의심스러우면 보류한다.** 보류된 후보는 내부에 남아 다음 배치에서 다시 심사된다. 조건을 넘으면 그때 승격한다. 하루 늦게 잡히는 것은 문제가 아니지만, 잘못 승격된 것은 영구히 남는다.

### `keywords` 적재

| 컬럼 | 값 |
| --- | --- |
| `domain` | enum 상수명. 이벤트 슬러그 `dev` → `DEVELOP`, `fashion` → `FASHION` ([01 §6](01-architecture.md)) |
| `name` | 대표 표기 (`surface`) |
| `normalized_name` | 비교키 ([04 §4](04-keyword-extraction-spec.md)) |

컬럼이 셋뿐이다. **v2 에서 `first_seen_at` 이 없어졌다** ([erd](erd/erd-00-current.md)).

```sql
INSERT INTO keywords (domain, name, normalized_name)
SELECT domain, name, normalized_name FROM pl_stage_keywords
ON CONFLICT (domain, normalized_name) DO UPDATE SET
  name = EXCLUDED.name          -- 대표 표기는 바뀔 수 있다
RETURNING id, domain, normalized_name;
```

### `first_seen_at` 이 없어진 것이 승격 설계를 바꾸지 않는다

그 컬럼은 `NEW` 판별의 근거였고, 승격 시점에 `pl_candidate` 의 최초 관측 시각을 옮겨 담는 자리였다. 지금 `NEW` 는 **언급량 이력으로 판별한다** ([07 §6](07-metrics-and-ranking-spec.md)).

| | v1 | v2 |
| --- | --- | --- |
| `NEW` 의 근거 | `keywords.first_seen_at` | `pl_keyword_daily_stat` 의 직전 구간 언급량 |
| 최초 관측 시각을 어디에 두나 | 승격 때 서비스 테이블로 옮긴다 | **`pl_candidate` 에만 둔다.** 옮기지 않는다 |

**서비스 테이블로 옮기지 않는 편이 낫다.** 그 값은 승격 심사와 운영 조회에 쓰는 파이프라인 내부 정보인데, 서비스 테이블에 있으면 백엔드가 스키마를 다시 만들 때 함께 사라진다 ([08 §6](08-storage-schema.md)). 지금은 파이프라인이 소유한 테이블에만 있으므로 그 사고에 영향을 받지 않는다.

`RETURNING` 으로 `id` 를 받아 내부 매핑 테이블에 둔다. `keyword_contents` 가 `keyword_id` 를 요구하기 때문이며, [03 §8](03-normalization-spec.md) 의 `contents.id` 처리와 같은 이유로 `DO NOTHING` 이 아니라 `DO UPDATE` 를 쓴다.

**`name` 을 갱신하는 이유** — 대표 표기는 빈도로 정하므로 코퍼스가 자라면 바뀔 수 있다 (`ai agent` → `AI Agent`). 비교키가 같으면 같은 키워드이므로 표기만 고친다.

### ⚠️ `(domain, normalized_name)` UNIQUE 가 선행 조건이다

**합의됐지만 아직 적용되지 않았다.** 위 SQL 은 이 제약이 실제로 있어야만 동작한다 — `ON CONFLICT` 는 유니크 제약을 참조하기 때문이다.

**2026-09-09 확인 — 없다.** `Keyword.java` 에 `uniqueConstraints` 가 없다 ([08 §2](08-storage-schema.md)). 그래서 `io/keywords.KeywordSink.unique_constraint_ready()` 가 `pg_index` 를 조회해 컬럼 집합이 정확히 `(domain, normalized_name)` 인 유니크 인덱스를 찾고, **없으면 승격 단계만 건너뛴다.** 병합 · 검수 큐 · 이력은 전부 `pl_` 이라 그대로 돈다. 기본은 fail-closed 이고(`extract.registry.required`, base.yaml `true`) 로컬만 `false` 이며, 그 밖에서는 `--allow-missing-keyword-unique` 로 명시해야 풀린다 — `ingest.contents.required` 와 같은 형태다. 조용히 건너뛰지 않는 이유도 같다: 증상이 "트렌드가 하나도 안 나온다" 로 화면에서야 나타난다.

제약 없이 그냥 INSERT 하면 **매 배치마다 같은 키워드가 새 행으로 쌓인다.** `Kubernetes` 가 100개 행이 되고, 언급량이 100 갈래로 흩어지고, 사용자가 관심 키워드로 등록한 행과 트렌드가 붙은 행이 서로 다른 `id` 가 된다.

**나중에 붙일 수 없다는 점이 핵심이다.** 중복이 쌓인 뒤에 UNIQUE 를 걸려면 먼저 청소해야 하는데, `keyword_contents` 는 3번 행을, `member_interest_keywords` 는 47번 행을, `trends` 는 88번 행을 가리키고 있는 상태에서 무엇이 진짜인지 판별할 수 없다. DB 가 초기 버전이라 대부분은 구현하면서 고쳐도 되지만([08 §6](08-storage-schema.md)) **이건 그 예외다.**

**애플리케이션에서 SELECT 후 INSERT 로 우회하지 않는다.** 경쟁 조건이 있고, 무엇보다 제약이 없으면 한 번 어긋난 데이터를 나중에 정리할 수 없다.

`normalized_name` 단독이 아니라 `domain` 과의 복합이어야 한다. 단독이면 개발의 `모델` 과 패션의 `모델` 이 충돌해 한쪽이 들어가지 못한다 ([§6](#6-동형이의어)).

## 6. 동형이의어

같은 표기가 다른 것을 가리키는 경우다.

**도메인이 다르면 분리된다.** `(domain, normalized_name)` 복합 UNIQUE 덕분에 개발의 `모델` 과 패션의 `모델` 은 별개 행이 된다 ([§5](#5-승격)). 단독 UNIQUE 로 걸면 이 분리가 깨진다.

**같은 도메인 안의 동형이의어는 구분하지 못한다.** 개발 도메인의 `Swift`(언어)와 `Swift`(결제망) 같은 경우다. 문맥 클러스터링으로 나눌 수는 있지만, 판별이 불안정하고 `keywords` 스키마에 의미 구분을 표현할 자리가 없다.

**이 묶음은 이걸 해결하지 않는다.** 한계로 인정하고 문서에 남긴다. 실제로 문제가 되는 사례가 관측되면 그때 다룬다.

## 7. 검수 큐

층 2·3 이 자동 판별하지 못한 것들이 모인다. 내부 테이블이며 서비스 스키마가 아니다.

| 항목 | |
| --- | --- |
| 후보 쌍 | 대표 후보, 흡수 후보 |
| 근거 | 임베딩 유사도, NPMI, 문맥 유사도, 층 2 신호 유무 |
| 상태 | `PENDING` / `APPROVED` / `REJECTED` |
| 우선순위 | 두 후보의 문서 수 합 — **영향이 큰 것부터** |

**`REJECTED` 를 반드시 기록한다.** 기록하지 않으면 같은 쌍이 매 배치마다 다시 큐에 올라와 검수자를 지치게 한다.

승인된 병합은 다음 `extract` 실행부터 적용된다. 구현은 `pl_review_queue` 의 `APPROVED` 행을 병합 쌍으로 되읽는 것이고(`registry/review.approved_pairs`), 그 쌍은 층 1·2 가 낸 쌍과 함께 [§1](#1-절대-제약--키워드를-삭제하지-않는다) 의 대표 선정에 들어간다.

**⚠️ 층 3 후보는 사후 병합이 되기 쉽다** (2026-09-09). 층 3 의 대상을 "승격 심사를 통과한 것 ∪ 이미 승격된 것" 으로 좁혀 뒀는데(보이지 않는 후보끼리의 동의어는 아직 어느 화면에도 영향이 없다), 그러면 같은 회차에 양쪽이 승격된 쌍의 승인은 다음 실행에서 아래 경우가 된다. **그 경우를 이 절이 이미 정해 뒀으므로 새 결정이 아니다.**

**이미 승격된 키워드끼리의 병합 승인은 [§1](#1-절대-제약--키워드를-삭제하지-않는다) 의 사후 병합이라 자동 적용하지 않는다.** 큐에 남겨두고 백엔드와 함께 처리한다. 구현에서는 `registry/alias.resolve` 가 그런 쌍을 병합에서 빼고 큐로 되돌린다 — 사슬로 승격된 것이 둘 엮이면 **그 덩이를 통째로 보류한다.** 가운데 후보만 한쪽에 붙이는 것도 가능하지만, 그 선택이 곧 "두 승격 키워드는 별개다" 라는 판단이고 증거는 그 반대를 말하고 있다.

### 검수를 안 하면 어떻게 되나

큐가 비어 있어도 파이프라인은 정상 동작한다. 층 1·2 자동 병합만 적용되고, 층 3 후보는 병합되지 않은 채 각각 별개 키워드로 남는다. **의미적 동의어가 나뉘어져 있는 상태**이고, 그건 잘못 합쳐진 것보다 훨씬 낫다.

검수는 품질 개선 작업이지 파이프라인의 필수 경로가 아니다. 이 성질을 유지하는 것이 중요하다 — 사람 손을 파이프라인의 의존성으로 만들면 아무도 안 볼 때 파이프라인이 멈춘다.

## 8. 병합 이력과 재계산

병합할 때마다 내부 이력 테이블에 남긴다.

| 남기는 것 | 왜 |
| --- | --- |
| 대표 후보, 흡수 후보 | 무엇이 합쳐졌나 |
| 근거 (층 번호, 신호 값) | 나중에 판단을 검토하려면 |
| 적용 시점 | **통계 재계산 범위 판단** |

**병합은 과거 통계를 바꾼다.** `MCP` 와 `Model Context Protocol` 을 오늘 합치면, 어제까지 따로 세던 언급량이 하나로 합쳐져야 그래프가 이어진다. 합치지 않으면 병합 시점에 계단이 생기고, 사용자에게는 그게 실제 급증으로 보인다.

재계산 범위는 두 후보가 관측된 전 구간이다. 실무적으로는 최근 N일로 자르고, 그보다 오래된 구간의 계단은 감수한다. 구체적인 범위 정책은 [07 §3](07-metrics-and-ranking-spec.md).

### 구현 — 이력과 재계산이 한 트랜잭션이다 (2026-09-09)

| 순서 | 무엇 | 왜 그 자리인가 |
| --- | --- | --- |
| 1 | **바뀐 별칭만** 골라 임시 표에 담는다 (`_new_alias`) | 매 실행 같은 별칭을 다시 기록하면 이력이 부풀고 "적용 시점" 이 뜻을 잃는다 |
| 2 | 그것만 `pl_merge_log` 에 남긴다 | `pl_alias` upsert **보다 먼저**여야 한다. 뒤에 하면 비교 대상이 이미 갱신돼 무엇이 바뀌었는지 알 수 없다 |
| 3 | `pl_alias` upsert. **지우지 않는다** | 증거가 이번 실행에 안 잡혔다고 병합을 되돌리면 언급량이 다시 갈리고, 그 계단이 사용자에게 하락으로 보인다 |
| 4 | 바뀐 별칭이 관측된 전 구간을 모은다 | 최근 N일로 자르지 않았다 — 지금 규모([00 §3](00-overview.md))에서는 자를 이유가 없고 자르면 그 밖에 계단이 남는다 |
| 5 | 그 날짜의 일별 원자료를 다시 센다 | `io/candidates.DAILY_STAT_RECOUNT` — [04] 가 부르는 것과 **같은 SQL** 이다 |

**넷째·다섯째가 앞의 셋과 같은 커밋인 것이 정확성 조건이다.** 별칭만 들어가고 재집계가 죽으면 `pl_alias` 는 합쳐졌다고 말하는데 언급량은 표기별로 갈려 있고, 다음 실행의 `_new_alias` 가 비어 재집계가 다시 트리거되지도 않는다 — 그 상태가 영구히 남는다.

**사슬이 없어야 다섯째가 맞는다.** 재집계는 `coalesce(pl_alias.canonical_key, normalized_key)` 로 **한 홉만** 따라간다. `a → b` 와 `b → c` 가 동시에 있으면 `a` 의 문서가 사라진 대표 `b` 밑으로 셈된다. 그래서 대표 선정이 매 실행 **기존 별칭까지 쌍으로 되먹여** 전체 닫힘을 다시 계산한다 — 나오는 표는 늘 한 홉이다.
