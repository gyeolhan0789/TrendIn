# 웹 수집 설계

소스에서 새 글을 주기적으로 모아 MinIO 에 쌓고, 저장이 확인된 건마다 Kafka 이벤트를 낸다.
지금 코드에 있는 소스는 패션 매거진 7곳과 Hacker News 다(#1). 다국가 패션 소스는 S15P21A102-291 이 등록한다.
이 문서는 **무엇을 지켜야 하는지**(결정·불변식·계약)를 적는다. 어떻게 만드는지는 구현할 때 정한다.

- 실측일: 2026-09-03. 사이트 구조는 바뀌므로 #2 의 표는 그날의 사실이다.
- 근거 등급 표기: ① 실행 결과 ② 출처 ③ 감. 표기가 없는 줄은 이 문서의 결정이다.
- 잠정값은 **(잠정)** 으로 표시한다. 확정처럼 적힌 값은 바꾸려면 이 문서를 고친다.
- 뒤집힌 결정은 취소선과 날짜로 남긴다. 없어진 불변식·확정 번호는 결번으로 둔다 — 코드 주석이 번호로 부른다.

## 2026-09-17 기준 전환

MinIO 보존 기간(90일)은 바꾸지 않는다. 무기한 보존을 검토했지만 datastore 담당(유정균)의 결정을 따르기로 했다(확정 11).

특이사항.

- **harpersbazaar·cosmopolitan 의 `/rss`** 는 살아 있지만 사이트 전체 피드이고 `?category=` 파라미터를 무시한다. 카테고리는 항목 안 `cate_depth1` 태그로만 구분된다. 건수가 2건(bazaar)·10건(cosmo)이라 발견 경로로 쓰기엔 얕다. 그래서 목록 HTML 을 발견 경로로 삼는다.
- **harpersbazaar·cosmopolitan 에 회원 전용 기사가 있다.** 판정 신호는 **기사 페이지의 `div.membershipLine`** 이다 (① 재실측 2026-09-03, 표본 8/8 정확히 갈랐다). 목록 6장 기준 회원 전용은 217건 중 16건(7.4%)이다. 처리 규칙은 #7 불변식 2.
  - ⚠️ **판정에 쓰면 안 되는 것 둘.** (1) 목록 HTML 의 `membersYn` 은 **추천 위젯 JSON** 의 필드다. 그 JSON 은 페이지당 20건인데 앵커 36건 중 34건이 거기 없다 — 목록이 아니다. 목록 앵커 쪽 신호는 `div.memmark` 이고 둘은 다른 집합이다. (2) 기사 페이지의 "전체 페이지를 읽으시려면…" **마스크 문구는 8/8 전부에 있다**(숨은 모달 템플릿). 일반 기사에도 있으므로 구분자가 못 된다. `memmark` 역시 기사 페이지의 관련기사 위젯에 1~3개 나타난다.
- **두산매거진 4곳의 피드는 10건뿐**이고 vogue 는 하루치가 10건을 넘길 때가 있다(09-02 ~ 09-03 사이 10건). 주기가 길면 놓친다. #9 의 주기가 이 관찰에서 나왔다.
- **두산매거진 4곳은 WordPress REST(`/wp-json/wp/v2/posts`) 가 401** 이다. 피드가 유일한 구조화 경로다.
- **hypebeast 행은 2026-09-03 실측이다.** 약관 8조 때문에 뺐다가(옛 확정 2-1) 2026-09-17 기준 전환으로 다시 후보가 됐다. 291 이 등록할 때 이 행이 출발점이다.
- 모든 소스가 curl 기본 UA 에도 200 을 줬다. 즉 우리를 막는 건 없고, 우리가 스스로 지킬 규칙만 있다.

## 3. 법적 검토 (② 출처, 2026-09-03 조사)

전제: 비영리 학생 프로젝트. 원문은 내부 저장소에만 두고 외부에 재게시하지 않는다.
**2026-09-17 부터 약관과 robots.txt 는 판정 기준이 아니다.** 기준은 셋이다 — 접근 차단을 우회하지 않는다(불변식 2), 재게시하지 않는다(불변식 3), 회원 전용·유료 표시 본문을 저장하지 않는다(불변식 2).
법령 조문은 국가법령정보센터(law.go.kr) 원문, 약관은 각 사이트의 약관 페이지, 판례는 판결 요지를 확인했다.

**결론.** 공개 페이지를 정상 접근으로 읽는 것 자체는 문제가 없다. 위법은 **차단 우회**와 **재게시**에서 갈린다. 야놀자 대 여기어때(대법원 2022.5.12. 선고 2021도1533)는 회원가입 없이 열린 API 를 읽은 행위를 전부 무죄로 봤다. 접근권한 제한 여부는 "보호조치나 이용약관 등 객관적으로 드러난 사정을 종합"해 본다. 잡코리아 대 사람인(대법원 2017.8.24. 선고 2017다224395)은 VPN 으로 정체를 숨기고 출처를 지운 뒤 경쟁 서비스에 재게시한 행위를 부정경쟁행위로 봤다. 이 두 사건 사이가 우리 기준선이다.

## 4. 구조 — 다섯 단계와 장부

```
[발견] ─후보─▶ [취득] ─원문─▶ [정규화] ─article.json─▶ [저장] ─장부 행─▶ [발급]
  소스별          소스별          공통                 MinIO+장부           Kafka
```

| 단계 | 하는 일 | 입력 | 출력 |
|---|---|---|---|
| 발견 | 소스에서 새 글 후보 목록을 얻는다 | 소스 정의, 마지막 커서 | 후보 `{article_id, url, published_at?}` 목록. 피드 소스는 원문(item XML)도 함께 |
| 취득 | 후보의 원문 바이트를 얻는다 | 후보 | raw 바이트 + 받은 시각. 피드 소스는 발견에서 받은 item 이 곧 raw 라 이 단계가 빈다 |
| 정규화 | raw 에서 공통 스키마를 만든다 | raw | `article.json` (#5.3) |
| 저장 | MinIO 에 raw 와 article.json 을 쓰고 있음을 확인한 뒤 장부에 적는다 | raw, article.json | 장부 행 (#5.4) |
| 발급 | 장부에서 아직 이벤트가 안 나간 행을 골라 Kafka 에 낸다 | 장부 | 이벤트 (#6), 장부 `event_emitted_at` |

**발견과 취득은 소스마다 다르고, 정규화 이후는 소스와 무관하다.** 소스 어댑터의 책임은 "후보 → raw → article.json" 까지다. 저장·발급은 어댑터를 모른다.

**장부(`collected_article`)를 두는 이유.** "저장이 확인된 뒤에 발급한다"를 재시도에도 성립하게 만드는 자리다. 저장 태스크가 장부에 적고, 발급 태스크가 장부를 읽어 낸다. 둘 사이에서 죽어도 장부에 `event_emitted_at` 이 비어 있으니 다음 실행이 이어 낸다. 같은 기사를 다시 발견했을 때 건너뛰는 판정도 장부로 한다. (대안: 장부 없이 MinIO 객체 존재 확인만으로 판정 — ⚠️ #12)

## 5. 저장 구조

### 5.1 버킷과 키

버킷 하나. 도메인·소스·경로·날짜는 키 접두어다.

```
{bucket}/{domain}/{source}/{route}/{yyyy}/{mm}/{dd}/{article_id}/raw.{ext}
{bucket}/{domain}/{source}/{route}/{yyyy}/{mm}/{dd}/{article_id}/article.json
```

| 자리 | 값 | 규칙 |
|---|---|---|
| `bucket` | `raw-data` | 하나. `datastore/` 가 만드는 이름이고 `TRENDIN_MINIO_BUCKET` 으로 온다 |
| `domain` | `fashion` \| `dev` | #1 의 표 |
| `source` | #1 의 소스 키 | 소문자·숫자·하이픈 |
| `route` | `rss` \| `listing` \| `api` \| `linked` | **소스당 하나로 고정**한다. `linked` 는 Hacker News 가 링크한 외부 원문이다 (`source-discovery.md` #5.1). 경로를 바꾸면 소스 정의를 바꾸는 것이고 이 문서를 고친다. 소스 하나가 두 경로를 가지지 않으므로 같은 기사가 두 키에 생기지 않는다 |
| `yyyy/mm/dd` | **발행일**, Asia/Seoul 기준 | 수집일이 아니다. 같은 기사를 언제 다시 받아도 같은 키에 간다. 수집 시각은 article.json 과 객체 메타데이터에 |
| `article_id` | 소스 안에서 유일하고 바뀌지 않는 값 | #2 표의 "기사 ID" 열. URL 슬러그는 쓰지 않는다(제목이 바뀌면 슬러그도 바뀐다) |
| `ext` | `xml` \| `html` \| `json` | 피드 소스 `xml`(item 조각), 목록·`linked` 소스 `html`(기사 페이지), API 소스 `json`(응답 그대로) |

객체 메타데이터 (확정, S15P21A102-158): `collected-at`(ISO-8601 KST), `content-sha256`.

`content-sha256` 은 **그 객체 자신의** 해시다 — raw 객체에는 raw 의 해시, article.json 에는
article.json 의 해시. 이벤트·장부에도 같은 값이 있지만, 객체만 손에 쥔 상황에서 "언제 받은
것이고 내용이 무엇이었나"를 되짚을 수 있어야 해서 여기에도 둔다.

`run-id` 는 **객체 메타데이터에는** 넣지 않는다. 객체는 한 번 쓰이고 안 바뀌는데 발급은
나중에, 때로는 다시 일어나기 때문이다. 이벤트의 `run_id`(#6)는 그것과 다른 값이다 — 거기엔
"이 이벤트를 낸 실행" 이 들어가고, 재발급에 따라 바뀌므로 소비 측 파티션 키로 쓰지 않는다.

값은 ASCII 만 넣는다. 객체 메타데이터는 `x-amz-meta-*` 헤더로 실리고 헤더는 latin-1 이라
한글이 섞이면 요청 자체가 깨진다. 저장 구현이 요청 전에 막는다.

### 5.2 raw

받은 바이트 그대로. 인코딩 변환·정리·압축을 하지 않는다.

그래서 content-type 에 charset 을 붙이지 않는다 (`application/xml` · `text/html` ·
`application/json`). 소스가 EUC-KR 로 줄 수도 있는데 utf-8 을 단정하면 헤더가 내용에 대해
거짓이 된다. article.json 은 우리가 만들어 항상 utf-8 이지만 그건 JSON 규격이 못 박는다. 정규화가 틀렸을 때 raw 에서 다시 만들 수 있어야 한다.

2026-09-17 이전에 저장된 article.json 은 평문 그대로 두고 다시 만들지 않는다 — Spark 가 평문을 다시 벗겨도 꺾쇠 표기 말고는 바뀌지 않고, 객체는 90일 뒤 사라진다.

| `source` `article_id` | 유일키 |
| `domain` `route` `url` `title` `published_at` | article.json 과 같은 값 |
| `raw_key` `article_key` `content_sha256` | 저장 결과. 회원 전용이거나 유료 표시면 `raw_key` `content_sha256` 이 NULL |
| `published_at_offset` | 소스가 준 UTC 오프셋(분). `timestamptz` 가 오프셋 표기를 버려서 따로 남긴다 |
| `article_sha256` | article.json 의 해시. 발급 봉투의 `checksum` 이 이 값이다 |
| `members_only` | 발급 봉투에 싣는다. NOT NULL |
| `paywalled` | 위와 같다. NOT NULL DEFAULT false. 이미 있는 표에는 DDL 이 `ADD COLUMN IF NOT EXISTS` 로 더한다 (2026-09-17) |
| `collected_at` | |
| `event_emitted_at` | 발급 성공 시각. NULL 이면 아직 안 나갔다 |

발급이 장부만 읽고 봉투를 채울 수 있어야 해서 `article_sha256` `members_only` `paywalled` 가 있다.
없으면 발급이 MinIO 에서 article.json 을 다시 읽어야 하고, "저장 확인"의 `stat` 이 `get` 으로 커진다.

DDL 은 `trendin.common.collect.ledger.DDL` 이고 DAG 의 첫 태스크가 `CREATE TABLE IF NOT EXISTS`
로 매번 적용한다. 앱 DB 에 마이그레이션 도구가 없어서다 — `docker/postgres-init/` 은 빈 볼륨
초기화 때 한 번만 돌고 EC2 의 이미 있는 DB 에는 안 먹는다.

**같은 DB 의 backend 가 `ddl-auto: create` 다.** 이 테이블이 JPA 밖이고 지워지지 않는다는
합의가 S15P21A102-12 에 적혀야 한다. 코드가 자동 복구하는 경로와 사람이 아는 경로가 둘 다 필요하다.

`published_at_offset` 은 팀 시각 규약("`published_at` 은 소스가 준 시각을 그대로 보존")을 지키는
자리다. `timestamptz` 는 순간만 보관하고 오프셋 표기를 버려서, 그냥 읽으면 한국 매체의 `+09:00`
이 세션 시간대로 바뀌어 나간다. 이 칸이 생기기 전에 적힌 행은 오프셋이 `NULL` 이고, 그 행은
읽은 그대로 낸다 — 없는 값을 지어내면 출처가 아니라 추측이 나간다.

조건부 요청용 `collect_validator(url, etag, last_modified, updated_at)` 도 같은 DDL 이 만든다.
실행 사이에 ETag 가 남아야 304 가 실제로 듣는다.

소스별 국가는 `collect_source_country(source, country)` 가 든다. 국가는 기사가 아니라 소스의 속성이라
장부 행에 칸으로 넣지 않고, 소비 측 창구 뷰가 이 표를 `LEFT JOIN` 해 `source_country` 로 낸다 — 없으면
`XX` 다. 값의 정본은 코드의 `SourceDef.country` 이고 DDL 뒤의 UPSERT 가 DB 거울을 맞춘다. **사라진
소스의 행은 지우지 않는다.** 지우면 그 소스로 이미 받아 둔 기사가 전부 `XX` 로 바뀌어 과거 집계가
흔들린다 (S15P21A102-276).

v1 은 장부에 있는 `(source, article_id)` 는 다시 취득하지 않는다. 수정 기사 추적은 범위 밖이다.

장부는 지우지 않는다. MinIO 객체가 보존 기간(#9)을 넘겨 사라진 뒤에도 "언제 어디서 무엇을 받았나"는 장부에 남는다. 그래서 장부의 `url` `title` `published_at` 은 article.json 의 사본이지 참조가 아니다.

## 6. 이벤트 (Kafka)

기사 토픽 `raw-file-ready`와 실행 요약 토픽 `collect-run-summary`로 나눈다.
봉투의 전체 필드·null 규칙·샘플은 [`spark-integration.md` §3](spark-integration.md#3-봉투--토픽별-계약)가 정본이다.

| 항목 | 기사 토픽 | 요약 토픽 |
|---|---|---|
| 단위 | 저장 확인된 기사 하나 | 소스 하나의 한 회차 (0건·실패 포함) |
| `event_id` | `{source}-{article_id}`, 결정적인 중복 판정 함수 | `{source}-{run_id}` |
| 실행 ID | `run_id`, 발급 실행 | `run_id`, logical date 파생 KST |
| 건수 | `record_count=1` | 수집 `stored`와 발급 `emitted`를 분리 |
| `status` | `success` | `success` 또는 `failed` |
| MinIO 키 | `object_key`, `raw_object_key` | 해당 필드 없음 |

message key는 둘 다 `source_id`다. 같은 토픽의 같은 소스는 한 파티션에 모이지만,
**두 토픽 사이 순서는 보장하지 않는다.** 기사와 요약의 `run_id`로 대사한다.
`event_id`를 파싱해 source를 추출하거나, 재발급에 따라 바뀌는 기사 `run_id`로
파티션을 나누지 않는다. 이 토픽 분리(2026-09-09)로는 `article.json`과 장부 스키마가 바뀌지 않았다. `paywalled` 칸은 2026-09-17 따로 더했다(#5.3 · #5.4).

수집은 `discovered`, `stored`, `skipped`, `not_modified`, `failed`, `failed_by_stage`,
`failures`, `duration_ms`, `members_only_stored`, `paywalled_stored`(2026-09-17)를 남긴다. 수집 태스크가 죽으면 전부
`null`이다. 실패 이유는 원래 길이가 예측되지 않아 XCom에서 제외했지만,
**표본 10건·사유 200자 상한**으로 길이를 제한해 이번에 포함한다. 전체 실패 건수는 유지한다.
`Failure.stage`는 discover·materialize·store다. 회원 전용·유료 표시 저장 수는 저장 확인에 성공한 수다.

발급은 장부의 `event_run_id`로 소스별 `count(*)`와 `min(collected_at)`을 집계한다.
요약의 `emitted`와 `emitted_oldest_collected_at`이 이 값이며, 수집 태스크 성패와 무관하다.
이월분이 섞이면 수집 수보다 발급 수가 많아질 수 있다. 미발급 행을 전부 비운 후 집계하므로
같은 회차의 재시도는 발급 통계를 보존한다. `run_started_at`은 logical date로 재시도에도 같다.

**요약 활성화는 선택적이다.** `TRENDIN_KAFKA_TOPIC_RUN_SUMMARY`가 비면 기사만 발급하고
로그 및 `summaries=0`, `summary_enabled=false`를 남긴다. 토픽을 만든 뒤 환경변수를 채운다.
구체적 생성 요청과 이행 순서는 `spark-integration.md` §12에 있다.

## 11. 순서

설계가 못 박는 순서만 적는다. 나머지는 병렬이다.

1. **MinIO 가 있어야 저장 부품이 검증된다.** 어댑터는 고정 자료(저장한 피드·HTML)로 저장소 없이 검증한다.
2. **Kafka 가 있어야 발급 부품이 검증된다.**
3. **저장 부품(장부 포함)이 있어야 발급 부품이 읽을 행이 있다.**
4. 어댑터 8개는 서로 독립이고 저장 부품과도 독립이다.

```
[MinIO 구축] ──▶ [저장 + 장부] ──▶ [발급] ◀── [Kafka 구축]
[어댑터 ×8] ──────────────────────────┘ (합류는 실행 DAG 에서)
```

## 13. 실행 방법 참고 (결정이 아니다)

파이프라인 규약(`pipeline/README.md`)에 맞춘 한 가지 방법이다. 수행자가 바꿔도 이 문서의 결정은 그대로다.

- 도메인당 DAG 하나(`fashion_collect`, `dev_collect`), 소스별 동적 매핑. 외부 요청 태스크는 `pool="crawler_pool"`. 호스트별 간격은 어댑터 안에서.
- MinIO 는 S3 호환이라 Airflow 의 S3 훅(`endpoint_url` 지정)으로 쓴다. Kafka 는 Airflow 의 Kafka provider 또는 `confluent-kafka` 직접.
- MinIO·Kafka 는 `infra/compose.yaml` 의 `s15p21a102-shared` 네트워크에 붙는다. 포트는 `127.0.0.1` 바인드, 접근은 SSH 터널.
- 커서: 피드 소스는 커서가 없다(매번 10~20건 받고 장부로 거른다). hn 도 같은 방식이다 — 매 실행이 현재 시각에서 6시간 창을 묻고 장부로 거른다. Airflow 데이터 구간을 쓰지 않는 이유는 수집 태스크 계약에 실행 문맥을 새로 끌어들이지 않기 위해서다. 창보다 오래 멈춘 구간은 `trendin.dev.collect.backfill` 이 받는다.
- 보존 기간은 MinIO 버킷 수명주기 규칙(ILM)으로 건다. 코드가 지우지 않는다.
- 호스트별 3초 간격은 어댑터 안의 단일 세션에서 지킨다. 같은 호스트를 두 태스크가 동시에 치지 않도록 소스당 태스크 하나로 매핑한다.

| 키 파티션 | `domain=…/collected_date=…/source=…/run_id=…` (수집일) | `domain/source/route/yyyy/mm/dd/article_id` (발행일 KST) |
| 버킷 | `raw-data` | `raw-data` — **맞췄다** |
| 토픽 | `raw-file-ready` | 기사 `raw-file-ready` · 요약 `collect-run-summary` (#6) |
| 이벤트 단위 | 파일 하나당 하나 | 기사 하나당 하나 + 별도 토픽의 소스별 실행 요약 하나 |
| 중복·멱등 | Spark 단계에서 중복 제거 | 장부와 기사별 키로 수집 단계에서 |
| dev 소스 | reddit · github · stackoverflow 를 예시로 | Hacker News 만 (이 문서의 범위) |

**기사별로 갔다 (2026-09-07, S15P21A102-167).** 이유는 #8 확정 5·7 이다. 배치 파일이면 같은 기사를 다시 받았을 때 새 `run_id` 밑에 또 생겨 불변식 7 이 성립하지 않고, 소비자가 기사 하나를 다시 읽으려면 파일 전체를 열어야 한다.

배치 파일 쪽 이점은 객체 수와 이벤트 수가 적다는 것이다. 규모가 하루 700건 안팎이라(① HN 시간당 26건, 패션 7곳 합쳐 하루 100건 안팎) 둘 다 감당된다.

버킷과 토픽은 팀 것에 맞췄으므로 남은 차이는 **저장·이벤트의 단위** 하나다. 팀이 배치 파일로 되돌리면 이 문서의 #5·#6·#7 을 고친다.
