# 개념 연결 — 지금 어떻게 돌고 어디가 문제인가 (2026-09-22)

한 줄로 줄이면 이렇다.

> 사전에 있으면 **찾긴 찾는다.** 문제는 사전 커버리지가 낮다는 것과, 사전에 없을 때 쓰는
> 자동 연결이 DB 를 너무 많이 왕복하면서 정작 LLM 에는 문맥을 안 준다는 것이다.

"잘 붙는다" 가 아니라 "찾긴 찾는다" 인 이유는 아래 [무엇을 아직 못 쟀나](#무엇을-아직-못-쟀나)
에 적었다. 붙인 것이 맞는지는 아직 아무도 확인하지 않았다.

설계는 [concept-layer.md](concept-layer.md) 에 있다. 이 문서는 **지금 상태의 성적과 병목**이다.
측정 방법과 원자료는 [concept-dictionary-regression-2026-09-22.md](concept-dictionary-regression-2026-09-22.md)
에 있다.

## 현재 흐름

```
기사 수집
  → GLiNER 가 키워드 후보 추출        (pl_document_candidate)
  → 기사 5건·저자 3명 넘은 것만 승격   (pl_keyword_id_map)
  → 개념 사전에서 같은 표현 찾기
      있으면  → concept 연결
      없으면  → unmapped
  → --auto-link 면 LLM + 유사도 검색으로 한 번 더
  → 그래도 실패하면 사람 검토          (scripts/concept-review.py)
```

기본 매핑은 단순하다. LLM 을 부르지 않는다.

```
"코트"
  → (lang=ko, normalized=코트) 해시 조회
  → concept 하나면      바로 연결
  → 여러 개면           기사에 이미 붙은 개념들의 category 로 판별
  → 못 고르면           유보
  → 아예 없으면         미등록
```

## 속도 — 어디서 시간을 쓰나

### 초기 사전 적재가 매 실행 2만 번 왕복한다

**여기가 제일 크고, `--auto-link` 와 무관하다.** 기본 경로에서도 돌고 `--dry-run` 에서도 돈다
(사전 없이 돌리면 전부 미등록이 되므로 일부러 그렇게 해뒀다).

`concept/seed.py` 의 `apply_seed` 가 개념을 하나씩 upsert 하면서 `RETURNING` 으로 id 를 받고,
표현도 하나씩 INSERT 한다. 연결은 하나를 재사용하지만 **문장마다 왕복한다.**

| | 수 |
| --- | ---: |
| 개념 upsert | 3,436 |
| 표현 INSERT | 16,786 |
| 상위 UPDATE | 34 |
| **매 실행 문장 수** | **20,256** |

왕복 1ms 면 20초, 5ms 면 100초, 15ms 면 300초다. `execute_values` 로 묶으면 수십 번으로
줄어든다. 표현 1.6만 건은 그냥 한 번에 보낼 수 있고, 개념은 `RETURNING` 때문에 조금 손이 간다.

> 이전 문서의 "조회 0.08~0.11초 · 사전 구성 1.3~1.9초 · 매핑 0.5~0.9초" 는 **컨테이너 안의
> 조회와 매핑만** 잰 것이다 (2026-09-20 문서가 그렇게 밝혀뒀다). 사전 upsert·스키마 확인·결과
> 쓰기가 빠져 있으므로 Job 전체 시간으로 읽으면 안 된다.

### 자동 연결이 표현마다 DB 를 5~7번 새로 연다

`io/jdbc.py` 의 `connection()` 이 매번 새 psycopg2 접속을 만든다. 판정 캐시 조회·기록, 벡터
검색 2회, 검증 캐시 조회·기록, 유보 기록이 전부 이걸 직접 쓴다.

```
표현 1개
  → 연결 → 캐시 조회 → 끊음
  → 연결 → 벡터 검색(원문) → 끊음
  → 연결 → 벡터 검색(영어명) → 끊음
  → 연결 → 캐시 기록 → 끊음
  ...
```

문서의 "DB 검색 60~90ms" 는 대부분 이 접속 비용이다. 1.6만 × 384차원 스캔 자체는 한 자릿수
ms 다. Sink 가 실행 동안 연결 하나를 들고 있게만 해도 사라진다.

### 철자 유사도를 후보마다 처음부터 계산한다

`concept/candidates.py` 의 `_NgramIndex.search` 가 후보마다 `SequenceMatcher` 를 새로 만들고
전부 `ratio()` 를 돌린다. 조각 색인으로 좁힌 뒤에도 표기 하나에 **비교를 927번** 한다
(최종 후보가 927개라는 뜻이 아니라, 유사도 계산 횟수다. 후보는 5개로 끊는다).

매처 하나를 재사용해 질의를 고정하고 `real_quick_ratio`/`quick_ratio` 로 먼저 쳐내면
**20.3ms → 7.1ms** 다. 표본 200개에서 결과가 한 글자도 달라지지 않았다. `retrieve()` 가
원문·영어명으로 두 번 부르므로 표기당 26ms 가 사라진다.

### 링크 하나 붙었다고 30일 전체를 다시 매핑한다

`spark/jobs/concept.py` 의 `_run_automatic_linking` 이 그렇다.

```
30일 전체 매핑
  → 새 링크 발견
  → 30일 전체 또 매핑 + 전체 행 또 적재
```

실제로 달라질 수 있는 것은 새로 붙은 표현이 나온 기사뿐이고, 그 목록은 `auto_pairs` 를 만들 때
이미 손에 있다.

### 한 번에 보낼 수 있는 것을 한 건씩 보낸다

`apply_links` 는 여러 건을 한 트랜잭션에 받게 만들어져 있는데 루프 안에서 한 건씩 들어간다.
링크마다 접속 + advisory lock + **사전 버전 1 증가**다. 버전 번호가 부풀어 성능만의 문제도 아니다.

판정 캐시도 배치 20개면 왕복 40번이다. 목록으로 한 번에 읽고 `execute_values` 로 한 번에 쓰면
2번이다.

### 벡터 검색은 지금은 문제가 아니다

`io/concept_vectors.py` 의 `SEARCH_SQL` 이 개념별 `min(거리)` 를 GROUP BY 로 구한다. 이 모양이면
pgvector 의 HNSW·IVFFlat 을 계획기가 쓰지 않는다 — 그룹 최솟값을 내려면 어차피 전부 계산해야
하기 때문이다. 표현 단위 ANN Top-N 을 먼저 뽑고 개념으로 접는 2단 질의로 바꿔야 색인이 붙는다.

다만 1.6만 규모에서는 병목이 아니다. 사전이 10만을 넘길 때를 위한 대비다.

## 품질 — 속도보다 큰 문제

최근 30일 `fashion`, 기사 4,460건, 승격 표기 34,133개.

| 결과 | 비율 |
| --- | ---: |
| 붙음 | 37.8% |
| 사전에 없음 | 58.4% |
| 애매함(유보 + 문맥 판별) | 3.8% |

**실패의 원인이 "알고리즘이 못 골랐다" 가 아니라 "애초에 사전에 없다" 다.** 그래서 지금은
임계값 튜닝보다 사전 확대가 훨씬 중요하다.

그리고 사전에 없는 것들의 머리는 옷이 아니다. 기사 5건 이상 나온 1,032종을 위키데이터에
물어보니 **사람이 최소 46.6%** 였고(라벨 정확 일치로만 찾아 놓친 것까지 넣으면 60% 이상),
나머지는 패션위크·영화제 같은 **행사**, `Vogue`·`GQ`·`Getty Images` 같은 **매체·플랫폼**,
그리고 `メゾン マルジェラ` 처럼 **개념은 있는데 다른 언어 표기가 없는** 경우였다.

### LLM 에게 정보를 너무 적게 준다

`concept/judge.py` 의 `user_prompt` 가 보내는 것은 `{"i":1,"w":<비교키>}` 뿐이다. 거의
"이 단어가 뭘까요?" 에 가깝다. 이미 가지고 있는데 안 넘기는 것이 셋이다.

* **원표기** — 모델이 `バレエコア` 가 아니라 정규화된 `ばれえこあ` 를 본다. `Question.surface`
  에 이미 들어와 있다.
* **기사 제목** — 표현당 20개까지 `pl_unmapped_context` 에 쌓여 있는데 벡터 재판정 프롬프트만
  쓴다. (본문 문장은 애초에 DB 에 없다. `pl_document_candidate` 에 문장 칸이 없고 본문은
  오브젝트 스토리지에 있다. 지금 쓸 수 있는 문맥은 제목이다.)
* **언어**

`vogue`→brand, `브이넥`→style 오판이 여기서 나왔다.

### 증거가 약한 경로의 검증이 더 느슨하다

```
쉬운 경로 (문 2)
  LLM 이 영어 이름 생성 → 사전에 하나 있으면 → 바로 영구 연결

어려운 경로 (문 3)
  후보 5개 → 유사도 → category 일치 → 기사 문맥 존재 → LLM 검증 → 연결
```

거꾸로다. 문 2 는 문맥도 안 보고 검증 호출도 없이 `pl_concept_expression` 에 동의어를 영구히
쓴다. 실제로 지금 붙는 자동 연결은 대부분 문 2 에서 나온다.

### category 를 하드 필터로 쓴다

`vector_judge.eligible_choice` 가 LLM 이 추측한 분류와 후보 분류의 **문자열 완전 일치**를
요구한다. 분류를 틀리면 정답 후보가 있어도 탈락한다. 절대 조건보다 점수 중 하나로 쓰는 쪽이
맞을 가능성이 크다.

### 유사도 관문은 사실 걸리지 않는다

`min_combined_score: 0.55` 인데 채널 문턱 × 가중치의 최솟값이 벡터 0.7×0.85=0.595 다. 채널
문턱을 넘은 후보는 전부 자동으로 이 관문도 넘는다. `LOW_SCORE` 유보는 분류가 어긋났을 때만
발동하고, 그건 `eligible_choice` 가 따로 요구하므로 자동 연결 판단에서는 죽은 코드다.

### generic 판정이 조용히 일을 지운다

LLM 이 `generic` 이라고 하면 후보 검색도 안 하고 버린다. 실측 20개 중 **11개**가 여기서
사라졌다. 문맥 없이 내리는 판단이고, 잘못 버려도 오연결로 안 잡히므로 찾을 방법이 없다.

### DB 에 이미 중복 개념이 있다

`UGG/brand`(3133) 와 `Ugg/brand`(12446) 가 서로 다른 개념으로 존재한다. DB 유일키
`(canonical_name, category)` 는 대소문자를 가리는데 이름 조회 `name_key()` 는 소문자로 접기
때문이다.

```
"ugg" → 후보 2개 → 하나를 못 고름 → 연결 실패
```

문서에 나온 `어그` 유보가 이것이다. 사전 품질 자체의 문제라 규칙으로는 못 푼다.

## 무엇을 아직 못 쟀나

지금까지 잰 것은 전부 **"붙었나"** 이고 **"맞나"** 는 라벨이 없어 못 쟀다. 붙는 것의 다수가
브랜드라 평균이 낙관적으로 나올 가능성이 크다 — 브랜드는 글자가 같아 틀리기 어렵고, 위험한
것은 일반명사와 인명이다.

유사도 문턱·category 관문·`generic` 규칙은 이 숫자 없이는 조정할 수 없다. 붙은 것 중
**분류별로 골고루 200개**를 뽑아 사람이 O/X 를 치면 된다. 많이 나오는 순으로 뽑으면 브랜드만
걸려 정확도가 100% 로 나온다.

## 고치는 순서

되돌릴 수 있고 측정 없이도 확실한 것부터다.

1. **초기 사전 적재 배치화** — 매 실행 2만 왕복. auto-link 와 무관하게 전부에 듣는다.
2. **DB 연결 재사용** — 표현당 5~7개 접속.
3. **SequenceMatcher 최적화** — 동작이 안 바뀌는 순수 이득. 측정 끝났다.
4. **링크·캐시 배치화**, **새 링크 생겼다고 30일 전체 재매핑하지 않기**.
5. **사전 확대** — 인물, 행사, 다국어 표기. 못 붙는 것의 절반 이상이 여기다.
6. **LLM 에 원표기 + 언어 + 기사 제목 주기** — 품질 쪽 제일 큰 지렛대.
7. **중복 개념 제거** — 대소문자 유일키부터. `lower(canonical_name)` 함수 인덱스로 바꾸거나
   적재할 때 접는다.
8. **정답 200개를 만든 뒤** 유사도 문턱 · category · generic 규칙을 조정한다.
9. 사전이 훨씬 커지면 그때 **ANN 검색 구조**를 고친다.

"Spark 를 써야 하나", "벡터 검색을 갈아엎어야 하나" 같은 대공사보다, **사전 확대 + auto-link
주변의 자잘하지만 큰 병목 제거**가 먼저다.

사전을 바꿀 때는 [회귀 검사](concept-dictionary-regression-2026-09-22.md#왜-만들었나)를 먼저
돌린다. 표현을 늘리다가 원래 붙던 것이 밀려날 수 있고, 합계 매핑률만 보면 그게 안 보인다.
