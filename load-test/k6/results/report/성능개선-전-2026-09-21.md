# 부하테스트 결과 — 성능 개선 전 (2026-09-21)

**개선 작업을 시작하기 전의 기준선이다.** 이 문서의 수치가 "before" 이고, 인덱스·풀 설정을
손본 뒤 같은 방법으로 다시 재서 "after" 와 나란히 놓는다.

k6 로 엔드포인트 일곱 개를 하나씩 격리해 측정했다. 원본 로그는 이 파일의 부모 디렉터리
(`load-test/k6/results/`) 에 있고, 측정 방법은 [`../../README.md`](../../README.md) ·
[`../../../README.md`](../../../README.md) 에 있다.

## 세 줄 요약

1. **두 엔드포인트가 무너졌다.** `GET /trends/{id}/contents` 와 `GET /members/me/notifications`
   는 p95 가 **55초·56초**다. 목표 부하의 20% 만 처리하고 나머지는 드롭됐다.
2. **`GET /trends/{id}/regions` 는 성능 문제가 아니라 기능 고장이다.** 부하와 무관하게
   **200 응답률 0%** 이고, 2 RPS 에서도 똑같이 실패한다. 이건 성능 수치로 읽으면 안 된다.
3. **나머지는 여유가 있다.** 상세·이력·저장목록은 100~200 req/s 에서 p95 가 **20ms 아래**이고
   실패·드롭이 0 이다. 같은 DB·같은 서버인데 이만큼 갈리는 것이 곧 문제가 코드 쪽에
   있다는 증거다.

### DB 에 들어 있는 것

`load-test/seed/` 가 `setseed(0.42)` 로 매번 같은 데이터를 만든다.

**회원 10,000명** — `load1@test.com` ~ `load10000@test.com`, 비밀번호는 전부
`Loadtest1234!` 다.

**회원마다 활동량이 크게 다르다.** 이게 이 시드에서 가장 중요한 부분이다. 전원에게 같은
양을 주면 PostgreSQL 통계가 "회원당 N행" 으로 잡혀 플래너가 늘 같은 계획을 고르고, 실제
서비스에서 무너지는 자리가 드러나지 않는다. `id % 100` 으로 네 계층으로 갈랐다.

| 계층 | 비율 | 인원 | 저장한 트렌드 | 관심 키워드 | 알림 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 가입만 함 | 50% | 5,000 | 0 | 0~1 | 0~2 |
| 가볍게 씀 | 30% | 3,000 | 1~5 | 2~5 | 5~20 |
| 꾸준히 씀 | 15% | 1,500 | 6~30 | 5~15 | 50~200 |
| **헤비** | 5% | 500 | **100~500** | 20~50 | **300~1,500** |

**개인화 조회는 헤비 회원(`id % 100` = 95~99)으로 잰다.** 평균 회원으로 재면 문제가 드러나지
않는다. 알림·저장목록이 그렇다. 상세·이력·지역은 비교군이라 평균 회원(50~79)을 쓴다.

| 테이블 | 행 수 |
| --- | ---: |
| `keyword_metric_history` (일별 이력) | **4,500,000** |
| `keyword_country_daily_metrics` (국가별 일별) | **~2,400,000** |
| `keyword_contents` (키워드–콘텐츠 연결) | ~600,000 |
| `keyword_relations` (연관 키워드) | ~500,000 |
| `contents` | 200,000 |
| `keyword_metrics` · `trend_analyses` | 150,000 씩 |
| `keywords` · `trends` (1:1) | 50,000 씩 |
| `members` | 10,000 |

**콘텐츠와 국가 데이터는 상위 2,000개 키워드에 몰려 있다.** 실제 서비스도 그렇고, 고르게
뿌리면 어느 트렌드를 눌러도 결과가 작아 아무것도 재지 못한다. k6 도 그 범위에서 고른다.

### 동시 요청 수는 고정하지 않았다

**"동시 사용자 N명" 모델이 아니다.** `ramping-arrival-rate` 로 **초당 도착 건수**를 고정하고,
동시 요청 수(k6 의 VU)는 서버가 느려지는 만큼 **저절로 늘어난다.**

고정 VU 로 재면 서버가 느려질 때 요청 발생도 같이 느려진다. 부하가 저절로 줄어드니 포화점이
보이지 않고 그래프가 완만하게 눕는다.

| | |
| --- | --- |
| 부하 모델 | `ramping-arrival-rate` — 도착률 고정, 동시 요청은 가변 |
| 램프 | 피크의 25% → 50% → 75% → 100% (각 36초) + 피크 유지 |
| 길이 | 엔드포인트당 3분 (+ graceful stop 30초) |
| 동시 요청 한도 | 사전 배정 50, **최대 1,000** (`MAX_VUS=1000`) |
| 요청 타임아웃 | **15초.** 넘기면 끊는다 — 더 기다리면 큐 대기 시간만 재게 된다 |
| 인증 토큰 | `setup()` 에서 50개 발급해 나눠 쓴다. VU 마다 로그인하면 bcrypt 가 가짜 병목이 된다 |
| 기준선 | `bench.sh` — 램프 없이 **10 RPS 고정** 1분 |

그래서 **관측된 최대 동시 요청 수가 곧 얼마나 밀렸는지**를 말해 준다.

| 엔드포인트 | 목표 도착률 | 실제 최대 동시 요청 | 읽는 법 |
| --- | ---: | ---: | --- |
| 상세 + 이력 ×2 | 100/s | **7** | 한도 1,000 중 7개. 한계 근처도 아니다 |
| 저장 + 관심 키워드 | 100/s | **10** | 여유 |
| 지역 ×3 | 50/s | **2** | 에러를 즉시 돌려주니 쌓일 틈이 없다 |
| 로그인 | 30/s | **43** | 쌓이기 시작 |
| 목록 | 200/s | **1,000** | 한도 도달 |
| 콘텐츠 | 100/s | **1,000** | 한도 도달 |
| 알림 | 100/s | **1,000** | 한도 도달 |

## 한눈에

| 엔드포인트 | 목표 도착률 | 달성 | p95 | 실패율 | 드롭 | 판정 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| `GET /trends/{id}` + 이력 ×2 | 100 it/s | 197.6 req/s | **13.6ms** | 0% | 0 | 🟢 여유 |
| `GET /members/me/saved-trends` + 관심키워드 | 100 it/s | 117.6 req/s | **20.2ms** | 0% | 0 | 🟢 여유 |
| `POST /auth/login` | 30 it/s | 20.3 req/s | **1.34s** | 0% | 0 | 🟡 주의 |
| `GET /trends` (목록) | 200 it/s | 97.1 req/s | **10.16s** | 0% | 6,003 | 🔴 포화 |
| `GET /trends/{id}/contents` | 100 it/s | 20.6 req/s | **55.75s** | 1.34% | 7,476 | 🔴 붕괴 |
| `GET /members/me/notifications` (+unread) | 100 it/s | 19.6 req/s | **56.61s** | 3.12% | 9,497 | 🔴 붕괴 |
| `GET /trends/{id}/regions` ×3 | 50 it/s | 99.4 req/s | 8.9ms | **66.5%** | 0 | ⚫ 기능 고장 |

**표 읽는 법.** 목표는 **반복(iteration)/초**, 달성은 **요청(request)/초**다. 반복 하나가
엔드포인트에 따라 요청을 1~3개 보낸다. 달성값이 목표보다 낮아 보이는 것은 4단 램프(피크의
25→50→75→100%)의 평균이라 그렇고, **드롭이 0 이면 정상**이다. 드롭이 붙었다는 것은 k6 가
요청하려던 반복을 시작조차 못 했다는 뜻 — 그때 비로소 한계다.

| --- | ---: | ---: |
| p95 (목록) | 103.7ms | **56.4s** |

| 실패율 | 0% | 3.12% |
| 드롭 | 0 | 9,497 |

2 RPS 에서는 100ms 안쪽으로 멀쩡하다. 부하를 올리면 **500배 이상** 벌어지고 요청의 3%가
타임아웃(15초)에 걸린다. 동시 요청이 한도인 **1,000개까지 찼고**, 측정이 끝나는 순간에도
794개가 처리를 기다리고 있었다.

15:28 과 15:32 두 회차가 거의 같은 수치(p95 56.94s / 56.61s, 드롭 9,576 / 9,497)로 나왔다.
**우연이 아니다.**

측정 스크립트가 세운 가설은 `notifications` 테이블에 **`member_id` 인덱스가 없다**는 것이다
([`../../README.md`](../../README.md) 의 스크립트 표). 헤비 회원 한 명이 알림 300~1,500건을
갖도록 시드했으므로, 인덱스가 없으면 조회마다 풀스캔이 된다. 수치는 이 가설과 모순되지
않지만, **`EXPLAIN` 으로 확인한 것은 아니다.**

### `GET /trends/{id}/contents`

p95 **55.75s**, 실패 1.34%, 드롭 7,476. 목표 100 it/s 중 20.6 req/s 만 처리했다.

스크립트가 보는 것은 `keyword_contents` 가 **`keyword_id` 단독 조회**를 받는 부분이다.

### `GET /trends` (목록)

여기는 결이 다르다. **실패가 0%** 이고 에러도 없다. 다만 200 RPS 를 목표로 걸었더니 97 req/s
까지만 따라오고 6,003 반복이 드롭됐다. 즉 **터진 게 아니라 한계에 닿은 것**이다.

기준선과 나란히 놓으면 분명하다.

| 부하 | p95 |
| --- | ---: |
| 10 RPS (`bench.sh` 기준선) | **28.68ms** |
| 약 97 RPS (본 측정) | **10.16s** |

인증이 없는 가장 단순한 목록 조회이고 다른 측정의 기준선 역할을 하는 엔드포인트다. 10 RPS
에서 29ms 라는 것은 **질의 자체는 빠르다**는 뜻이므로, 이 구간은 질의보다 커넥션 풀·스레드
쪽을 먼저 보는 것이 맞다.

## ⚫ 성능이 아니라 고장

### `GET /trends/{id}/regions`, `GET /trends/{id}/regions/{code}/history`

**200 응답률이 0% 다.** 6,104번 호출해서 한 번도 성공하지 않았다.

```
✗ 지역 목록 200   ↳ 0% — ✓ 0 / ✗ 6104
✗ 지역 이력 200   ↳ 0% — ✓ 0 / ✗ 6104
✓ journey 200     ↳ 100%
```

성능 문제가 아니라고 보는 근거:

- **빠르게 실패한다.** 평균 3.1ms, p95 6.1ms. 느려서 죽은 게 아니라 즉시 거절당했다.
- **부하와 무관하다.** 2 RPS 로 낮춰도 0% 그대로다.
- **같은 컨트롤러의 `journey` 는 100% 성공한다.** 서버도 DB 도 살아 있다.

셋의 차이는 `?period=30D` 파라미터를 받느냐다. 실패하는 둘은 받고 `journey` 는 안 받는다.
다만 같은 `period=30D` 를 쓰는 `GET /trends/{id}/history` 는 **100% 성공**하므로, 파라미터
파싱만으로 단정할 수 없다. **응답 본문을 봐야 한다** — k6 요약에는 상태 코드가 남지 않는다.

```bash
curl -i -H "Authorization: Bearer <토큰>" \
  'http://127.0.0.1:18080/trends/<상위트렌드ID>/regions?period=30D'
```

이 수치를 "지역 API 는 p95 8.9ms" 로 읽으면 안 된다. **에러 응답을 잰 시간**이다.

## 이 측정의 한계

정직하게 남겨 둔다. 다음 사람이 같은 함정에 빠지지 않도록.

**무릎(knee)을 못 찾았다.** `sweep.sh` 를 `notifications` · `trend-regions` 에 두 번
돌렸는데 **표에 행이 한 줄도 쌓이지 않았다** (헤더만 남은 표 파일은 내용이 없어 지웠다).

개별 회차 파일(`*-rps2-*.txt`)은 남았으므로 **2 RPS 지점만** 알 수 있다. 여러 도착률을 훑어
"달성 RPS 가 목표를 못 따라가기 시작하는 첫 지점" 을 찾는 작업이 남아 있다. 그전까지
**"이 엔드포인트가 몇 RPS 까지 버티는가" 에 대한 답은 없다.**

**k6 가 병목이었는지 확인하지 않았다.** k6 는 대상과 같은 EC2 에서 돈다. 무너진 세
엔드포인트는 VU 가 수백 개까지 쌓였고(`notifications` 794, `trend-contents` 351), 그 상태의
k6 는 CPU 를 상당히 먹는다. Grafana CPU 패널에서 **프로세스는 여유인데 시스템만 1 에
붙었다면 그 숫자는 서버의 한계가 아니다.** 측정 당시 이 확인을 하지 않았다.

**DB 를 운영과 공유한다.** EC2 가 한 대라 `trendin_test` 는 운영과 같은 PostgreSQL 안에
있다. 버퍼 풀·WAL·디스크가 공유되므로 측정 중 운영 상태가 수치에 섞였을 수 있다.

**첫 회차는 오타로 날아갔다.** 15:27 회차는 스크립트 이름을 `endpoint/notification.js`
(단수)로 잘못 줘서 k6 가 시작도 못 했다. 오류 한 줄뿐인 로그라 지웠다. 알림 측정은 15:28 ·
15:32 두 회차가 실제 결과다.

## 다음에 할 일

우선순위 순.

1. **`GET /trends/{id}/regions` 의 실제 응답을 확인한다.** 성능 작업을 시작하기 전에 해야
   한다. 고장난 엔드포인트를 튜닝할 수는 없다.
2. **`notifications.member_id` 인덱스를 `EXPLAIN` 으로 확인하고, 없으면 넣는다.** 가장 큰
   효과가 기대되는 한 줄이다.
3. **`bench.sh` 로 전후를 비교한다.** 인덱스를 넣기 **전에** `./bench.sh baseline` 을 먼저
   찍어 둬야 한다 — 지금 기준선은 `trends-list` 하나뿐이다.
4. **`sweep.sh` 표가 왜 비었는지 보고 무릎을 찾는다.** p95 개선과 한계 RPS 는 다른 축이라,
   하나만 재면 절반을 놓친다.
5. **Grafana 의 HikariCP pending 을 본다.** 0 을 넘었다면 커넥션 풀이 마른 것이고, 그때는
   질의를 아무리 고쳐도 소용없다. `GET /trends` 가 특히 의심스럽다 — 질의는 29ms 인데
   부하에서 10초가 됐다.
