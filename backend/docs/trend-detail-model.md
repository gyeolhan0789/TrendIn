# 트렌드 상세 조회 저장 모델

트렌드 상세 API는 `GET /trends/{trendId}?period={period}`이며 `24H`, `7D`, `30D`를 지원한다.

| 테이블 / 매핑 | 저장하는 값 |
| --- | --- |
| `keywords` / `Keyword` | 키워드 ID, 이름, 기존 `member.domain.Domain` Enum 문자열 (`DEVELOP`, `FASHION`) |
| `trends` / `Trend` | 트렌드 ID, 키워드 FK, 한 줄 설명, 최초 탐지 시각 |
| `trend_metrics` / `TrendMetric` | 트렌드 FK, 기간, 트렌드 유형, 최근·직전 언급량, 두 동일 기간 구간, 분석 시각 |
| 위 지표 테이블에 임베딩 / `TrendEvidence` | 실제 적용한 규칙 버전·설명, 숫자 임계값 JSON, 데이터 완전성 상태 |
| `trend_ai_analyses` / `TrendAiAnalysis` | 트렌드 FK, 실제 AI 상태, 요약, 이유, 생성 시각 |
| `trend_ai_analysis_sources` | AI 분석 FK, 실제 AI 입력 콘텐츠 ID 목록과 순서 |

`growthAmount`와 `growthRate`는 저장된 언급량으로 계산하며 중복 컬럼을 만들지 않는다. 증가율은 소수 첫째 자리까지 HALF_UP 반올림하고, 이전 언급량이 0이면 null이다.

분야 Enum은 중복 정의하지 않는다. 기존 Enum에 표시명 접근자가 없으므로 트렌드 응답 DTO에서 코드별 표시명만 매핑한다. 회원 코드는 변경하지 않는다.

기간은 API 값과 동일한 `24H`, `7D`, `30D`로 저장한다. 모델 생성 시 최근·직전 구간이 `Asia/Seoul` 자정 기준으로 각각 요청 기간과 같고 연속인지 검증한다. API는 해당 트렌드와 기간의 `analyzed_at DESC, id DESC` 첫 결과를 읽는다.

요청 기간 지표가 없으면 기본 정보를 유지하고 기간별 지표 필드를 모두 null로 반환한다. AI 분석은 기간 지표와 별도로 조회하므로 최신 AI 결과가 있으면 그대로 반환한다. 지표의 판정 상태·규칙·임계값과 AI 분석의 출처·시각은 각 생산자가 실제 값을 저장해야 하며, 조회 API는 이를 추정하지 않는다.

현재 콘텐츠 Entity가 없으므로 AI 출처는 실제 입력 콘텐츠의 ID 값 목록으로만 저장한다. 콘텐츠 모델을 임의로 만들거나 키워드의 모든 관련 콘텐츠를 AI 출처로 대체하지 않는다. 콘텐츠 테이블에 대한 FK 및 검증은 해당 저장 모델과 연동할 때 정해야 한다. 이 작업에는 콘텐츠 조회 API와 분석 생산 파이프라인이 포함되지 않는다.

JPA 매핑이 새로운 저장 구조를 정의한다. 운영 DB에는 배포 전 해당 테이블을 반영해야 한다. 테스트 데이터만으로 API를 구현하지 않으며, 서비스 코드에 초기 데이터나 가짜 분석값을 삽입하지 않는다.

조회 서비스의 읽기 전용 트랜잭션 안에서 키워드·기간 지표·AI 출처를 DTO로 변환한다. 기본 정보 조회는 키워드를 EntityGraph로 함께 읽고, 최신 지표 조회에는 트렌드·분석 시각·ID 인덱스를 둔다.

테스트는 세 기간 값 검증, 기간별 최신 지표 선택, `Asia/Seoul` 분석 구간, 지표 미존재, 증가율 0 기준값, 최신 AI 결과의 독립 조회, HTTP 성공·400·404 및 REST Docs를 검증한다. 명세상 401과 실제 JWT 검증은 인증팀 연동 사항이다.
